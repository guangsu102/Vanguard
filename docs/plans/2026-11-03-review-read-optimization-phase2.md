# 审核读取第二阶段：在一期剩余量上再降30%的设计

状态：设计目标，未实施、未发布，收益尚未实测。日期：2026-11-03。

本分期设计已合并到[完整方案 V5](2026-11-03-review-read-optimization-complete.md)。统一配额、记录预留、物理硬限范围及实施顺序以完整方案为准，本文保留作二期设计依据。

前提：[一期读取优化方案](2026-11-03-review-read-optimization-v4.md)。保留普通成员广告满24小时的trial路径，包括一般禁广告规则的覆盖关系；保留原权限、警告、保护、退出、频率和回执边界。

## 1. 目标的正确计算

用户要求进一步降低读取，本方案按“一期之后的剩余量再降30%”设计。若一期下降20%–25%，两期累计相对原始量下降44%–47.5%，不是把百分比相加。

现有四账号样本基线为6941次审核＋续授权读取。一期中位估算省1539次、剩5402次；二期目标再净省约1621次，降到约3781次，累计约45.5%。一期1539本身也是估算，正式验收需先冻结一期实测剩余量。

这需要结构性改变，不能仅把缓存命中率假设调高，也不能靠减少审核完成量、丢事件、延长现场事实有效期或提高预算达成。

## 2. 已确认的结构性读取来源

| 生产实现 | 读操作机会 | 不能误算的部分 |
| --- | --- | --- |
| `group_qualification._classify_history`先对每条有文本消息调用role，随后才判断是否广告/规则 | 无关聊天作者也可能消耗身份额度和续片 | 同collector已有roles缓存，多轮Python分类不等于多次RPC |
| `listener_interest.project`接到正文后只留ID/date并将消息轻量化 | 后续按ID重新取回刚收到的材料 | 第一次接收不证明24小时后原帖仍在 |
| 事实槽`message_id % 32`、候选裁剪及仅取6个提示 | 现有提示无法供完整增量证据消费 | 当前这些提示不能作为48小时完整覆盖 |
| 续授权先new proof_collector，后new collector | 同次事件中的相同作者可能再次核实 | 跨时间需要现场确认的身份查询仍保留 |
| proof/event/旧管理消息分别get_messages，警告辅助又逐个读root | 重叠消息、刚取的原帖可统一读取 | 合并API容器不等于减少真实RPC |

## 3. 核心改造一：先证明足够，再停止无关取证

增加原trial规则的**充分条件快速路径**。先从已有候选中选择一条最可能快速完成证明的广告，而不是先取完置顶、三天首批历史和许多聊天作者。

快速路径要求同时满足：

1. 正确群和本次加入关系，账号可用，非保护/自有/管理身份。
2. 本账号当前确实在群、可发文字，无付费及临时限制等原门禁；系统身份覆盖和资料等本地门禁满足。
3. 已核实当前人数至少50、真实在线至少2；原投放历史和频率/回执不存在阻断。
4. 一条根话题广告的**原发布时间在最近48小时内**，且从发布或最后编辑的较晚时刻起已满24小时。
5. 当前账号确认原帖可访问、内容和时间未变，作者ordinary且非系统成员；警告检查完整且无警告。
6. 没有未处理的相关变化、技术错误或其他足以改变原结果的未知依赖。

这些事实共同排除了原退出分支：已知最近48小时有普通成员广告，人数不低于50，在线不低于2，当前可正常发言；一般广告禁令仍被原先例路径覆盖。因而此分支可确定trial，无须为该结论再普查无关聊天作者或读取全部三天历史。

这是充分条件，不是新的准入门槛。任一条件不满足，回到原有必要取证路径；在线少、人数未知、48–72小时前的先例等不因此被直接拒绝。原帖60小时前发布、36小时前编辑虽可成熟，但不能作为最近48小时新发广告的反例。

候选优先级改为：已有有效锚点、原发布时间24–48小时前且警告线索少的根话题广告，再考虑其他候选。旧48–72小时先例仍保留原有作用。

未读取的规则字段标记NOT_EVALUATED，不能写成“无禁令”“无置顶”或完整覆盖。之后在线/先例等条件变化使群规重新影响结论时，先补齐规则。续授权也不能将NOT_EVALUATED当空规则集合做比较。

普通聊天角色、valid_messages及unknowns改为按依赖求值：正向结论不依赖时延迟；历史重入门禁或48小时无广告退出真正消费这些字段时，仍按原要求补齐。不能删除未知项、将未查作者当ordinary，或凭未采集宣称无广告。

## 4. 核心改造二：接收时保存证据，减少再次拉取

在选择性监听及protocol compact两条裁剪路径之前，将已接收到的有用材料写入可恢复的事件证据日志：

- 广告候选、规则、警告的完整必要正文及媒体/回复元信息；
- 消息ID、作者、群、接收账号、原始日期、编辑版本、删除状态；
- 协议水位、业务持久化水位、可见性上下文和分类器版本；
- 普通消息保留判别索引及覆盖元数据，不为该功能存一份无界聊天档案。

新证据通道不能继续用32槽覆盖旧事实。以消息及事件版本精确幂等；队列上限、写入失败、缺失和溢出必须形成明确覆盖缺口。已持久化的正文才能交给工作者消费；不能推进伪造的业务连续性水位。

工作者遇到规则/警告事件，先消费该账号已收到的对应版本，不再次GetMessages。历史增量由已覆盖消息索引维护；初始72小时缺少基线或真实gap无法恢复时，仍按原规则回填。

不变的必要读取：24小时成熟时仍现场确认原帖可访问、编辑时间及作者身份；没有完整警告覆盖时仍补查回复。A接收的事件不直接证明B可见；消息流完整也不代表角色流完整。

若新管道没有覆盖旧置顶/管理员规则的相关变化来源，不能省略这些必要查询。只以覆盖证据替代相同事实的重复拉取，不凭“没收到”证明没有变更。

本项需要预热。已有历史不会因打开新日志自动出现；正向新候选可能较快受益，完整滚动72小时基线通常需积累相应时段或做一次有界回填。预热读取和缺口补偿均计入成本。

### 4.1 保存必须同时受期限、数量和实际磁盘容量约束

新增材料分为**受保护证据**与**可淘汰缓存**。已接纳的24小时观察证据不得因容量、TTL、LRU或普通日志清理而提前丢失。以下为待实测调整的初始配置建议，尚未应用到生产：

| 材料 | 保存与清理规则 |
| --- | --- |
| 已接纳候选及其必要判定证据 | 独立保护槽，入场即预留完整容量；保护到该版本满24小时并结束一次成熟核验任务，期限细则见4.2；一般清理不能删除 |
| 待处理原始事件副本 | 受保护事实必须先成功转入保护槽，才能确认并删除副本；其他副本处理成功即删，最长1小时，超时未处理需记业务缺口 |
| 非受保护的候选、规则、警告必要正文 | 可淘汰缓存最多72小时；按事件/消息版本时间到期，读取、重试和重放不续期；旧规则需要时读取当前快照 |
| 普通消息分类索引、覆盖元数据 | 可淘汰层仅维护当前72小时窗口；不保存普通聊天正文，连续覆盖区间合并，不逐次追加永久轨迹；保护槽依赖的事实单独保护 |
| 当前选中先例的最小锚点 | 复用既有审核记录中的ID、版本、结论及依赖，只维护当前需要的引用，不再长期复制正文 |
| 新缓存的诊断日志 | 最长24小时并按大小轮转；不记录正文，不在日志中复制一份证据 |

上述期限只约束新增业务证据副本，不用于清理SDK协议恢复日志、推进pts/seq或跳过未处理的协议更新；超时产生的是业务证据覆盖缺口，现有协议恢复照常执行。普通层72小时TTL不能覆盖保护槽的生命周期，也不延长任何原业务事实的有效期。原发布时间和编辑时间仍分开记录，不能用编辑或回填时间把原帖伪装成最近48小时发布。选中锚点存在也不等于原帖仍可访问、作者身份未变或没有新增警告。

初始容量建议为：**所有账号合计新增证据逻辑占用最多256 MiB、最多10万条记录，其中192 MiB预留保护槽，64 MiB用于可淘汰层；单账号单群的可淘汰层最多1 MiB/1000条；单条正文最多16 KiB；新增证据存储实际磁盘最多1 GiB。** 保护槽另设固定数量及每账号每群配额，数量按单包最坏预留占用计算，不能按当前正文很小而超卖；字节和记录数都必须提前预留。任何进程或副本不得各复制一份额度。正文超过单条上限时不能作为完整证据接纳，只留定位信息并按原流程取证；不能截断后继续声称警告/规则检查完整。不下载图片、视频、文件，仅保存需要的Telegram引用及必要属性。

256 MiB必须同时计算待处理入箱、正文、普通索引、去重键、缺口、保护控制状态及失效标记等新增记录，不能把淘汰材料转移到另一张无上限表或死信队列。正文按群、消息及版本去重，账号可见性仍分别保存，内容去重不能合并访问证明。所有元数据也受额度限制；若无法保留精确缺口，提升为对应账号/群覆盖整体失效，缺失状态默认未知。普通缓存或普通缺口记录不得借用已承诺给保护槽的剩余容量。

1 GiB是独立证据载荷存储的**物理硬限**，需要独立存储配额或真正定长的文件布局落实，并包括索引、WAL/日志、临时文件和整理峰值；只做SQL计数或定时DELETE不能声称已经实现。硬限无法落实时，暂不启用新增持久化证据载荷，继续原有按需读取。不得为这项优化修改共享PG配置、挤占Redis现有业务空间或执行共享库VACUUM FULL。PG的DELETE不保证文件缩小，Redis键过期也不保证RSS/AOF立即缩小，这些额外占用不能漏算。

清理规则：每层分别计量、写入前校验预留，并由本地每5分钟清理任务兜底；该任务不请求Telegram。可淘汰层达到自身额度80%先清到期及已消费材料，90%开始淘汰低价值可重建材料，满额拒绝普通缓存写入。保护槽只按4.2规定的终态释放，不能因全局或单群达到上限被普通淘汰器删除。保护区满时停止接纳新持久化观察任务，已有预留继续履约；新候选仍走原按需审核，这只是缓存接纳限制，不是新的业务准入门槛。写入前原子预留容量，整理使用独立已预留的峰值空间，不创建无上限临时副本。

可淘汰层窗口外自然过期可推进保留窗口；其窗口内或未处理材料被淘汰，必须先标记覆盖缺口，再删除。**已进入保护槽的判定依赖不走这条淘汰路径。** 已应用到当前判定的警告/删除/编辑事实不能因原始事件过期被撤销。实际故障造成受保护材料不可恢复时，标记技术缺口并按原流程补证，不能默认存活、无警告或48小时无广告；故障降级不是允许正常提前清理。

回填仅服务当前必要任务，合并相同需求并按原预算执行；容量不足时直接供同次任务消费，不立即把刚淘汰材料重新写满，不触发全群全量重拉。TTL清理、容量淘汰和补偿读取需分别统计；补偿RPC计入二期净成本。若有界空间不足以支撑30%的收益，优先遵守容量上限并报告实际降幅。

### 4.2 24小时观察采用先预留、后接纳、到期核验的保护槽

保护对象是账号可见性上下文中的**具体消息内容版本及其必要依赖**。入场时先持久化原帖必要正文、ID、原始/编辑时间、版本、覆盖状态及相关事实，再确认接纳；必要事实尚未转存成功时，不能因原始副本到期而删除唯一一份材料。

单槽预留必须覆盖正文、索引、受保护依赖、状态更新和整理峰值的最坏占用。回复取证仍有原上限50，按需预留相应最大空间；无法计算或无法承诺空间的任务不进入该优化路径。每槽另有固定大小控制区和提交所需空间，不能被正文挤占。

正常生命周期如下：

1. **接纳：** 原子取得字节和记录配额，成功落盘后进入观察。保护区无空间时不接纳新缓存任务，不删除既有观察证据腾位。
2. **观察：** `t_ready = max(date, edit_date) + 24h`。到此时刻前，普通TTL、容量淘汰、LRU及“事件已消费”均无权删除保护槽；重放和读取不改变成熟时间。
3. **成熟：** 到时进入原有预算调度，现场核验可访问性、内容/时间、作者和必要警告。时间满24小时只意味着可核验，不自动获得trial。
4. **结束：** 核验任务记录结论、依赖和覆盖状态后，释放完整载荷保护，只留下原机制需要的最小锚点；载荷可在可淘汰层有剩余空间时短期复用，不能无条件再复制一份。

核验长期阻塞也不能无限占槽：建议给成熟核验预留有限宽限期，初始可设6小时，截止为`max(admitted_at, t_ready) + 6h`；具体值需根据现有调度实测。**该截止一定在满24小时之后。** 同一版本的重试、重放、再次排队不能顺延截止。截止仍无法核验时，本次优化任务明确结束为UNKNOWN/待补证，保存最小定位及缺口、转回原技术恢复和按需取证，再释放载荷；不能据此通过、判无广告或作业务拒绝。这个截止只结束一次缓存优化任务，不缩短原业务证据窗口或修改准入规则。

编辑、删除和警告不能被满额挡住：优先在预留控制区写入版本失效、警告存在/待核实、源ID及缺口等事实，并使相关旧结论失效。相关新正文放不下时，明确置为证据不完整、按原规则补证，不能继续当成无警告。语义控制状态可合并覆盖，不保存无限事件或版本链；无法在槽内完整表示的依赖进入UNKNOWN。

编辑使旧内容版本结束观察，必须先记EDITED及原版本失效；新内容版本从新的`max(date, edit_date)`重新计算24小时，并重新申请空间，不能继承旧版本已等待的时间或自动延长旧任务。真实删除或原规则确认候选不再适用时可以提前结束其保护，保留必要失效事实；磁盘紧张不能被当成“候选失效”的理由。

保护槽与可淘汰层必须使用独立计量、配额和清理入口。验收要求普通清理器对任何尚未终结的保护槽删除数为0；配额满时拒绝的是新缓存接纳，不能撤销已有保护承诺。

## 5. 核心改造三：一次事实任务只有一个读取集合

同账号、同规范群、同事件快照内，把先例、事件及旧规则消息ID合并为唯一读取集合。查询返回后由各判定步骤引用同一份原始响应。

- proof_collector与规则collector共用同次已核角色；不同事实时段或失效版本不共享。
- 已新鲜取得的root传给警告核验；缺失root批量取，不逐帖再取一次。
- 原帖明确声明回复数0且同快照无相关变化时，可以直接表示空回复集合；`None`或未知不能等同0。仍保留其他现有警告范围和来源要求。
- 存在回复时按原范围读取，声明数量、实际数量、上限50及警告判定均保留；不能只检查管理员回复。
- 证明一条已足够且其他依赖齐全时，停止继续核验额外5条先例。
- 规则作者较多时按成本选择完整管理员列表或新鲜参与者对象，只有实际返回的有效身份才能作为相应证明；名单不完整/缺席不能制造ordinary。

GetMessages按ID合并只有在最终实际RPC变少时计收益。返回NotModified、压缩字节或把多个独立RPC装进一个容器，均不直接计为读取次数减少。

## 6. 原规则不可省的路径

冷启动且没有正向候选、需要确认48小时无广告退出、历史不可见、角色覆盖不足、警告线程超限或存在真实gap时，可能仍需要完整取证；快速路径不能覆盖所有群。

所有原保护、账号权限隔离、收费/禁言、内容范围、发言频率、未知回执和退出前新鲜度要求保留。不通过固定15分钟TTL巡检换取表面“新缓存”，不通过缩短原历史窗口达标。

快速路径是读顺序与充分条件早停。上线前必须逐项证明未读取字段不会翻转该分支结果；无法证明的分支保持原读取，不能为达到百分比强行跳过。

## 8. 实施与验收

1. 先记录逐调用用途、参数、实际消费者及“是否本可跳过”，并审计valid_messages、unknowns和角色覆盖的全部消费者。
2. 为充分条件快速路径写判定等价测试；运行影子读取计划，仅使用既有事实，不额外请求一套Telegram做对照。
3. 接入裁剪前事件证据日志，确认水位、重放、溢出和恢复，落实期限、条数与物理磁盘硬限，完成必要预热。
4. 同轮读取集合与快速路径分别开关；一个账号灰度，保留完整回退取证和单一真实执行器。
5. 先冻结一期实测基线，再至少观察三个完整且可比较的预算窗口，区分预热期和稳定运行期。

验收条件：二期实际审核相关成本不高于一期的70%，所有通道合计也证明净减少；同等业务工作量、准入条件、新鲜度及处理时长不下降。快速路径命中率、角色必要查询比例、推送直接消费率和回填占比必须可解释。

存储验收还需覆盖：突发大群流量、单条超长正文、消费者停滞、清理失败、多进程同时写入、跨窗口重放、保护区满时的新任务接纳、23小时59分遇到TTL/容量/LRU清理、编辑重计、预留控制区处理新警告和删除、成熟核验超时及整理无剩余空间。上述情况下新增存储不得超过实际硬限，普通清理器不得提前删除受保护证据，不得保留伪完整覆盖，不得通过反复全量回填制造读取风暴。
