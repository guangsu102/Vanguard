# 2 号会话异常、审核额度和加群阻塞改进方案

本文回答本轮发现的问题及改法。依据为 11 月 4 日夜间只读生产核验、生产源码 SHA 对比和无网络离线 SDK 契约复现；本轮未修改产品代码、账号、配额或生产配置，未调用 Telegram。下面是实施方案，不是已修复结果。

## 2 号为什么异常

直接触发原因已经确定：21:03:26.839902，Telethon 抛出 MTProto **wrong session ID**；21:03:28.448657，账号池拒绝继续使用该会话。SDK 已通过包的 auth_key_id / msg_key 检查，但解密后包里的 session ID 与本地当前 MTProto state.id 不同，于是触发 SecurityError。Vanguard 守卫随后隔离、断开连接并释放租约，账号持久状态变为 ERROR。

这是 MTProto 连接会话标识，不是 Telegram 用户 ID。有限范围日志没有发现 AuthKeyDuplicated、Unregistered、Revoked、身份校验不符或 lease generation replaced 的对应标记，不能据此断言代理共用、密钥重复、会话被撤销或账号被盗。为什么会收到不同 session ID 的包，现有日志仍缺连接代次关联，不能把候选诱因写成已经证明的根因。

已另外证实一个必须修复的生命周期缺陷：

- 生产 Telethon 1.45.0 的 `disconnect()` 在运行的事件循环内返回被 shield 的 **Future**。
- `session_guard.py` 的部分清理只在 `asyncio.iscoroutine(result)` 为真时等待；Future 不满足该条件。
- 生产 SDK 两个关键文件 SHA 与本地一致。使用真实 SDK 方法和假接收器做离线复现：返回值是 Future，旧条件执行后 transport 仍未关闭，真正 await 后才关闭。
- 因此 `await old_guard.close()` 并不总能保证旧连接已关闭，存在清理未完就释放会话租约的窗口。这是已证实的代码缺陷；它是否实际造成 2 号本次错误包，尚需代次日志证明。

反证边界：正常 SDK reconnect 会取消并等待旧 send/recv，再 reset 同一个 state；hook 绑定这个 state 的 decoder，不意味着 reset 后仍比较旧 ID。r9 stage timeout 也等待服务栈清理，不是超时就立即释放执行槽。不能把所有常驻 listener 或正常 reconnect 当双持有。

## 为什么审核预算仍不足

总限额保持每账号 180/分钟、360/小时、3600/日。用途分配、小时约束和准入债均可能先于总限额阻止工作。

| 问题 | 已确认依据 | 改进方向 |

| 34 号总日剩 40、审核仍为 0 | 剩余由存活 25 和广告 15 保护；critical 已用超过已消费贷款调整后的额度，review/join opposite_hold 均 0 | 保留真实保护；只重算未用预测和释放未用预留，不能回收已花贷款制造余额 |
| 34 号续检有 15，却仍可能等待 | 默认完整续检最低 16，和实际剩余阶段没有完全衔接 | 能证明有界时执行 6/14 读计划或可持久保存的小步骤，后续依赖完整前不放广告 |

752、376 是保守预测债，不能称为已经发生或确定必需的远程读。新群 60 也是未知路径下的生命周期预留，不能为了开加群直接删除。缺审、旧 policy 必须明确生成修复工作，不能忽略或默认为通过。

## 按顺序实施

1. **先修会话关闭和隔离持久化。** 将清理路径的返回值判断改为完整 Awaitable 契约，覆盖 hook fallback、quarantine、close 和通用回调。等待旧 transport/send/recv 清理完成后才能交接 generation；有界清理超时必须继续隔离并阻止新 owner 联网，不能当关闭成功。记录有限枚举原因、连接代次、关闭确认和 lease 代次；日志不写 auth key、session 内容或网络凭据。对 2 号先核验本地会话对应关系和旧 owner 清理状态，修复后受控恢复并验证身份；未知广告/加群结果先对账，禁止自动重放。
2. **修数据库长占用，保持共享库连接边界。** 20:50—21:10 的完整有限范围 growth 日志中，4 条明确包含 QueuePool limit：RPC 守卫 2、私有 outbox 1、会话隔离落库 1。说明应用连接池耗尽参与了故障，但没有证明它造成错误 session ID。将有问题的外层事务拆成“短事务读取带版本快照 → 释放连接 → Telegram/AI/Redis 等待 → 短事务校验版本并提交”。隔离状态写入需要受保护的短事务及可重试持久化路径；失败时运行隔离围栏保持有效。生产仍按每进程池 2+overflow 1、项目账号总连接上限 25 设计，不通过普遍扩大池掩盖占用。
3. **统一工作清单，先做不耗读的收尾。** 每项绑定 account/membership/joined_at/policy/profile/evidence generation，给出 ready_at、deadline、下一段最大读、剩余保守总读、依赖和是否可本地完成。首审、续检、观察成熟、终态和缺审修复分清；同一义务去重。纯本地完成为 0 读优先，未来成熟不占当前活动槽，未来截止义务仍纳入计划。
4. **小步执行并按真实需求分配。** 预留下一有效步骤及必需控制开销，完成后持久 checkpoint、结算真实读并释放未用部分；不得重复读取已完成页。首审/续检独立公平队列，按真实用途计费。优先硬截止、已承诺结果核对和阻塞现有广告的续检，再考虑新加群。已消费贷款不能回收，账号间不能转移额度，存活/listener/sync 等真实保护保留。
5. **重算加群准入和唤醒条件。** 审核债复用执行器的真实剩余计划，按小时/日及截止时间检查已承诺义务，再支付新群完整生命周期；不再用泛化 pending 数代替全部债。纯未来等待/终态不占执行容量，缺审/未知不能消失。工作结算、释放预留、hold/窗口变化触发同账号同用途的合并唤醒，同轮共用预算快照，减少空查；成熟期、平台 cooldown 仍不可提前绕过。
6. **修历史状态语义，保留不重复执行的围栏。** 6 条 pending/sent/resolved 的“resolved”可能只是风险清理停止调度，并不一定证明 Telegram 结果。不能简单加一个 `resolved` 排除条件就全部放行。拆开停止对账、请求阶段、远端结果和目标去重围栏；按真实已加入事实、明确平台响应、未知结果分别结算。未知仍保留目标围栏，只做必要事实核对，不直接删除/重发。

## 状态与统计一并修正

现有加群代码在真正 Telegram RPC 前就持久写 `sent` 和 `telegram_action_attempted`。它们更接近请求前意图，不能普遍当成 SDK 已进入、Telegram 已接受或已加入。取消也可能发生在 RPC 前、RPC 中或成功落库前，必须区分。

新读模型至少展示：intent 已持久化、RPC 已进入、平台明确响应、成员事实已确认、结果未知；把“停止自动对账”和“远端结果已解决”分开。任何无法证明未发出的边界故障都不能自动重放。历史行缺少新阶段事实时保留 unknown 并定向核对，不伪造 ACK。

上一轮窗口的加群意图标记和成功均为 0，因此“未观察到新加群产出”的结论不变；非零场景必须按上述阶段分别统计。广告 unknown 同样按消息回执对账，不自动重发。

## 验收和不可放宽的条件

- Future 返回、真实 close 等待、清理取消/超时、旧 generation 围栏均有离线回归；未确认关闭时不能建立新的可联网 owner。恢复 2 号后再用自然运行验证稳定性，不能只看 ONLINE 字段。
- 证明指定长事务路径在等待 Telegram/AI 时不持有数据库连接；RPC/隔离写入不再因后台审核占满同进程池而失败。用连接等待时间、持有时间和 QueuePool timeout 计数验收。
- 健康、无平台限制、下一步可支付的任务，建议初期 SLO 为 95% 在 120 秒内开始；纯本地收尾在两个调度周期内完成。资金不足或证据不完整必须显示准确原因，不能靠无限重试满足 SLO。
- 初期可在准入时保护审核消化 24 读/小时的目标（每日最多 576），仅在已证明闲置且总额允许时临时增加；已耗尽的窗口不承诺补发。先按真实剩余计划重算债，不能把 752/376 直接当预计完成耗时。
- 总额/贷款守恒、未知结果不重放、广告授权完整性、群规则及普通成员广告先例的既有机制全部保留。24 小时成熟等待按原语义执行；分段和清理不提前删除保护证据，中间进度不授予广告权限。
- 同时观察实际远程读、重复前置读、空转次数、广告成功、真实加群阶段和积压年龄；不以“没运行所以读少”作为优化成功，不承诺未经实测的节省比例。
