# 广告优先、补群其次、监听积压治理方案

状态：核心改造已于 2026-09-29 01:47:28（北京时间）部署，完整验收进行中。下文保留原 01:04:49 方案基线；最新实现、未完成范围、生产回执、历史清理审批及回滚资料见 [发布报告](../reports/2026-09-29-bounded-listener-release.md)。不能将方案中的全部目标视为已经实现或验收通过。

## 目标与可兑现的边界

优先保障到期广告及其必要核验，其次保障补群和入群验证。监听负责提供必要业务事实，不把全部群聊历史当成需要永久保存的业务任务。

治理目标是普通闲聊不形成无限磁盘队列，已完成事件及时释放，一个群的同步缺口不拖住其他已确认事件，补同步不能耗尽广告和补群保底。网络中断或 Telegram 冷却期间仍可能有关键事件等待；不能同时承诺任意输入量下完整保留一切历史、零等待和发送必成功。

继续保留：广告读取 35% 保底、成熟群每 24 小时检查上一周期最后一条广告、成熟群不占 30 个试投成功名额且不抵扣补群缺口、总群上限 300、账号 3 隔离、真实 Telegram 冷却和结果未知防重发。

当前代码存在三处需要结构性修改：

1. `listener_journal.py` 在 SDK 排序和业务过滤前把完整更新包写入 SQLite。下游过滤闲聊仍然不能避免上游落盘。
2. `listener_checkpoint.py` 以全局没有 `getting_diff_for`、`possible_gaps` 作为统一确认条件。一个频道存在缺口，会延迟其他已处理记录释放；重启又会加载这些 pending。
3. `rpc_budget_policy.py` 中同步和补群仍共用普通 50% 父额度。把候选预览从 background 改为 critical，只改变子额度，未消除父额度饥饿。

此前清理的 95,704 条是历史批次，现有记录是之后产生的。继续定期全删不能修复这些缺陷。

## 1. 将业务保留范围收窄到实际用途

生产当前 ordinary_group_messages_required=false。普通聊天正文不进入长期可重放队列。仍保留：本账号广告的删除/编辑和明确相关反馈、本账号权限/成员身份变化、入群验证、私聊，以及已有自营群功能真正需要的事件。关键词或 AI 监听将来启用时，必须显式恢复对应消费范围和容量规划。

删除事件先按账号、群类型、群 ID、消息 ID 与已发送广告索引匹配；无法确定归属的事件进入有界核验流程，不能直接当作无关删除。不能把任意其他成员的回复、任意机器人发言都长期视为推广关键事件；验证期间的未知提示应保留并标明原因。

过滤不额外调用 Telegram 查询每条消息。使用本地索引、当前入群验证状态和已加载实体；未知类型先保守分流并监测，避免策略过期后退回无限全量落盘。

协议仍必须正确处理 seq/pts/qts。采用经过测试的最小事件表示保留排序、缺口判断与崩溃恢复所需字段；连续且已处理的普通更新合并为游标区间。不能在 SDK 排序前简单丢整个更新包，也不能把“看到更大的 pts”当成“中间都已完成”。协议依据：[Telegram Working with Updates](https://core.telegram.org/api/updates)。

## 2. 按真实依赖确认，消除跨群拖累

为更新包记录账号级 seq 依赖、各频道 pts 依赖、业务 inbox 幂等写入结果。只有这些依赖满足时才确认该包；跨多个群的混合包必须全部满足，不按单个群粗暴放行。普通群和私聊共用账号消息序列，不能假定每个群都完全独立。

独立频道 A 的缺口只阻挡依赖 A 的记录；已完成且不依赖 A 的记录可释放正文。账号级真正缺口仍保留必要阻塞。游标提交和 journal 确认保持同一 SQLite 事务；业务 inbox 通过幂等键容忍提交边界崩溃，不能先确认后入库。

面板拆成：尚未交给 SDK、已交给 SDK 等待依赖确认、业务待处理、需要核验。分别展示数量、字节、最老年龄、所属账号/群与阻塞原因，不继续用一个 pending 数字表示全部工作量。

## 3. 广告、补群、同步分别分配预算

建议第一版采用以下分配，按分钟/小时/天同时受总额度约束，整数分配的合计必须等于总额度：

| 用途 | 比例 | 当前 1,680 次/日下的基数 |
| --- | ---: | ---: |
| 广告发送前必要读取、发送结果核对 | 35% 独立保底 | 588 |
| 广告存活和相应必要核验 | 15% 独立保底 | 252 |
| 补群候选预览、加群必要读取、入群验证/结果核对 | 25% 独立保底 | 420 |
| 必要协议补同步 | 20% 基础额度 | 336 |
| 资料刷新等可延后任务 | 5% 弹性额度 | 84 |

这些是本系统预算，不是 Telegram 承诺的限额，也不是每日群数或广告条数。25%/20%/5% 为拟议初始配置，需用每次实际 RPC 成本校准。

广告优先使用弹性额度，其次补群，最后同步和资料刷新。有补群需求时，同步不能动用补群保底；广告和存活保底相互保护。不得提前消耗另一业务本窗口尚未使用的硬保底后，仍宣称该保底可用。额外借用必须限定在真正未分配的弹性额度或已明确释放的容量，记录借用来源。

到期广告先调度；影响本次发送的删帖、禁言和未知结果核对属于必要前置。补群在广告间隔和自己的额度内持续推进；成熟群数量不抵扣补群需求。同步按账号/群公平调度，不能让单个活跃群反复吃满同步池。预算等待应释放执行槽和操作租约，由 next_attempt_at 唤醒，避免等待本身占住账号。

迁移保留已有总消耗、窗口 TTL 和真实冷却；不能通过清零计数制造容量。旧普通窗口缺少细分账目的部分采用保守过渡，说明首个窗口可能暂时不足，不伪造归属。

## 4. 对超载明确处理，而不是无限重放

普通聊天：连续已处理事件合并为游标，正文不留存；无业务消费者时不为恢复闲聊正文额外翻历史。协议必须取回的差异仍正常处理，不能假定 Telegram 可以只返回我们关心的事件。

重复状态：按账号、群、事件类型合并重复任务，只保留最新待办；负面证据有独立标记，后来的普通状态不能覆盖已知删帖/禁言。

已发送广告：继续按已知消息 ID 做定点检查，成熟群常规检查每 24 小时一次；发现缺口涉及广告状态时可进行有原因的异常核验，不恢复例行 2 分钟/1 小时检查。确实无法核验时只限制受影响目标，不把普通群同步等待扩散为全账号广告禁用。

每个队列设置数量、字节和年龄监控及可恢复的超载状态。普通内容可以压缩/舍弃，已完成记录可以删除；关键未决记录不能仅因超时被标记成功或丢弃。严重断线时保留最小待核验状态并报警，按真实范围承认延迟，不能把队列截断伪装为零积压。

## 5. 现有记录的迁移与部署顺序

1. 先完成依赖确认和预算分配的实现、回归，备份代码、数据库和 listener journal，冻结写入时生成可审计的清单。
2. 把当前 pending 与 inbox 幂等键、已提交游标对应起来。能证明完成的释放；无消费用途的普通正文按新表示压缩；尚未确认的关键事件保留最小必要记录。
3. 对 419 条 reconciliation_required 单独分类，列明可本地完成、需定点读取和无法恢复的数量，不全部标成成功。
4. 灰度一个现有账号，按真实回执验收广告和加群，再观察完整 24 小时周期。出现游标跳跃、关键事件遗漏或重复发送立即回滚应用逻辑；不回滚真实发送账本，不重放未知发送。

## 6. 验收条件

- 混合账号/频道序列、空差异、DifferenceSlice/TooLong、乱序、重复更新、重启、数据库写入失败均有明确恢复路径。
- 人为制造一个频道缺口，其他没有依赖该缺口的事件仍确认释放；队列数字能区分“未处理”和“等待确认”。
- 普通群聊流量压力下，保留正文和逐条确认记录不随累计闲聊量线性增长；关键队列在消费恢复后下降，不靠全量清空达标。
- 同步额度耗尽时，广告和补群各自保底仍可申请；总消耗不超限，真实 FloodWait 不被缩短，旧计数不清零。
- 广告成功凭新 Telegram 消息 ID 和成功回执确认；加群凭真实成员结果确认；未知结果没有重复操作。
- 成熟广告仍不占 30 个试投成功名额、不抵扣补群缺口；总群上限仍为 300；成熟群只保留 24 小时例行检查。
- 正常连接且未受真实平台限制时，关键事件处理延迟目标 P95 不超过 30 秒；超过 2 分钟给出明确原因。此为拟定验收目标，不是当前已达成指标。
- 连续观察 24 小时，普通正文无持续增长，已完成记录正常释放；用峰值流量、关键事件年龄、实际广告回执和补群结果共同验收。
