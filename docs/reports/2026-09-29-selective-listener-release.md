## 实施规则

1. 普通推广群聊天、机器人回复、提及、状态和输入提示不再因为“可能有用”而完整落盘。没有业务消费者的正文在入口释放。
2. 已知自身广告删除通知留下小型、可去重事实。新发送与策略刷新之间存在短暂竞态，因此未知删除 ID 按群合并并限制最多 512 个，再在本地数据库核对是否属于自身广告；不会读取整段群历史。
3. 本账号退出、被移除或禁言等负面变化触发资格复核；旧的成功入群通知不能把已审核群重新降为首次审核。入群验证线索仅在当前入群阶段及有效时间内保留。
4. 私聊、自有群管理、已启用的关键词/AI 消费仍按既有业务处理。未知外部动作不能凭空判为成功或重新发送。
5. 原始 pending 和旧待核验记录均可在本地分批投影；即使 Telegram 同步正在等待额度，也能提取必要事实并释放无用记录。
6. 事实先在 SQLite 保存，再在 PostgreSQL 提交，成功提交后按版本确认删除 SQLite 待办；中断后可幂等恢复。重复删除通知不会清除正在执行的存活检查 claim。
7. Telegram SDK 保留最多 1,000 个内存协议缓冲及有界恢复标记。它们不是需要逐条处理的推广消息历史；溢出后交由 SDK 正常补同步，不伪造 pts/seq 检查点。

广告 35%、存活 15%、补群审核验证 25%、同步 20%、弹性 5% 的预算规则未变。成熟群仍按每天检查上一周期最后一条广告的规则运行；真实删除信号属于异常处理。试投名额 30、成熟群不抵扣补群缺口、总群上限 300、账号 3 隔离、群 1 身份保护均保留。
