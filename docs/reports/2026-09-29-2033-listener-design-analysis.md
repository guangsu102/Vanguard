# 回调监听与审核阻塞：生产设计分析

采集时间：2026-09-29 20:24–20:31，北京时间。目标：oracle4c24g:/opt/vanguard。

**结论：存在确定的设计与实现缺陷。此前改造已使“连接正常时，已收到的关键事实入库”与补同步等待部分解耦，但没有保证冷启动/重连时恢复回调接收，也没有把线上删除处理完整改为事件直接驱动。将当前问题简单描述为“读取额度不足”不充分。**

生产仍为 `local/vanguard:frequency-schedule-d3939fce49ad`，镜像 `sha256:f5711b17582f8b12e55e04b00591d030691e33e84ecab42bfac3c118fcf59055`，Telethon 1.45.0。本文分析使用从运行容器只读导出的源码；本地工作区多个关键文件与线上不同，不能用本地候选行为代表生产。

本轮没有修改应用、部署、重启、清零预算、连接 Telegram 进行主动验证或发送消息。新增的是本地诊断脚本、源码快照和本报告。

## 1. 当前直接原因：回调连接的恢复依赖已耗尽的同步池

20:27 的实时证据：

- Growth worker online，心跳新鲜；实际 active_listeners=0、connected=0，账号 2 为 deferred / telegram_read_budget。
- 无当前 RPC cooldown 键；分钟、小时预算计数已到期。阻挡来自本系统日窗口分配。
- 磁盘最后检查点为 11:31:07，11:31:30 新容器启动；本容器日志没有成功连接或挂载回调处理器记录。
- worker 的 raw_journal 来源为 disk，没有活动客户端提供的运行中监听快照。
- 账号 2 最新 listener_fact 入库时间为 11:02:07。这个时间不证明那之后 Telegram 没有相关事件，但不能据空业务队列声称监听持续正常。
- 2 条约 700 字节协议待办，最老约 9.8 小时。当前大量旧正文积压已经消除；剩余问题是连接与恢复能力。

生产调用链：

```text
进程重启 / 监听断线
  → _ensure_growth_listeners
  → check_read_ready(purpose='growth_listener', requires_bootstrap=True)
  → 检查 sync 读取预算
  → 额度不足，抛 RpcDeferred
  → 不执行 connect_by_id
  → 不挂载事件处理器，不恢复回调接收
  → 等日窗口到约 22:41 后重新评估
```

生产源码位置：`source/app/workers/telegram_worker.py:597`、`:599`、`:610`；`source/app/core/account/rpc_governor.py:201`。

这是明确的生命周期耦合：一个用于主动补同步的预算检查，决定是否连回回调传输。当前代码对“已有连接”已有例外，连接活着时不会仅因预算为零而在每轮巡检中强制断开；但冷启动没有独立恢复路径，也没有为必要初始化留可兑现的保底。

离线执行生产函数验证：相同零同步额度下，已有连接继续维持；无客户端的冷启动在调用 connect_by_id 之前就被拒绝，连接调用次数为 0。因此上一版只覆盖了连接存续路径，缺少重启/重连路径验收。

SDK 更新循环还存在有限的保活例外：GetChannelDifference 等待时继续处理其他群更新，GetDifference 等待时保持传输并接收原始包；其他内部读取拒绝仍走 ListenerPause 并断开。该分支是额外脆弱点，不能断言它就是这次停连的实际触发原因。本次证据更直接支持发布重启后的启动前预算拒绝。

## 2. 预算口径修正：分项“满额”包含历史消耗补占

当前同一日窗口原始计数：

| 通道 | 新分项计数 | 未细分历史消耗补占 | 门禁按此判断 | 基础份额 |
|---|---:|---:|---:|---:|
| 广告 | 588 | 0 | 588 | 588 |
| 存活 | 96 | 0 | 96 | 252 |
| 审核/补群 | 344 | 76 | 420 | 420 |
| 同步 | 201 | 135 | 336 | 336 |
| 弹性 | 48 | 36 | 84 | 84 |
| 合计 | 1277 | 247 | 1524 | 1680 |

`reserved_reads.classified()` 将总量与新分项之差 247，按“先同步、再审核/补群、最后弹性”补入各池。Redis Lua 执行同样的保守归类。

这 247 已存在于总使用量，没有又给总计数多加 247；问题是无法归因的旧消耗在新策略下压满了三个业务池。因此此前“同步已用 336、审核已用 420”应准确表述为**含历史保守分摊后的门禁占用**，不能声称全部是该用途的已测 RPC 次数。UTC 每日用途遥测与当前滚动窗口起止不同，也不能直接相减还原这 247 的真实用途。

总剩余 156 全部是受保护的存活份额；线上没有空闲存活预算借用实现。保留历史总量和真实窗口是正确的，但没有设计迁移窗口里的监听恢复资源，导致保守迁移与启动门禁共同形成长时间饥饿。解除归类不能靠清零真实消耗。

位置：`source/app/core/account/reserved_reads.py:18`、`:27`，证据 `detail.json.classification`。

## 3. 明确删除回调在线上仍转为读取任务

线上已经在原始更新入口投影并保存自己的广告删除事实，不需要读取群历史才能把该事件入库。但最终处理仍调用 `queue_deleted_observation()`：

```text
收到删除更新
  → 精确匹配账号 / 群身份 / 已发送消息 ID
  → survival_status = pending
  → survival_error = deletion_event_requires_confirmation
  → 等后续读取核验
```

位置：`source/app/core/account/listener_facts.py:51`、`source/app/modules/acquisition/adaptive_frequency.py:556`、`:587`。

对于归属和周期均可确定的官方删除事件，这没有兑现“回调直接记录删除事实并执行相应频率规则”的要求。回调缺失、身份不明或结果未知仍应定点核验；不能把这些不确定情况与明确删除事实统一变成一次额外读取。

更具体的衔接缺陷：成熟广告原状态为 not_required / daily。删除回调将其设为 pending，但保留 daily。普通存活 worker 的 claim 和扫描都明确排除 daily，而回调没有提前推进群级 daily_review_due_at。因此“把该消息 due_at 设为当前时间”并没有让成熟群删除异常立即进入处理链。每日任务最终可能检查该消息，但还取决于周期选择，不能视为已及时完成删除处理。

位置：`source/app/modules/acquisition/automation.py:13124`、`:13147`、`:13471`；`source/app/modules/acquisition/daily_frequency.py:364`。

离线执行生产删除函数复现：已匹配自身广告的删除事件得到 pending / daily / deletion_event_requires_confirmation，普通存活 deadline 为 None。此为源码和离线复现确认的处理缺陷；本轮没有证明某条实际广告已被删除却漏处理，因为当前断连期间缺少完整实时事件证据。

本地已有 `cycle_deletion.py` 候选，设计为明确删除直接处理并用周期检查兜底；它尚未部署。即使只部署这个候选，也不能自动修复监听冷启动门禁。

## 4. 本地事实消费仍间接依赖活动监听列表

`_project_growth_listener_facts()` 只遍历 `_growth_listener_sessions`；`_process_growth_inbox_once()` 也把这张列表作为 inbox 领取范围。`event_inbox.claim()` 收到空列表立即返回。

位置：`source/app/workers/telegram_worker.py:711`、`:731`；`source/app/core/account/event_inbox.py:101`。

当进程重启、预算拒绝启动时，该列表为空。即使磁盘或数据库已有只需本地处理的事实，也不能通过这条路径继续消费。“本地投影可在同步等待时执行”只在内存里仍保留监听对象的前提下成立，没有覆盖冷启动恢复。

这是已由生产函数离线确认的恢复缺陷。本次业务事实待办为 0，所以不能把它说成当前两条协议待办的直接原因，也不能宣称它已经造成某个实际删除事实丢失。

## 5. 审核仍是主动采证流程，没有改成回调证据驱动

需要区分两种工作：

- 已发送广告的明确删除、成员/权限变化：回调携带足够且可信的信息时，应主要依靠本地事实处理。
- 新群准入、规则、成员身份、历史广告可存活证据：未来消息回调不包含完整现存信息，必要的首次快照、缺口修复和定点核验仍需要主动读取。

生产审核 `assess()` 仍会 get_entity、get_me、调用 EvidenceCollector.collect。当前消息入口为了避免保存无关聊天，会清空没有显式消费者的普通群消息正文；资格观察没有完整接入一个有界回调证据消费者。因此现在的实现不能同时声称“审核消息证据都由回调维护”与“普通消息全部释放”。

位置：`source/app/modules/acquisition/qualification_service.py:895`–`:934`；`source/app/core/account/listener_interest.py:165`。

当前 10 条停滞审核被统一 critical 预算挡在采证前。checked_at 保留 09-27 01:54–02:01 是因为没有真正开始新读取，系统只更新 next_retry_at；不代表这两天不断真实读取了同一批群。

另一个前置门禁问题：run_reviews 在进入 assess 前无条件执行 read_wait，而 assess 内已有“有效现存证据直接重做 AI 判定”的分支。即使某个任务仅需本地证据和 AI，也可能先被 Telegram 读取预算拦下。此为代码路径问题；并不意味着当前 10 条缺证据任务都可以直接跳过采证批准。

位置：`source/app/modules/acquisition/qualification_service.py:1812`、`:895`。

## 6. 为什么回调系统仍需要少量协议读取

Telegram 用户账号事件通过授权连接推送，启动需要初始化连接；pts/seq 出现缺口时需要通过差异接口恢复顺序。这类协议恢复与逐条轮询消息内容不同。Telethon 当前版本也会在必要初始化或缺少自身实体时调用 get_me/GetState 等方法。

官方依据：[Telegram Working with Updates](https://core.telegram.org/api/updates)。生产 SDK 依据：`source/telethon/client/telegrambaseclient.py:576`–`:619`、`source/telethon/client/updates.py:563`。

因此合理目标是“正常消息通过推送处理，主动读取限定在必要初始化、缺口恢复、首次采证和规定周期检查”，而不是承诺永久零 RPC。这个协议约束不能用来合理化本系统把回调接收停掉数小时。

## 7. 整改顺序与验收要求

1. **先修监听生命周期与本地消费。** 回调连接、必要初始化、批量补同步分开调度。在既定总预算内预留可验证的初始化/重连资源；本地队列消费者按有待办的账号运行，不以当前 socket 是否建立为前提。普通同步预算不足仅延期对应主动读取；真实平台冷却、鉴权失效等仍遵守限制。
2. **接通明确删除事件的直接处理。** 账号、群命名空间、消息、发送回执和频率周期全部匹配后，事务内记录删除、幂等降频/停投并持久化退出意图；外部退群另行受权限与结果核对约束。未知删除不能误判，也不能重发未知消息。修复 daily 状态回调与周期任务的衔接。
3. **拆开审核的本地部分和读取部分。** 已有事实归并、规则计算和有效证据的 AI 重判不申请 Telegram 读取额度。需读取时仅获取缺失部分。需要持续观察的群注册明确、限大小和期限的回调证据消费者，维护计数、采样及必要规则证据，不恢复无限保存群聊正文。
4. **完善预算账本与迁移过渡。** 展示新分项计数、未分类消耗和推定分摊；保留真实总量/窗口，不伪造容量。历史迁移不能耗光监听恢复资源；预留与调度应在旧窗口也能兑现。空闲存活额度借用只是辅助，不能代替上述解耦。
5. **按真实故障场景验收。** 同步额度为零但连接仍在、额度为零时重启、单频道/账号级缺口、明确删除与未知删除、daily 广告删除、重复回调、数据库暂不可用、已有本地待办的离线恢复、只有 AI 重判的审核任务，均需独立测试。正常网络和无平台冷却时的回调延迟应有实测目标，监控不能以 inbox=0 或进程 online 代替持续接收成功。

本地候选“直接处理删除 + 周期检查 + 存活额度借用”仅覆盖部分问题，需要补上监听恢复与离线消费后，再形成可部署的完整候选。当前任务为仔细分析，尚未实施上述修改。
