## 2. 三项新确认的问题

### 2.1 历史页缓存尚无生产生效证据，主执行归属已纠正

现网普通区 **0 页、0 记录**，`cache_writes=0`、`cache_hits=0`、`cache_misses=0`。这说明还没有进入普通区保存/读取，不能仅解释为缓存被淘汰。已有 snapshot 的初步聚合也未发现历史页引用；该辅助扫描不能代替完整事件轨迹，存储生命周期计数是主要证据。

严格生产源码确认 Celery 本地/无 owner 回退路径至少缺两道运行前置；这不等于账号 34 的实际 owner 执行路径也缺少它们：

1. `core/scheduler/tasks.py::_run_with_worker_cleanup` 为 Celery coroutine 初始化 Redis 与指标健康，但不启动 `start_ingest_worker`；生产中的启动调用位于 API lifespan 和 `telegram_worker`。这些组件属于其它进程，不能给 Celery 提供同进程 `_worker`。
2. `review_evidence_ingest.cache_safe()` 在 `_worker=None` 时返回 false，`review_history_progress.fingerprint()` 因而立即返回 None。即使补齐 ingest，当前短连接账号路径默认 `keep_connected=False`，而池只在长连接条件下包装/安装 ListenerSession checkpoint；不能假定短连接客户端已经有 `session.journal`。

因此，r2 已修正“普通历史页可以打开既有定长文件”，**仍不等于真实审核路径已经有效复用**。不能绕过安全门禁强行命中；需要定位 owner 实际拒绝原因、补齐必要的有界事实交接/连续性来源，并增加真实入口回归。

其它失配还包括 scope、待处理规则/成员/gap、SDK 水位或连接代次变化、五分钟过期，以及采集前后指纹变化。目前这些原因多为静默 None，缺少有界原因计数，尚不能分解每种拒绝占比。completion 中两项新复用也依赖相关前置，不应直接发布后假定收益会出现。

最近 9 个完整小时的 `resume.used=7`、`fallback=35` 可以来自游标提示和回退，不是历史正文缓存命中率；`same_work.used=36` 也不能直接换算成少 36 次 RPC。

### 2.2 SDK 进入计量存在取消过计边界

部署版 `rpc_governor.py` 在调用原 SDK 前，先 `await record_read_rpc(..., 'entered_sdk')`；计量先加工作片计数并持久化，之后才真正进入 SDK。

严格冻结生产 r2 的离线复现使用真实固定计量文件，在 entered 事务真实落盘后、SDK 调用前取消任务，得到：

| 证据 | 结果 |
| --- | ---: |
| 原 SDK coroutine 实际 await 次数 | 0 |
| work.entered_reads | 1 |
| 固定文件 entered/actual_reads | 1 |
| 固定文件 complete / gap | true / 空 |

探针没有访问生产或真实 Telegram；使用虚拟时间/心跳及测试专用事务返回阻塞来准确命中边界。它证明缺陷可发生，**不证明现网已经发生或发生了多少次**，也不能据此宣布全部读数错误。

正式收益验收前需要消除 SDK 前计量 await 的取消窗口，或将这种无法确定的边界明确标为不完整；同时补对应取消回归。文件覆盖完整不等于调用计数语义已经完全准确。

### 2.3 保护维护反复尝试未成熟 UNKNOWN 移交

当前生命周期记录：`rejected_early_handoffs=8123`、`illegal_early_releases=0`、`legal_early_releases=0`、`maturity_scheduled=0`，32 个保护槽全部仍在。

源码路径是：ingest 启动向旧槽记录 gap，维护看到 facts 后尝试 UNKNOWN 移交；未到 ready 被存储时间门禁拒绝，但拒绝计数仍持久化。维护节流/单飞只在进程内，多进程/入口可以重复执行。

**8123 是被拒绝的提前移交尝试，不是提前删除或 Telegram 读取次数。** 当前保护门禁起作用，但存在无效数据库锁、文件提交和维护开销。需要在到期前按状态跳过这类 UNKNOWN 移交，并协调维护所有者/幂等；同时保留编辑、删除及真实不再适用的控制语义。

这批槽因 gap 保守等待补证，尚不能作为正常“成熟定点核验成功”的生产样本。

## 4. 实际距离目标有多少

目前没有可信 baseline，也没有启用二期的可比数据，因此**不能给出实际已经降低 X% 或还差 Y 个百分点**。工程测试数、开关数量和文件数量同样不能折算为完成百分比。

最新固定聚合中，**北京时间 01:00–10:00 的 9 个完整小时**来源覆盖完整、无 gap：

| 口径 | 记录次数 |
| --- | ---: |
| 账号 34 全部已治理用途 SDK 进入 | 2419 |
| RPC purpose=review | 1257 |
| RPC purpose=renewal | 918 |
| 上述审核相关用途合计 | 2175 |
| 该窗口结算工作片中的 review＋renewal SDK 计数 | 1990 |

2175 与 1990 采用不同事件/结算与归类边界，**不能混用为同一分母**；185 的差额尚需归因核对，不能猜成同步流量。取消过计边界也意味着这些数值仍是待校准的测量记录。

若仅把当前 2175 作为同工作量的参考值，二期额外下降至少 30% 的数学要求为：`2175 × 70% = 1522.5`；整数计数需 **不高于 1522 次，至少净少 653 次**，并计入预热、失败、回填、失效补证和维护新增读取。这只是目标换算，不是正式一期稳定分母或已发现 653 次可删除重复。

正式目标仍为：一期成本降至同口径 baseline 的 **75%–80%**；二期降至一期的 **70%**；两期累计降至 baseline 的 **52.5%–56%**，即累计减少 **44%–47.5%**。目前三项均未证实。

24 小时窗口仍 `complete=false/window_before_source`，00:00–01:00 发布小时已有 gap。若后续无新增缺口，最早 11 月 5 日 01:00 才可能得到第一份完整 24 小时读数；它不会自动补出 baseline、修复计量或证明下降。
