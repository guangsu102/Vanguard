## 解决方式

### 1. 保障审核和加群各自能推进

在原 critical 读取池内，审核与加群各保留该池的四分之一，另一半共享；其他原有弹性额度和经过预测的安全池借用仍受原上限约束。加群份额覆盖候选预检查、实际加入、验证及入群结果核对。监听、广告、存活检查和历史同步原有保留量不变。

所有请求在同一个 Redis Lua 分配器内原子检查，业务子计数沿用原小时/日窗口到期时间。旧的未分类消耗按两类分摊，不能因为新增计数器而“恢复”已消费额度。保底表示有读取推进机会，不保证每小时一定有群符合入群条件；保留份额也可能降低单一业务独占时的峰值。

真实 Redis 并发实验：正常预算下，一类工作最多先获得 57 次，另一类仍有 15 次可用；反向相同。在一半预算下，对应为 29 次与 7 次。旧窗口耗尽仍阻塞、TTL 保留、父窗口重建时旧子计数清理均验证通过。

### 2. 用回调定位证据，减少重复历史扫描

只对需要审核的已加入群积累广告候选消息 ID 和日期，不归档聊天正文。入口每群最多保留 32 个待落盘槽位，数据库缓存最多 80 条线索并按 72 小时有效期筛选；成熟线索优先，账号、群和本次入群时间必须一致。

审核优先按这些 ID 批量定向读取，然后核实当前可见性、发送者身份、群规与警告回复。已有采集器在定向证据足够时可以停止宽范围历史扫描。线索本身不授予投放资格，不延长旧证据的有效期；缓存损坏时退回既有采集路径。实际节省多少 RPC，仍需生产采样验证。

陌生群尚无本账号回调，需要第一次有界预检查；权限变化和断线缺口仍需读取。监听收到回调、审核取得足够证据、Telegram 允许加入是不同状态。

### 3. 按实际产能安排广告节奏

账号发送前同时考虑原最小间隔、成熟群/试投的有效动作上限、实测读取成本、资源产能、日窗口剩余时间和已消费广告读取量。为失败读取及结果核对保留原规划中的 20% 余量，避免把全天额度集中用完后长时间停发。

既有 30 条试投配置不被误用为成熟群与试投合计上限。群每日上限、群间隔、账号风险和未知发送对账继续生效。每次计算使用最后成功广告时间和原预算 TTL，反复轮询不会把恢复时间不断往后推。

### 4. 让状态与执行使用同一套判断

修正加群容量读取 routine 池而实际操作使用 critical 池的差异。容量和实际预检使用同一个 purpose 到预算的映射，并分别显示广告、加群、候选预检查、审核、监听恢复额度及同步额度的状态。

当广告和加群都在等待预算时，不再汇总为无原因的“已调度”。账号隔离、平台冷却与分业务较长等待时间都被保留。展示的最早复核时间仍不是成功承诺。

## 生产成功的判断标准

真实新广告必须同时有消息 ID、成功 outbound 和对应投放记录；真实入群必须有执行结果及匹配成员状态。还需看到候选预检查和审核在各预算窗口持续推进、周期存活检查完成、同步补差有进展，且无未知发送、重复回执或持续业务事实积压。

当前 SDK 历史补差尚未完成完整周期验证。本轮不改变 SDK 游标或同步算法；窗口恢复后仍需验证追平能力。群规、审批等待、AI 冲突及证据不足也不会因为预算划分改变而自动通过。完整稳定性应以至少一个 24 小时业务周期的实际结果判断。
