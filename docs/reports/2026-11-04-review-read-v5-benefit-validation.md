## 1. 验收对象和固定口径

验收对象为同一健康账号、同一代码及计量版本、同一原业务准入与预算规则下的三个阶段：

| 阶段 | 生产功能开关 | 用途 |
| --- | --- | --- |
| baseline | 所有读取优化阶段关闭；保留本次修复镜像、计量、控制事件与既有保护维护 | 得到原取证路径的 SDK 同口径实测 |
| phase1 | REUSE、RESUME、MINIMAL_PLAN 开启；二期、FACT_HANDOFF、DEPENDENCY_RESUME 和新载荷接纳关闭 | 验证一期，不混入二期收益 |
| phase2 | 只开启本次待验收且已独立通过安全验证的二期开关，配置逐项记录 | 以同代码 phase1 稳定窗口为分母验证额外 30% |

实施后若增加开关，以最终 manifest 与阶段开关快照为准。`measurement_stage()` 的标签不能代替真实配置证明；若把二期功能标成 phase1，该窗口作废。

主成本口径使用固定计量文件中的 **entered_sdk**，即受治理读取进入 SDK 的次数；同一个多请求调用按实际进入的请求数计。它不是 Telethon 内部重试后的 wire RPC 总数。baseline、phase1、phase2 必须来自完全相同的计量入口、方法分类、用途分类和版本，不得把旧预算扣费样本与新 SDK 次数相除。

同时展示 attempted、success、error、budget_charged、reserve，彼此不能互换。reserve 不代表消费；缓存命中、预测读数和优化 used 次数不直接当作节省。6941、5402、3781、45.5% 均是旧样本/计划数，不参与新的实测比值。

## 2. 开始前的必过条件

在不发送 Telegram 测试请求的前提下，执行只读检查并保存有限的数字汇总：

1. 应用 manifest、镜像、阶段开关和计量版本匹配；原准入、广告频率、退避、180/分钟、360/小时、3600/日及调度份额一致。存在其它产品变化则重新冻结对照版本。
2. 账号真实 ONLINE，登录/session、代理和目标群工作范围稳定。账号 ERROR、离线、封禁或无法取得业务任务的时段不能作为节省。旧ONLINE快照不能代替当前健康证明，最新账号状态见文末17:33:28采样记录。其它账号恢复在线不自动构成34的可比基线，仍需完整健康窗口及同账号工作量核验。
3. 自然任务产生新 ledger settled 行、消费 journal 和带 SDK 字段的新 work samples；旧样本缺字段仍为 unknown。若尚无自然工作，继续等候，不能强造工作或称 0 次读取为收益。
4. backend/growth/celery 的实际执行进程均已验证接线，来源租约健康，角色不缺失、容量不溢出、计量无 gap/计数饱和。仅看到三个角色名字，不替代检查实际进程覆盖。
5. 受治理成本之外的潜在 Telegram 读取通道已清点。若有未计量通道，主结论限于已覆盖范围，不能宣称全系统净减少。
6. 32 个既有保护槽的生命周期维护继续工作；未成熟有效保护的提前释放为 0。没有未解决的新鲜度、未知转允许、错误退出、重复发送或预算绕过缺陷。

任意一项不满足，状态为“验收条件未满足”，不计算目标已达标。

## 3. 窗口选择和阶段切换

默认使用 **24 个完整 UTC 小时**组成一个预算窗口，排除当前小时。每次比较至少需要三对可比较的完整窗口：一期为 baseline 对 phase1；二期为稳定 phase1 对 phase2。不是连续运行三天就自动构成三对，也不能把同一个滚动窗口每小时截一次当作三个独立窗口。

窗口只有同时满足下列条件才接纳：

- 窗口开始早于计量源/角色 coverage 起点，或缺源、gap、持久化失败、overflow、saturation、来源未确认到窗口结束时，一律拒收，不补零。必须检查原始 completeness 字段，不能只取 `known_entered_sdk`。
- 全窗口内账号健康、阶段配置和代码版本固定；不含发布、阶段切换、重启预热或旧阶段在途工作。自然业务不中断，切换时的在途工作按其原阶段结算，并单独归入过渡段；等旧阶段工作自然结算和原重试期限过后，再从下一个完整 UTC 小时起选窗。
- 未通过清空缓存、删除保护、重置预算、清空任务、暂停广告/加群、改变调度份额或人为减少工作量来制造对照。
- 新消息量、目标群/账号范围、审核触发类别与复杂度、必要警告/身份缺口等分布可匹配。未知复杂度单独保留，不把它分配到简单组。

阶段切换由操作者使用已审查的规范 Compose 流程显式执行。本协议不自动改生产、不创建 automation。一次只改变声明的开关，保留镜像、计量、既有保护维护、消费 journal、原预算和其它配置。

缓存预热、初次回填、同步和切换开销独立计入过渡成本；稳定收益报告同时提供这些开销及回本条件，不把其从全通道净成本中隐藏。缓存访问/重试不续期，baseline 也不得破坏保护承诺。

固定聚合只留 7 天。验收可分段完成：先取得并冻结三对 baseline/phase1 的有限汇总，再验三对 phase1/phase2。超过保留期未取出的窗口不可从旧样本猜测；不扩大存储期限或新增无界明细库。最终报告只保存选中窗口的数字与版本证明，不保存正文、账号凭证或逐 RPC 无界标签。

## 4. 每个选中窗口必须采集的量

| 维度 | 必须保留的字段/检查 |
| --- | --- |
| 身份与配置 | account_id、UTC 起止、镜像/manifest/计量版本、阶段开关、角色覆盖、健康有效时长 |
| 审核相关成本 | review＋renewal entered_sdk，按方法、用途、阶段、复杂度分组；attempted/error/FloodWait 和额外补偿成本 |
| 全通道成本 | 该账号所有已计量用途总 entered_sdk；同时查看其它账号和 listener/sync/reconciliation，防止换账号/通道转移成本 |
| 工作到达量 | 首审、续片、成熟、事件、续授权等各类新工作量；候选/规则/警告范围与未知缺口 |
| 工作完成量 | 已提交的独立业务决定/续授权完成数，allowed/trial/observe/wait/reject/protected/technical_wait 分布；finished_slices 不当作独立完成数 |
| 质量和延迟 | 失败、预算等待、AI等待、重试、积压量与最老任务年龄、完成时长；未知/不可得字段明确标出 |
| 实际业务 | 广告尝试、成功回执、未知回执、重复发送、必要退出和加群完成量；不通过少投广告或少完成审核达标 |
| 存储与安全 | 普通/保护占用、接纳拒绝、回填、gap、降级、保护提前释放、成熟/截止移交；组件实际物理占用仍小于 1 GiB |

现有固定聚合能够提供部分成本、work slice 和 scheduler commit 字段，但不能单凭它证明全部业务到达量、完成延迟、广告回执和积压。缺项使用既有业务表作有界聚合查询补齐，不调用 Telegram；若不能可靠补齐，窗口结论为“不完整”。只读脚本不得打印 SQL 参数、消息正文、用户名、代理认证或连接字符串。

`production_followup.py` 可检查自然接线和错误类别，但它不是最终收益计算器。保持原 `runtime-before.json`、`runtime-after.json` 不变，跟进汇总另存有限文件名。

## 5. 比较方法与通过条件

先比较每对窗口的同账号、同触发阶段和复杂度分层工作量。可比窗口的到达量或复杂度分布不能明显偏离；有偏离时先匹配分层，用预先冻结的 baseline 工作量权重计算，不事后挑最有利分组。某组任一阶段无足够有效工作时，该组不能宣称有收益。

对可匹配的工作层 `s`，记录该层全部审核＋续授权读取 `R[s]` 及独立完成数 `C[s]`。参考量可使用 `sum(weight[s] * R[s]/C[s])`，权重在查看优化结果前按 baseline 冻结。零完成、失败堆积或在途增长时不计算有利比值；全部 failed/inflight 读取仍留在成本分子。原始总读数与原始工作量必须同时展示，标准化数不能遮盖积压或完成量下降。

- 一期降幅读作 `1 - phase1_cost / baseline_cost`，20%–25%是规划范围，不是默认通过；报告实际值和三对窗口差异。
- 二期额外降幅读作 `1 - phase2_cost / stable_phase1_cost`，目标至少 30%；phase1 分母必须是同代码、同计量、未混入二期的新稳定实测。
- 累计降幅直接用 `1 - phase2_cost / baseline_cost`，不得把两个百分比相加，也不得继续引用 45.5% 作为实测。
- 正式“通过”要求至少三对完整可比窗口均满足目标方向，合并标准化二期成本不大于 phase1 的 70%，且各对差异有解释。若样本不足或波动使结论不稳定，继续记录为“尚未证明”，不下调门槛。
- 同时要求全通道净读取下降，成本未转移；必要完成量、事实新鲜度和完成延迟不恶化，失败、积压、限流、未知回执没有由优化导致的恶化，广告成功回执不存在工作量下降造成的假改善。
- 任意业务等价性或存储保护缺陷均直接不通过，读取下降不能抵消安全失败。

因自然群活跃度变化无法获得同量输入时，如实报告观察性关联及范围，不伪称严格因果。只有已捕获材料可用于离线等价轨迹核验；不能额外向 Telegram 发一套 shadow 请求来补对照。
