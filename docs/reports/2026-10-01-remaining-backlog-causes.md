# 2026-10-01 剩余积压与广告反复等待的原因

13:10—13:16（北京时间）只读核查后确认：上一轮优化没有覆盖全部阻塞路径。剩余等待不能仅归因于已用日额度；额度保护、加群准入和规则续期之间还有机制冲突。12:52 的单次广告成功只能证明当时链路可用，不能证明后续持续可用。

## 1. 已暂停的加群仍锁住复核需要的额度

13:10 快照的日预算为 3,240，已使用 2,259，尚余 **981**。其中：

| 预算类别 | 基础份额 | 已用 |
| --- | ---: | ---: |
| 广告 | 1,134 | 491 |
| 存活检查 | 486 | 261 |
| 加群与普通复核 | 810 | 842 |
| 同步 | 648 | 631 |
| 公共余量 | 162 | 34 |

广告、存活与同步的未用额度继续受保护。计入已证明空闲的 43 次存活检查额度后，加群/复核日通道还可使用 **139** 次。公平分配函数又固定为加群保留 `floor(810 / 4) - 81 = 121` 次，最终普通复核只有 **139 - 121 = 18** 次，低于每轮最低预约的 **24** 次。

同时，加群调度返回 `join_review_backlog`；当前复核压力 19，已触发暂停新增。另有 7 条已加入、未完成初审的 `join-attempt` 记录，也会触发新增前的初审阻塞检查。因此出现：复核需要额度 → 为加群保留的额度不可用 → 加群又要等复核完成。

这是跨规则的等待环。它没有占住数据库锁或执行线程，但会让业务工作停滞到窗口或需求发生变化。当前不存在未释放的工作预约。20 条已加入群的最新审核记录都是 `technical_wait / telegram_read_budget`，其中 7 条是加入后的初审，另 13 条是其他复核；它们不是 20 个新加群。另有 2 条证据观察和 4 条入群审批等待，应分别计数。

相关实现：`critical_fairness.other_hold()` 固定计算最低保护份额；`read_work.initial_pending()`、`JoinBudget.status()` 和 `capacity` 的水位控制暂停新增；`run_reviews()` 的最低 24 次检查拒绝启动。新加入群的额度交接只覆盖发布后的新操作，旧初审没有此前预约可以继承。

## 2. 规则续期没有接入初审的分轮控制

`RpcGovernor` 只对 `critical` 通道执行 `ReadWork.ensure()` 及单轮额度限制。`ad_qualification_refresh` 使用广告通道，`try_light_renewal()` 仍直接调用完整的 `refresh_live_authorization()`。因此上一轮新增的 24 次初审上限不约束该路径。

群 10 的实际续期：读取 **36** 次，其中 **29** 次是 `channels.GetParticipantRequest`。保存的数据中 `reserved_reads=0`、`collection_progress={}`、无 `pending_collection`；续期函数在预算异常时只推迟时间，没有保存这轮规则核验完成到哪个消息或作者。

该小时三次成功续期分别花费 13、9、10 次，共 32 次；群 10 随后花费 36 次而未完成。合计 **68** 次，已达到广告基础小时额度 114 的 60% 续期上限。之后还有 4 次广告发送读取，总广告用量 72。发送仍有可用读取 58，但续期余量为 0，下一小时窗口约 **13:51:23** 才刷新。

初审进度保存不能解决这条续期路径；下一次续期仍可能重复获取群信息、置顶和消息，并重新查询作者身份。`EvidenceCollector` 的角色缓存只在当前调用内复用，不能把失败续期变成下次可接续的工作。

## 3. 规则事件范围过宽，持续产生新的待核验工作

初审的 `possible_rule()` 已区分普通促销和规则指令，但监听的 `listener_interest.project()`、续期的 `refresh_live_authorization()` 仍直接使用宽泛的 `RULE / WARNING` 正则。`RULE` 含“广告、推广”等词，因此普通促销也可能产生规则变化待核验事件，触发群信息、置顶和作者身份检查。

在最终生产镜像中用合成消息纯函数复现，未调用 Telegram：

| 合成消息 | 初审 possible_rule | 监听产生规则事件 |
| --- | --- | --- |
| 广告推广服务，低价套餐，联系 @example | 否 | 是 |
| 低价套餐服务，联系 @example | 否 | 否 |
| 本群禁止发送广告 | 是 | 是 |

这是可复现的筛选不一致，不代表现场每一条规则事件都是误报。已完成的消息事件会清空正文和 payload，不能据此还原历史误报比例。

监听还将 `UpdateChannel`、`UpdateChannelTooLong` 等情况标为 `gap`。当前 25 个已获资格群全部有待核验事件，21 个含 `gap + rules`、4 个仅含 `gap`。三个在 12:51—12:52 完成续期的群随后又出现待核验事件；到 13:10，广告可用群已经由 2 回到 **0**。

发送端要求先核清事件，续期通道又已耗尽，因此仅保留广告发送额度无法维持广告输出。新增事件还会使普通复核保存的历史游标失效，进一步放大重采成本。

同步此时仍在等待，空闲同步份额借用没有启用。同步等待也可能包含本地请求间隔：现行同步基础日份额 648 对应约 133 秒的平滑间隔，代码同样将这种等待标为 `telegram_read_budget`，不能看到该原因就认定总额度耗尽。

## 修复顺序与验收条件

1. **先打破等待环。** 加群与其初审按一条工作链分配额度；旧初审也能使用该链路的额度。暂停新增时按可执行的验证、退群等需求保留必要份额，让空闲加群份额支持复核。快照、预检和 Redis 原子分配必须使用同一规则，继续保护广告与监听。
2. **统一事件筛选。** 监听、初审、续期共享规则候选判定；保留真实群规、警告、置顶、已跟踪证据变化和权限变化的检查。对合并事件按语义去重，并区分同步缺口与已证实的规则变化。
3. **给续期也加工作上限和断点。** 保存事件版本、未完成消息及核验进度，优先检查实际变化的证据；中断后接续，事件版本改变时只丢弃失效部分。结束时对同一事件版本确认，避免覆盖后来到达的变化。
4. **增加跨路径验收。** 用“加群暂停 + 初审待办 + 另一通道有闲置份额”检验持续推进；用连续普通广告、真实规则变化、同步缺口和低余量续期检验不会重复消耗。30 账号测试要覆盖这些业务事件与额度组合，不能仅验证调度公平。
