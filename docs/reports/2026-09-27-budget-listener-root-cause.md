复核时间约 15:45—15:49。仅检查代码、现有生产状态及官方说明，没有更改限制。

## 1. 本地预算和 Telegram 限流必须区分

`backend/app/core/account/rpc_governor.py` 明确将 120/min、240/hour、2400/day 定义为本地保守预算，不是 Telegram 公布的固定阈值。`RpcDeferred('telegram_read_budget', ...)` 在原始 RPC 调用之前抛出。真正的 Telegram 限流由服务器返回 `FLOOD_WAIT_X` 等错误，再进入冷却与降额处理。

Telegram 官方说明：https://core.telegram.org/api/errors#420-flood 。Telethon 对具体限额受多因素影响的说明：https://docs.telethon.dev/en/stable/concepts/errors.html#avoiding-limits 。当前采样的 emergency_cooldown_seconds 为 0，先前一小时日志无新 FloodWait；当前等待来自本地预算。

#2 保留历史 FloodWait/冷却恢复记录，read_factor=0.5，所以其本地总额为 60/min、120/hour、1200/day。旧冷却已结束，但本地减额与日计数窗口仍在作用。历史方法记为 unknown_legacy_read_rpc，不能据此断言过去是哪条具体 Telegram 方法触发。

各通道共享同一组分钟/小时/日计数。#3 当前策略：

| 通道 | 共享小时计数达到多少就停止该通道 | 额外通道自身上限 |
| --- | ---: | --- |
| 背景预览 | 120 | 背景 60/hour |
| 监听同步 | 120 | 同步 60/hour |
| 普通资格审核/加群读取 | 180 | 无额外小时独立上限 |
| 广告、存活、对账等关键读取 | 240 | 仍遵守全局限额与真实 FloodWait |

这些不是互相独立的分配额度。其他任务也增加共享小时计数，因此即使同步自身只用了 55/60，总计数达到 198 后仍会阻断同步。这是本地调度耦合，不能解释成 Telegram 告知“监听限额耗尽”。

窗口从第一次计数起按 Redis TTL 到期，达到限制后等待窗口结束，不会按每分钟均匀补充。因此会出现窗口前几分钟集中使用、之后等待很久的情况。每次群审核需要多种读取，且读取请求尝试即计数，包含失败尝试；384 次读取并非384次发消息。

## 3. 监听是否为 bug

证实的机制：本地共享计数到达同步阈值后，SDK更新读取抛出 RpcDeferred，系统取消更新消费循环、等待正在执行的业务处理结束，再断开连接；队列/游标保存在当前进程会话，预算到期后复用连接对象恢复。

15:45 最新快照：#3 队列仍为89，队列连续非空约45分钟、读预算等待约44分钟、处理任务0、pause_error为空；RSS约194.8 MiB。14:00和15:00已有自动恢复业务的证据，因此当前没有证据证明永久死锁；同样没有证明消息已丢失或具有持久化恢复保证。

判断：暂停动作本身符合代码，但将持续监听与扫描竞争同一预算、并在同步受限时连已接收更新的处理也整体暂停，与持续处理事件的需求不匹配，应作为调度设计缺陷处理。前次暂停修复控制了继续积压和内存增长风险，没有解决持续吞吐问题。

修复方向应是保留硬预算及真实 FloodWait 保护，为监听保留最低服务能力，平滑安排资格/预览读取，并设计事件持久化与顺序处理，使需要新增RPC的补齐任务能延期，而已有可安全处理的事件不会全部停止。不能通过简单清空计数、跳过补齐顺序或清空队列来声称恢复。

另有已证实的观测问题：预算拦截被记为 join_failed；总状态 ready/scheduled 与通道可用量0并存。这些应在调度和展示中明确区分。
