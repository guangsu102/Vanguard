# v3 广告资格门禁加固（本地未发布）

本次只改本地工作区，未调用 Telegram、未改生产设置或数据库、未重启服务。既有自动加群和广告执行关闭状态未触碰。以下是新代码预期，不能描述为线上已生效。

## 广告先例

试投和当前明确允许的放行路径都要求两条不同普通成员、不同推广关联的广告。两条当前内容各需存留至少 24 小时；72 小时历史及警告搜索必须完整，不能将抽样未发现处罚解释为未处罚。发送前通过原消息 ID 重新读取，比较作者、文字、发帖与编辑时间、当前普通成员身份。删除、修改、身份变化或读取不确定均使审核失效并暂停发送。权威群规中的明确禁令、付费/白名单/管理员批准条件仍优先，两个广告样本不能替代许可。

完整历史要求使繁忙或隐藏历史群更容易停留在观察/人工状态，这是有意的失效关闭。两名发送者加不同推广目标仍不能证明两者经济上独立，也不能保证 Telegram 管理员之后不会删除；需要真实小范围投放与 24 小时留存数据才能校准阈值。

## 自家账号身份覆盖

新设置 automation.group_qualification.system_account_user_ids 是本地账号 ID 到 Telegram 数字用户 ID 的映射，例如 {"2": 200, "3": 300}。审核必须覆盖数据库中全部 PROMOTER 行，包括停用/受限账号；当前审核账号还必须与 Telegram get_me() 返回值相符。映射 ID 不能重复，system_user_ids 旧列表仅用于补充排除历史账号，不能单独证明完整。审核快照记录覆盖指纹和实际排除 ID，发送门禁重新核对数据库账号全集、配置和快照；新增账号或配置变化会使旧放行失效。

这是相对于 Vanguard 数据库现存账号的完整性证明，尚不能证明数据库之外或已删除账号从未参与推广。需要把此类历史身份列入额外排除清单，并在管理流程中保存来源和定期对账。未完成映射前资格停留在观察，旧批准也不能发送。生产现有 system_user_ids 仅 3 个、PROMOTER 账号 29 个；上线前需在只读盘点后逐个核实并录入映射，不应猜测数字 ID。

## 入群候选与 v3 的脱节

当前 _next_pending_join_group 从 pending_join / join_failed / cooling_down 且有公开 username 的候选中，按等级分、转化分、活跃分、人数降序，创建时间和 ID 升序取前 50，再跳过已占用或已预留群。入群前的旧封禁/重加核对不等于 v3 投放许可。排序没有纳入普通成员广告先例、群规可读性、置顶/管理员规则冲突、指定话题和收费发言迹象。因此高活跃但禁广告的群可以先花掉 Join 额度，入群后才被 observe；较小但公开规则清楚的群可能被排在后面。

建议后续单独改成两层候选队列：先对前 N 个公开候选做有上限的只读预览，记录采样时间、可见性、普通成员广告的候选线索、规则可读性和明显禁令；仅把这些当作优先级，不可作为发送许可。未知或不可见应标记为不确定而非“无广告”。结合历史转化与资源成本排序后再占 Join 额度；入群后仍用完整 v3 审核作唯一放行依据。需限制预览请求、处理 FloodWait，并跟踪 入群数 → 可完成审核数 → allowed/trial 数 → 实际发送数 → 24h 留存/账号限制。没有这些真实漏斗数据，30 次/日与 48 分钟只能视为风控上限，不能证明业务上合适。

## 验证边界

本地资格审核相关 510 个单元测试通过；最后身份提示顺序调整后的相关 94 个测试通过。修改模块及测试的 Ruff 检查通过；automation.py 原本有大量全文件 Ruff 存量问题，本次只改了 AI 提示词并通过编译及相关回归。未做生产灰度、真实首投或 24 小时效果验证。
