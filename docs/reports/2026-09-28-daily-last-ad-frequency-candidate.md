# 单群日核验频率候选验证

本轮按用户确认，把单群升级改为每 24 小时核验上一周期最后一条真实广告：存活则翻倍至最多 30，确认不存在则减半至最低 1，已是 1 条仍不存在则进入原有可靠退群通道。连续正常情况下，第六周期允许 30 条。

规则详情：`docs/plans/2026-09-28-daily-last-ad-frequency.md`。本轮基线与前端构建日志：`deploy-artifacts/daily-last-ad-frequency-20260928/`。

## 验证证据

- 相关后端回归 210 项通过，使用 SQLite 与模拟 Telegram；涵盖日核验、跨账号群额度、并发认领及旧回调、减额、最低频率退出、退出未知结果对账、账号额度、资格复核、存活读取预算和连接复用。
- 新日核验用例验证 1 → 2 → 4 → 8 → 16 → 30 的完整五次反馈；第三周期只核验第二周期最后一条，不把它伪记为完整 24 小时存活。
- 新用例验证账号在核验期间停用、消息发送者或时间不匹配、原发送结果未决、读取预算延期、确认自动过期、旧机制多日证据承接，以及广告日志先于群频率的 PostgreSQL 锁顺序。
- 新模块、频率模块、迁移和新测试 Ruff 检查通过；改动的集成文件 Python 语法解析通过。
- 前端 `npm run type-check`、`npm run build` 通过。构建存在已有 Sass 弃用和大包提示，不影响构建成功。
- `alembic upgrade 048_listener_continuity:049_daily_group_frequency --sql` 离线生成成功；只生成迁移语句，没有连接或修改生产数据库。
- 与本轮保存的基线比较，旧工作区修改均保留；发送落盘和存活任务只加入日核验调用点，界面只新增日核验字段、状态和说明。

## 发布边界

本轮未对生产执行迁移、部署或任何手动 Telegram 发送、加群、退群操作，未提交或推送。生产仍执行原机制，新规则尚未生效。

后续上线必须先验证独立 PostgreSQL 候选及迁移，再切换同版本应用和工作进程。目标只能为 `oracle4c24g:/opt/vanguard`，服务端口 `18080/13000`；保留完整数据库、消息账本、群频率事件及回滚镜像，避免操作同机其他服务。候选验证不能代替真实线上周期和退群回执验收。
