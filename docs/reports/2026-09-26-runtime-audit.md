### P1-A：统一所有读取任务的限流与冷却

生产源码证据：

- `backend/app/modules/acquisition/automation.py:3748` 的 `_apply_account_flood_wait` 更新 `next_join_after`，没有同时写账号级 `risk_pause_until`。
- `backend/app/core/group/collection.py:276` 的群资料同步收到 FloodWait 后才写账号级暂停，但未同步风险原因、事件时间与事件记录。
- 同一窗口可见先预览限流、约 9 分钟后同步任务再次限流，与上述不同处理路径相符。原始具体 Telegram RPC 名未在本次脱敏证据中确认，不能断言是哪一 API 的独立配额耗尽。

建议将预览、搜群、资格采集、群资料同步、入群核对的限流处理统一到账号共享的暂停入口。收到 FloodWait 后立即保存最晚冷却截止时间；其他任务获取租约前和发请求前都读取该截止时间。为正常读取增加账号级速率与并发预算，按任务优先级执行，减少无收益重查。保持 Telegram 要求的等待时间，不能通过清空暂停或换账号强行恢复。

验收：构造任一读取路径 FloodWait 后，其他路径均不再请求该账号；原因、截止时间及审计事件一致；原有未知发送状态不能被重复提交。

## 4. 其他优化项

### P1-C：补齐业务就绪检查及可工作的告警

当前 `/health` 仅固定返回 `healthy/version=1.0.0`（`backend/app/main.py:138`），不检查数据库、Redis、心跳或业务暂停。原点 `/ready`、`/metrics` 均为 404。

运行容器列表未发现 Prometheus、Alertmanager、exporter、Grafana 或 cAdvisor。服务器现有 `monitoring/prometheus.yml` 的 Alertmanager targets 为空，规则指向 `alerts/*.yml`；仓库提供的是同层 `alerts.yml`。因此这些文件不能证明已有可工作的告警链路。未核查主机之外的第三方监控。

建议保留轻量存活检查，增加依赖就绪检查；为 worker 心跳、调度延迟、账号冷却、暂停挂起复审、未决外发、存活检查超期、磁盘和备份新鲜度建立监控。验证告警实际路由，而非只放配置文件。

### P2-A：治理磁盘及发布制品

全主机 Docker 统计：561 个镜像，总计 43.8GB，标记可回收约 36.16GB；构建缓存约 22.44GB。两者可能共享数据，不能直接相加为可释放量。Vanguard 自身 `/opt/vanguard` 约 726MB，其中发布备份约 377MB，不是整个磁盘占用的主要来源。

建议先列出各服务镜像归属，保留当前版本、明确回滚版本及需要的候选，然后按保留策略处理旧镜像和构建缓存。共用主机含其他业务，不能全局 `prune -a`。当前 Vanguard 容器 `json-file` 日志配置没有 `max-size/max-file`，应补日志轮转。本次未删除任何制品。

### P2-B：减少无收益的模型复审及账号租约竞争

最新版本运行约 16.6 小时：日志记录 `glm-5.3-flash` 成功响应 223 次，响应记录里的 tokens 合计 557,656；这不是供应商计费结算。存在 22 次内容拒绝事件、5 条非 JSON 诊断及超时事件；这些来自不同层日志，不能直接相加为独立失败请求数。

审核热点累计尝试最多 27 次。#3/#4 推广暂停但仍在资格审核范围，是当前配置行为。投放日志另有 28 条租约忙、30 条群身份未知和 2 条群规则变化的安全跳过。

建议对无新证据的相同拒绝/冲突增加有界退避；按证据版本去重，优先处理接近成熟、有投放价值的复审。暂停推广账号按保留需求降低审核频率。任务队列继续隔离，但同账号任务按租约优先级协调。不得为了提高通过率放宽证据门槛或绕过模型拒绝。

### P2-C：控制常驻进程成本

Celery 主容器内存约 4.56GiB，进程 PSS 合计约 4.25GiB。11 个 worker 合计 24 个执行子进程，其中主容器 23 个，独立资源搜索 1 个。`multi` 模式按各队列配置取并发，不等同于 Compose 的 `CELERY_WORKER_CONCURRENCY=2`。

当前队列没有积压，说明可评估低频消息、QQ、批量等队列的常驻并发，但不能凭本次快照断定内存泄漏。应按高峰任务延迟和吞吐选择并发，并补内存上限/告警，保留审核、维护和安全控制任务的必要隔离。

### P2-D：队列持久性与备份验证

缓存、Celery broker 和 result backend 分别使用同一 Redis 实例 DB 0/1/2，实例策略是 `allkeys-lru`。当前驱逐数为 0，距 512MB 上限很远；这是未来容量风险，不是当前数据丢失。`allkeys-lru` 会在内存压力下驱逐键，逻辑 DB 分号不能提供内存隔离。[Redis 官方说明](https://redis.io/docs/latest/develop/reference/eviction/)

建议评估队列独立实例及 `noeviction` 配合容量告警，缓存单独使用淘汰策略；同时控制任务结果保留时间。此调整应通过候选和回滚验证，不能直接热改全部服务。

已核实最新发布备份 `database.dump` 为 18,697,075 字节、时间 9 月 25 日 19:48；`pg_restore --list` 成功；备份和环境文件权限均 600。回滚脚本存在。所检 cron、systemd 路径未发现 Vanguard 自动备份计划；异地备份和实际恢复演练未验证。建议把每日备份、异地副本和定期恢复演练纳入正式运维。

### P2-E：转化效果尚不可衡量

`acquisition_tracking` 全表 0 条；当前投放素材未配置 `link_url`。现有证据证明发送与存活，不能证明点击、注册或付费转化。若继续评估营销效果，需要为现有引流方式补可归因入口/事件，而不是单纯增加日投放上限。
