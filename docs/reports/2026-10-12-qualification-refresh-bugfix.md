# 有效广告授权被反复复核及 ad_refresh 预算不足

本报告记录修复及发布前验证。用户随后要求立即部署，已于北京时间 **2026-10-12 06:34:02** 完成生产发布，当前结果见 [线上发布与验收](2026-10-12-qualification-refresh-release.md)。下文“尚未发布”描述的是当时的验证边界。0 天广告暖机已在此前于北京时间 2026-10-11 19:27:31 发布；它不等于所有关系均已取得广告许可。

## 1. 原授权有效，为什么仍被审核阻挡

此前将 `qualified=0 / usable=0` 简称为“没有资格”不够准确。需要区分原授权、待处理变化和当前执行状态。

在 2026-10-11 的生产采样中，704、794、738、586 对应的原审核仍为 `trial`，`authorization_current=true`，但审核行已变成 `queued`。投放入口先被状态条件阻挡，因而统计为不可投放；这不代表原材料全部未通过。

代码中确认的缺陷是：`telegram_worker.py` 在替换监听客户端时无条件调用 `account_gap()`，把普通重连也视为账号全群连续性缺口。`pending_value()` 又把账号旧 UUID 的变化视作新事件，进而触发复核排队。普通重连本身无法证明群规、成员权限或广告证据发生变化。

本地修复：

- 普通重连不再生成账号全群资格缺口。真实 Telegram 更新仍经监听事实队列进入复核。
- 显式账号缺口改用 `gap:` 代次，旧重连 UUID 不再制造新工作。
- 仅修复能够严格识别的旧合成记录：仅含 gap、已排队、没有来源和消息 ID、32 位旧 UUID、同一次入群、原授权仍有效且关系仍 approved/active。修复后恢复 completed，清除这次误排队留下的期限。
- 清理时按审核行、会员关系顺序加锁，并重新检查事件和授权。真实事件、失效授权、重新入群和人工暂停均保留。

**不能将上述四个群直接全部放行。** 较晚的北京时间 2026-10-11 21:09:47 采样显示：704、794 有带来源的 gap/rules；738、586 的 gap 也带有来源。因此它们不符合旧合成记录清理条件，仍应完成对应事件核验。794 当时还处于 initial_pending/warming。该采样不是 2026-10-12 的实时投放确认。

现有 `authorization_mode=events` 授权不会仅因时间经过而到期；旧非事件授权仍检查证据有效期。真实规则、权限或证据变化需要复核，连接实例变化不应单独触发。

## 2. 为什么反复复核

多个机制叠加：重连生成新代次，代次差异把已排队事件再次视作未排队；周期维护和执行退避共用期限；有真实事件时，旧试投“毕业”快捷路径仍可能将它推迟到 14 天后。预算等待又使排队迟迟无法结束。界面的尝试次数不能直接解释为多次资格否决。

本地修复：

- 已排队且没有新证据的事件不重复排队；旧重连代次变化不再重置真实事件。
- 明确标记周期维护期限，真实事件可唤醒周期维护；预算、FloodWait、租约争用等实际退避仍按原期限等待。
- 有待处理真实事件时必须进入对应核验，不再走周期毕业快捷路径。
- 完成核验时只确认自己读取的事件版本，后来到达的新事件不会被旧任务清除。
- 任务取消后释放审核执行状态，保留未完成事件并记录重试期限。

还发现了无效读取：成员身份权限查询第一次被拒绝后就进入能力退避，但停止翻页仍等待累计拒绝达到三次，导致阈值永远达不到。现已在身份缺证且查询能力不可用时停止继续翻页；可用的新鲜成员名单仍可提供身份依据，名单缺失不被当作“普通成员”证明。

## 3. ad_refresh 为什么不足

北京时间 2026-10-11 20:03:38 的预算采样：

| 指标 | 账号 33 | 账号 34 |
| --- | ---: | ---: |
| 全局日读取剩余 | 182 | 128 |
| 广告日份额已借给其他工作 | 2043 | 1412 |
| 广告用途日读取已用 | 34 | 665 |
| 广告读取可用 | 23 | 23 |
| 为发送预留 | 12 | 12 |
| ad_refresh 可用 | 11 | 11 |
| 一次轻量复核最低预留 | 16 | 16 |

这里的额度是项目内部 Telegram 读取预算。全局、用途份额和发送预留同时约束准入；已借出的份额不会因为广告需要而取消记账。这次实际只读准入命中 `telegram_read_budget`。

直接卡点是 **23 − 12 = 11 < 16**：目标全部因事件等待而不能发送，预测却仍把它们计作发送需求，并至少保留两次发送的读取量。于是有余量却无法完成使目标恢复可发送的复核。

本地修复将受事件阻挡的目标计入复核需求，不计入可发送库存。没有可发送目标时，在真实广告余量内给一次完整复核让出空间：上述场景变成 **23 − 7 = 16**。若真实余量只有 15，则最多仍为 15，继续等待。总预算、已用计数和已借出额度均不增加、不清零；有可发送目标时仍保留发送缓冲。

## 额外修正：0 天暖机的一致性

若政策已经是 0 天，关系中缓存的旧 `first_ad_allowed_at` 不能继续将它挡到未来。只读暖机判断现在使用当前 0 天政策；非零政策仍尊重已有明确期限。此判断不写数据库字段。
