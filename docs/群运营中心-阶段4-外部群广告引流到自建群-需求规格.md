## 0. 废弃决定

- **业务结论**：外部群软广引流到自建群已经由现有广告素材 `link_url` 能力满足。
- **开发结论**：本规格 P0、P1 全部取消，工作量估算作废，不进入开发队列。
- **现有使用方式**：在增长中心广告素材中，把“跳转链接”配置为自建群公开链接或当前邀请链接；系统发送前会替换 `{{link_url}}`，未使用占位符时会把链接追加到正文。
- **仍然有效的边界**：Growth 账号在自建群内部发送 community、promotion、AI 或模板消息，不受增长中心广告配置影响。
- **可选后续**：自建群目标下拉选择、链接自动同步、目标失效阻断和转化归因只能另行立项，不能恢复本文直接开发。
- **正文用途**：以下内容仅保留为历史方案记录；与本节冲突时，以本节废弃决定为唯一有效结论。

## 1. 历史方案结论（已作废）

阶段 4 复用增长中心现有广告投放链，让广告计划选择一个已纳管的自建群作为 CTA 承接目标：

~~~text
增长中心广告计划
  → 选定推广账号、广告素材和外部投放群
  → 继续执行原广告许可、账号模式、额度、冷却、风险和存活检查
  → 解析本计划绑定的自建群承接目标
  → 公开用户名优先；当前有效私有邀请链接兜底
  → 确定性渲染 CTA，不让 AI 生成或改写链接
  → 向外部群发送广告
  → 冻结计划、账号、外部来源群、素材、承接群和链接版本快照
~~~

本阶段固定两条相互独立的业务链：

| 链路 | 消息发送到哪里 | 读取增长中心广告配置 | 读取阶段 2/3 群内消息配置 |
| --- | --- | --- | --- |
| 阶段 4 外部广告 | 外部群 | 是，全部沿用 | 否 |
| 阶段 2/3 自建群内部消息 | 自建群 | 否，完全不受影响 | 是 |

因此，Growth 账号在自建群内发送 community、promotion、AI 或模板消息时，仍不得读取或受以下设置影响：

- `AdCampaign`、`AccountAdBinding`、`AdCreative`、`AdDeliveryScheduleState`、`AdDeliveryLog`。
- `auto_ads_enabled`、广告许可、广告额度、广告冷却、广告时段和广告存活配置。
- `automation.ad_delivery_execution`、阶段 4 目标开关和 `acquisition_stop`。

反过来，阶段 4 的外部广告必须继续受增长中心全部既有广告配置约束；给计划绑定自建群只决定 CTA 去向，不产生任何额外投放权限。

阶段 4 P0 的“精确归因”固定为投放行为归因：可以准确记录哪个计划、账号、素材从哪个外部群引流到哪个自建群，以及 Telegram 返回的外部广告消息 ID。P0 不宣称可以准确统计直接 `t.me` 链接点击，亦不把公开用户名或共享邀请链接的入群用户包装成某次投放的精确转化。

## 2. 【历史作废】当前代码基线与原开发前置

### 2.1 可直接复用的现有能力

| 能力 | 当前实现 | 阶段 4 用法 |
| --- | --- | --- |
| 广告计划 | `AdCampaign` | 增加一个可空的承接自建群及 CTA 配置 |
| 素材与账号绑定 | `AdCreative`、`AccountAdBinding` | 保留多素材加权和账号绑定，不复制承接链接到素材 |
| 广告调度 | `AcquisitionAutomationService.run_ad_delivery()` | 在原链路中插入目标解析、CTA 渲染和发送快照 |
| 外部群排除 | `_list_joined_groups_for_account()`、`_is_owned_group_ad_domain_excluded()` | 继续保证自建群永远不是广告实际接收群 |
| 广告准入 | `_ad_skip_reason()` 等 | 拆出纯读 evaluator，继续执行 Growth/AD_ONLY、许可、风险、额度、冷却和时段；既有warmup副作用单独运行 |
| 调度租约 | `AdDeliveryScheduleState` | 复用现有状态机，增加 destination 原因码映射 |
| 投放日志 | `AdDeliveryLog` | 增加不可变的承接目标和 CTA 安全快照 |
| 自建群资产 | `OwnedGroupAsset` | 作为唯一承接目标主实体 |
| 纳管状态 | `get_governance_status()`、`ManagedGroupBinding` | 使用“有效治理状态”，禁止只看数据库表面字段 |
| 邀请链接 | `OwnedGroupInviteLink`、`owned_group_invites.py` | 投放链只在服务端内存解密、验证；阶段 4 页面不取得明文，既有 OwnedGroups 管理页仅保留 §14.10 的显式 admin 单次 reveal |
| Telegram 锁 | `telegram_chat_advisory_lock` | 保留外部来源群锁；新增独立承接链接锁 |
| 手动预演 | 现有异步 `POST /api/automation/ads/run` | 保持 202；新增同步 `POST /api/automation/ads/dry-run` 返回安全决策 |

### 2.2 必须补齐的缺口

1. `AdCampaign` 当前没有 `destination_owned_group_asset_id` 和目标配置版本。
2. `AdDeliveryLog` 当前只记录外部来源群，没有承接群、链接类型、链接版本和最终渲染哈希。
3. `_render_ad_content()` 只读取 `AdCreative.link_url`，不支持按计划在发送时动态解析 CTA。
4. AI 素材生成会复制 seed 的 `link_url`，可能让多个计划共用素材时串链。
5. `AdCampaign.status` 是自由字符串，调度当前未要求 `status=active`。
6. `AdDeliveryLog.ad_campaign_id` 当前 `ON DELETE CASCADE`，删除计划会删除投放历史。
7. 邀请链接轮换锁与外部广告发送锁没有共同的线性化边界。
8. 风险相似度 Redis 缓存可能保存包含私有邀请链接的标准化正文。
9. 当前只有较窄的 `automation.ad_delivery_execution.enabled`，没有覆盖搜群、加群、许可探测和投放的独立 `acquisition_stop`。
10. 广告计划、素材、绑定和手动运行接口当前多为“已登录即可写”，目标自建群接入后权限不足。
11. 当前 Guardian 没有持久化可用于可靠入群归因的邀请链接元数据和 durable update cursor。
12. `AccountAdBinding.creative_id` 当前可空并会退回全局素材池，目标型计划可能选中未经 CTA 校验的素材。
13. 现有 schedule lease 过期后可重新 claim；没有持久业务调度槽时，Celery 重投可能重选素材并重复发送。
14. 当前私链列表接口会返回解密后的链接，权限和响应契约须在阶段 4 P0 同步收口。
15. 来源群现有raw写入同时存在Telethon bare positive ID与marked `-100...`；不得原地改写破坏阶段1–3，阶段4须增加canonical sidecar，否则同一群会绕过source=destination、自建群排除和业务槽唯一约束。
16. 现有冷却和账号最小间隔只统计 `success + sent_at`；fence 后的 unknown/definite_failure 会被漏计。
17. 现有广告 dry-run 会经过创建 Profile、更新 Membership 和 LLM 生成素材的 helper；不能作为只读预演直接复用。
18. 停止门只在 RPC 前读取一次仍有检查到发送之间的竞态，必须定义在途排空和线性化点。
19. 广告表没有独立schema maintenance shared/exclusive permit，在线writer可能与expand/backfill/finalize并发。
20. 现有 `TelegramExecutionService.send_ad()` 会再次执行风险reserve，无法承载一次性预授权和durable fence；目标型路径须用专用发送合同。
21. 多素材由同account/campaign多条binding构成；若按outer binding循环调度或只冻结creative，会重复建槽或锁错binding。

## 3. 范围、目标和非目标

### 3.1 P0 必交付范围

1. 一个广告计划可绑定零个或一个自建群承接目标。
2. 目标绑定、解绑、CTA 文案更新使用 revision 乐观锁。
3. 计划启用前进行完整资格校验，投放前再次实时校验。
4. CTA 按“有效公开用户名 → 当前有效私链 → 阻止”解析。
5. CTA 由确定性代码渲染；AI、Persona 和素材链接不得决定目标 URL。
6. 保留现有 Growth/AD_ONLY、广告许可、额度、冷却、风险和存活逻辑。
7. 保留候选查询和最终发送前的自建群接收域排除。
8. 邀请链接轮换与外部发送共用承接资产链接锁。
9. 投放日志保存外部来源和承接目标的不可变安全快照。
10. 发送结果区分 confirmed、definite_failure 和 unknown，unknown 不自动重发。
11. 新增阶段 4 双开关和独立 `acquisition_stop`。
12. 增长中心页面增加承接群配置、资格、预览、日志和投放级统计。
13. 除 §14.10 经 admin 二次认证的单次 reveal 响应外，私有邀请链接不进入浏览器持久面、普通 API、数据库日志、Redis、结构化日志、指标或 Celery 结果。
14. 有投放历史的广告计划不可硬删除。
15. 阶段 2/3 内部消息对增长中心配置保持零业务依赖。
16. 持久化业务调度槽、冻结素材并提交 durable quota consumption，Worker 重投不可取得第二次发送资格。
17. 收紧既有私链读取接口为显式 admin reveal；阶段 4 页面永不调用 reveal。
18. 使用expand/finalize双迁移和maintenance runner；canonical使用sidecar，升级不得改变legacy raw值。
19. 目标型风险检查只预授权一次，冻结具体selected binding、外部recipient和payload后再提交send fence。

### 3.2 P1 可选增强，不阻塞阶段 4 P0 / 总方案 M3

1. 持久化 Guardian `chat_member` 入群观察及 durable cursor。
2. 使用邀请链接指纹进行 link-level 候选匹配。
3. 公开用户名入群仅标记为 destination-only。
4. 多个投放候选时标记 ambiguous，不选择“最接近”的一次。
5. 可选使用 owner 用户账号执行 `messages.getChatInviteImporters` 对账。
6. 展示归因覆盖率和置信等级。

### 3.3 明确不做

- 不把 `OwnedGroupAsset` 加入 `target_group_ids`；该字段永远表示外部投放群。
- 不让广告 Dispatcher 自动创建、撤销或轮换邀请链接。
- 不为每一次广告自动生成独立邀请链接。
- 不自动编辑已发送到外部群的历史广告；轮换后历史私链失效属于已知副作用。
- 不让 Persona 或 LLM 生成、选择、补全或改写 CTA URL。
- 不把阶段 2 `promotion_config.destination_url/cta_text` 与阶段 4计划配置同步。
- 不把广告发送成功叫作“入群转化”。
- 不承诺公开用户名路径可提供点击级或外部群级入群归因。
- 不把 XBoard 注册或支付归因作为阶段 4 P0 验收项。
- 不新建一套广告 Worker 或重写既有广告状态机。
- 不因为 `governance_stop` 暂停而直接停止外部广告；只依据目标的当前有效治理状态。
- 不因 `acquisition_stop` 或广告设置改变自建群内部消息行为。

### 3.4 成功标准

- 旧计划只有在 destination 为 null 且 destination revision=0 时，其素材渲染、准入、调度和发送结果才与上线前一致；曾绑定后解绑的计划不得伪装成 legacy。
- 新计划能稳定将 CTA 指向配置的 READY/MANAGED 自建群。
- 公开用户名有效时始终优先，私链只在规定条件下兜底。
- 两个计划共用同一素材但目标不同，不出现串链。
- 归档、降级、映射错误、链接失效或 source=destination 时不调用 Telegram。
- 链接轮换与发送并发结果可线性解释，新发送不会在旧链撤销后使用旧链。
- 除显式 admin 单次 reveal 的瞬时成功响应外，任何私链秘密扫描测试均为零泄漏。
- Telegram 结果不确定时不重复发送、不因 Redis TTL 释放配额；只能确认成功或关闭为不可重试的 `closed_unknown`。
- `acquisition_stop` 返回成功后，第 10.2.2 节接线清单内的搜群、加群、验证回复、广告许可探测、外部广告发送和 AD_ONLY 交接不存在在途 shared permit，也不再产生新的 Telegram RPC；明确排除的关键词回复、外部群常规暖场和私聊 CRM 不在本门禁承诺内，自建群内部消息仍正常。
- 真实 Telegram 测试 supergroup 的公开和私有 join-request 两条 E2E 通过。

## 4. 标识规范与业务隔离

### 4.1 ID 定义

| 字段 | 唯一含义 | 数据来源 |
| --- | --- | --- |
| `source_group_id` / 现有 `group_id` | 外部投放群 `Group.id` | 广告 Membership |
| `source_canonical_telegram_chat_id` | 外部投放群 canonical marked Telegram Chat ID；新 sidecar，不复用 legacy raw列 | `Group.canonical_telegram_chat_id` |
| `destination_owned_group_asset_id` | 承接自建群 `OwnedGroupAsset.id` | Campaign |
| `destination_core_group_id` | 承接群对应的内部 `Group.id` 快照 | OwnedGroupAsset |
| `destination_telegram_chat_id` | 承接群 canonical marked Telegram Chat ID 快照 | OwnedGroupAsset |
| `destination_invite_link_id` | 本次使用的 `OwnedGroupInviteLink.id` | Resolver |
| `account_id` | 实际向外部群发广告的 `TelegramAccount.id` | AccountAdBinding |
| `owner_account_id` | 验证承接群及链接的群创建者用户账号 | OwnedGroupAsset |
| `guardian_bot_account_id` | 自建群治理 Bot 账号 | OwnedGroupAsset |

禁止根据 ID 正负、长度或数值相等猜测实体类型。所有跨域映射必须通过显式外键和 Telegram Chat ID 一致性校验。

#### 4.1.1 Telegram Chat ID canonical 合同

阶段 4 所有身份比较、锁键、业务槽和新日志一律使用 Telethon marked peer ID 的有符号 BIGINT 表示：

~~~text
channel / supergroup = -(1_000_000_000_000 + bare_channel_id)  # -100...
basic group          = -bare_chat_id
~~~

实现固定新增 `canonical_telegram_chat_id(entity_or_peer, peer_kind)`；拿到 Telethon entity/peer 时以 `telethon.utils.get_peer_id()` 为标准结果。仅有正数或绝对值时不得猜 peer_kind，必须先由已授权账号解析远端实体，或读取已有且可信的 `PeerChannel/PeerChat` 类型证据。用户账号 ID 不允许进入任何 group chat 字段。

为避免直接改写现有 `Group.group_id` 破坏阶段 1–3，在 `group` 表新增 `canonical_telegram_chat_id BIGINT nullable` 和唯一部分索引 `WHERE canonical_telegram_chat_id IS NOT NULL`。合同如下：

- 阶段4候选、source/destination冲突、source lock、reservation token，以及 `AdDeliveryScheduleState`/`AdDeliveryLog` 新增的 `source_canonical_telegram_chat_id` 全部读取该 canonical 值。现有两表的 `telegram_group_id` 继续是legacy raw快照，不改写、不参与目标型身份判断。
- `OwnedGroupAsset.telegram_chat_id`、`ManagedGroupBinding.telegram_group_id` 的现值必须与各自core Group canonical精确核对，未来写入经过同一helper；supergroup结果必须是 `-100...`。只有报告能证明同一远端实体且阶段1引用预检通过时才允许专用remediation修正，禁止无证据批量重解释。
- `GroupFinder`、membership sync 和 Guardian sync 在新建/匹配 Group 前先按 canonical 列查询，禁止同一远端群再产生第二条 core Group。
- API 可以接收十进制字符串或 JSON integer，但只有在同时有可信 peer kind/entity 时才规范化；模糊 bare ID 返回 422 `TELEGRAM_CHAT_ID_AMBIGUOUS`，不自动补 `-100`。
- 所有新目标型日志的 source/destination canonical ID 必须 `< 0`；source 与 destination 相等时在 claim 前及 fence 事务内各阻止一次。

`backend/scripts/audit_telegram_peer_ids.py` 固定为三类命令。扩表前执行 `audit --output <report.json>`：只读扫描全部仍被 Membership、OwnedGroupAsset、ManagedGroupBinding、GroupAdProfile、ScheduleState、DeliveryLog 或广告策略事件引用的 Group/Telegram群ID，使用可用且已授权账号或可信 PeerChannel/PeerChat 证据解析实体，输出 `table/pk/raw_id/canonical_id/peer_kind/evidence_source/verified_at/db_snapshot_hash` 的安全报告；不得输出 access hash、session、手机号或邀请链接。report `generated_at` 到 apply 开始不得超过 `CANONICAL_REPORT_MAX_AGE_SECONDS=1800`，且 DB snapshot hash必须完全相同，否则脚本返回 `TELEGRAM_CHAT_ID_CANONICALIZATION_REPORT_EXPIRED` 并重新 audit。

`052/038` 只完成兼容扩表，随后在广告 schema维护闸门内执行 `apply --input <report.json> --expected-sha256 <hash>`。apply主事务只回填 `Group.canonical_telegram_chat_id`；Phase4尚未产生数据，因此ScheduleState/DeliveryLog的新canonical sidecar保持null供新代码写入。OwnedGroupAsset/ManagedGroupBinding只做一致性断言，确需修正必须使用报告证明同一实体的显式remediation并重跑阶段1回归。历史raw列一律不改：至少包括 `Group.group_id`、Membership/GroupAdProfile/GroupAdPolicyEvent/GroupAdOnlyAssessment/AutoJoinAttempt/GroupFailoverTask/GroupSearchRecord/ResourceSearchResult/AcquisitionMessage/TriggerRecord，以及ScheduleState/DeliveryLog既有 `telegram_group_id`。这样外部暖场日限/冷却、auto-join控制、阶段1–3查询仍使用原raw等值语义。

apply/finalize必须断言：所有可能进入目标型候选的当前Group均有唯一可信canonical；OwnedGroupAsset/ManagedGroupBinding与其core Group一致；新sidecar partial unique/index可创建；现有raw值、既有reservation_token、各表行数与外部暖场/auto-join命中数完全不变。Group已删除的历史DeliveryLog允许仅保留legacy raw值且version=2，不用于Phase4身份、槽或远端对账；禁止猜造canonical。

apply 成功同事务 upsert `SystemSetting.key=migration.telegram_peer_canonicalization`，value固定安全 JSON `{status:"applied",generation:1,report_sha256,db_snapshot_hash,schema_stage:"expand"}`，时间使用 SystemSetting.updated_at列。`053/039` 完成所有逐表断言后把同一行 CAS 为 `{status:"finalized",generation:1,...,schema_stage:"contract"}`。任一在用记录无法解析、同一 core Group 得到多个 canonical ID、或多个 core Group映射同一 canonical ID时 apply/finalize abort。碰撞不得自动 merge；管理员在维护窗口用专用 `remediate --survivor-group-id ...` 重指全部 FK并复核行数，再重新 audit/apply。报告按运维敏感件保存、不提交 Git，成功上线 7 天后删除；在线判断使用该安全状态行和数据库 canonical 完整性，不依赖报告文件仍存在。

## 6. 广告计划领域合同

### 6.1 计划类型

通过 `destination_owned_group_asset_id + destination_config_revision` 区分，不新增另一套表或可写 type 字段；响应中的 `destination_mode` 由服务端只读派生：

| destination / revision | `destination_mode` | 行为 |
| --- | --- | --- |
| null / 0 | `legacy` | 完全沿用 `AdCreative.link_url` |
| 非 null / >=1 | `owned_destination_bound` | 只使用服务端实时解析的自建群 CTA，禁止回退素材链接 |
| null / >=1 | `owned_destination_unbound` | 曾绑定后解绑；必须 disabled且非 active，不得运行或回退素材链接，重绑后才可启用 |

禁止通过普通 Campaign update 把 revision 改回 0；只有迁移前真实 legacy 行可以处于 `legacy`。

### 6.2 状态

`AdCampaign.status` 固定为：

~~~text
draft | active | paused | cancelled
~~~

执行资格必须同时满足：

~~~text
campaign.enabled == true
AND campaign.status == "active"
AND start_at/end_at/time window 命中
~~~

兼容规则：

- 创建请求 `enabled=true` 时服务端强制 `status=active`。
- 更新 `enabled=true` 时服务端同步为 `active`。
- 更新 `enabled=false` 且未显式指定 status 时，原 active 自动变为 `paused`；draft/cancelled 保持。
- cancelled 不允许再次启用；需要复制为新计划。
- 数据迁移将 `enabled=true` 的历史记录规范化为 active；`enabled=false AND status=active` 规范化为 paused；`enabled=false` 且非法或空 status 规范化为 draft；其他合法非 active 状态保持。
- 调度器不得再忽略 status。
- 数据库新增 `ck_ad_campaign_status`：`status IN ('draft','active','paused','cancelled')`，并新增 `ck_ad_campaign_enabled_status`：`(enabled AND status='active') OR (NOT enabled AND status<>'active')`。
- API 请求/响应使用同一个 `AdCampaignStatus(StrEnum)`；未知 status 返回 422，enabled/status 冲突返回 422，禁止只靠前端修正。

### 6.3 目标配置修改规则

- 计划启用时禁止绑定、解绑或改变目标/CTA，返回 409 `CAMPAIGN_MUST_BE_DISABLED`。
- 修改目标使用专用 endpoint 和 `expected_destination_config_revision`。
- 同值重放返回 200，revision 不增加。
- 不同值并发只有一个成功，其余返回 409 revision conflict。
- 初次从 null 绑定目标：revision 从 0 变为 1。
- 后续改变 asset、CTA 或解绑：每次加 1。
- 解绑后 revision 不回到 0；目标字段为 null，但保留最新 revision。
- 解绑同一事务强制 `enabled=false,status=paused` 并终结可终结的 pre-fence slot；返回 `destination_mode=owned_destination_unbound`。后续执行入口返回/no-claim `OWNED_DESTINATION_UNBOUND`，不调用 legacy renderer。
- 计划启用必须执行远端资格校验以及所有已启用绑定素材的 CTA 兼容检查。
- 当前日志若 `send_fence_committed=true`，或 outcome 为 unknown/legacy_unclassified，禁止改变 destination 或冻结 Creative，返回 `CAMPAIGN_HAS_UNRESOLVED_DELIVERY`。closed_unknown 已按第11.5节终结并清current；历史存在不阻塞新配置，若仍被current引用则返回 `CAMPAIGN_SCHEDULE_STATE_INCONSISTENT`。
- 当前日志若 `delivery_outcome=not_attempted AND send_fence_committed=false`，允许在第 12.2 节全局锁序内通过一次 CAS 原子终结：日志改为 skipped、reason=`CAMPAIGN_CONFIG_CHANGED_BEFORE_SEND`；quota=not_reserved 时保持 not_reserved，quota=reserved 时必须先确认同 token Redis风险 reservation已释放再改 released，其他 quota状态拒绝。清空 ScheduleState 的 current log/slot/冻结素材后再更新配置；CAS 失败返回 409，不得覆盖并发发送结果。
- 配置取消不会在同一 after_join/scheduled/interval 周期生成 replacement slot：interval推进到 `update_commit_at + interval`，scheduled推进到下一条正常 cron occurrence，after_join放弃该 membership epoch并等待下一次 join。这样 skipped旧 slot不会与业务槽唯一索引冲突，也不会借配置修改即时补发。
- 除下一条“单向安全暂停”外，所有影响执行的Campaign字段都必须复用 `finalize_pre_fence_slots_for_config_change()`：enabled/status、delivery_policy、send_mode、target_group_levels/ids、start/end、min_wait、interval、scheduled_times、两个daily cap、destination/CTA；Binding的account/campaign/creative/enabled；Creative的content/link_url/media_url/type/enabled。若影响多个disabled Campaign，先对destination ID排序取锁，再按ScheduleState ID排序，在单事务中校验并终结全部pre-fence slot；任何一行已过fence且未按允许路径终结则整次修改回滚，禁止部分更新。binding weight只影响尚未reservation的未来槽。
- destination专用更新同时递增destination revision和execution revision；普通Campaign PUT只改变execution revision。名称等纯展示字段不进入execution digest且不触发slot取消。
- 任一 ScheduleState 的 current outcome 为 unknown/legacy_unclassified 时，destination、Binding、Creative和其他执行字段修改一律返回 `CAMPAIGN_HAS_UNRESOLVED_DELIVERY`；confirmed/definite_failure/closed_unknown只有在current pointer已按状态机终结后才允许下一次修改。历史closed_unknown日志的不可变快照和quota继续保留，但它本身不再阻塞配置。
- 唯一例外是管理员通过通用 Campaign PUT 做单向安全止损：请求只能把 `enabled=false,status=paused`（status可省略并按第6.2节规范化）作为唯一执行变化，必须携带 `expected_execution_config_revision`、规范化 `reason` 和 canonical UUIDv4 `request_id`；若夹带其他执行字段返回422 `CAMPAIGN_SAFETY_PAUSE_ONLY`。首次止损在事务中锁 Campaign，并按ID锁其 ScheduleState/current DeliveryLog 仅用于识别未终结状态，然后只写 Campaign disabled/paused、execution revision+1及安全审计；不得调用pre-fence finalizer，不得改变任何 DeliveryLog、current pointer、slot、selected creative、quota/risk/proof或冻结快照。重新启用、改为cancelled或修改任何其他执行配置仍返回409。该例外只是禁止本Campaign未来claim，不等价于 `acquisition_stop`，不等待全局在途RPC排空。
- 目标型计划的 enabled binding 必须指定非空 creative_id；不允许使用全局素材 fallback。
- Creative 被 active 目标计划引用时禁止修改 content、link_url、media_url、type 或 enabled；需先暂停相关计划。

### 6.4 Campaign execution revision 与摘要

`execution_config_revision BIGINT` 是所有执行字段的统一CAS版本：历史Campaign回填0，新建写1；每次规范化后值实际变化才+1，同值重放不增加。目标型通用PUT和destination PUT必须分别携带expected execution revision（后者还要expected destination revision）；不匹配返回409 `CAMPAIGN_EXECUTION_REVISION_CONFLICT`。

reservation使用固定 `campaign_execution_v1` canonical JSON，字段顺序由 `json.dumps(sort_keys=true,separators=(",",":"),ensure_ascii=false)` 确定，输入包括：enabled/status/delivery_policy/send_mode；排序去重后的target_group_levels和整数target_group_ids；start_at/end_at的UTC微秒或null；min_wait_after_join_minutes/interval_minutes/排序去重scheduled_times；两个daily cap；destination asset/CTA/destination revision/execution revision。摘要为 `SHA256(UTF8("campaign-execution:v1\0") + canonical_json_bytes)`。

首次reservation把revision与digest同时写入ScheduleState/DeliveryLog。final fence锁内从当前Campaign重算并精确比对，且再次验证当前source Group仍命中冻结的target_group_ids或target_group_levels；target被移除、群level变化或任一字段变化均在fence前取消/失败关闭，绝不能按旧slot+新配置发送。安全暂停与final fence都锁同一 Campaign 行：暂停先提交时fence重读到disabled并保证该attempt的Telegram RPC次数为0；fence先提交时该attempt可完成，随后暂停只阻止未来claim且不改写在途/终态日志。

delivery_outcome IN ('not_attempted', 'confirmed', 'definite_failure', 'unknown', 'closed_unknown', 'legacy_unclassified')
attribution_capability IN ('placement_only', 'invite_link') OR NULL

delivery_state_version IN (0, 1, 2)

account/group 当日额度、间隔和冷却查询必须命中上述 partial index；PostgreSQL 集成测试用 `EXPLAIN (FORMAT JSON)` 断言目标数据量下不退化为全表顺扫。

跨字段不变量由 PostgreSQL CHECK 与服务层断言共同保证，但必须按 `delivery_state_version` 分域，不能破坏 destination=null 的既有 legacy 写入：

- `delivery_state_version=0` 仅用于阶段 4上线后的 legacy passthrough 新日志：destination/slot/link/rendered/media/acquisition/fence 快照均为空，`delivery_outcome=not_attempted`、`quota_state=not_reserved`、fence=false；status/message_id/sent_at/survival 完全沿用现有成功/失败/待处理语义，不套用下表。
- `delivery_state_version=1` 仅用于新目标型日志，必须有 destination asset、slot、source/destination安全快照和下表状态合同。
- `delivery_state_version=2` 仅由 `053/039` 写入迁移前历史日志；必须按第 7.2.1 节映射到下表，不允许应用创建。
- 数据库 CHECK 用上述 version predicate 包裹；禁止对 version=0 的 legacy success/failed 套用 `outcome/status` 下表。

| outcome | status | send_fence_committed | message_id/sent_at | quota |
| --- | --- | --- | --- | --- |
| not_attempted + pending | pending | false | 均为空 | not_reserved/reserved |
| not_attempted + skipped | skipped | false | 均为空 | not_reserved/released；released 只允许由 pre-fence reserved 释放 |
| confirmed | success | true | 均非空 | committed |
| definite_failure | failed | true | message_id/sent_at 均为空 | committed |
| unknown | unknown | true | message_id 为空 | committed |
| closed_unknown | unknown | true | message_id 为空 | committed |
| legacy_unclassified | unknown | true（保守） | 保留旧值，不据此推断 | committed |

- `delivery_outcome=definite_failure` 必须有 `send_fence_committed_at` 和第 11.4 节枚举的 `non_delivery_proof_code`；数据库 CHECK 拒绝其他值。
- unknown/closed_unknown 永远不得进入 released。
- `send_fence_committed=true` 的任何 outcome 永远不得进入 released；quota 仅能在 fence 前从 reserved CAS 为 released。
- 对 delivery_state_version 1/2，`quota_state=committed` 当且仅当 `quota_committed_at IS NOT NULL`，且必须与同事务写入的 `send_fence_committed_at` 完全相等；not_reserved/reserved/released 的 quota_committed_at 必须为空。
- `status=unknown` 只允许搭配 `delivery_outcome IN ('unknown','closed_unknown','legacy_unclassified')`；其他模型继续使用原 DeliveryStatus 值，不因共享 Python Enum 改变状态机。
- confirmed 的 survival status 只能使用现有 `not_required/pending/survived/deleted/check_failed`。
- not_attempted 不得有 `send_fence_committed_at`；confirmed/definite_failure/unknown/closed_unknown/legacy_unclassified 必须有。
- 新目标型日志自reservation创建起，source core/title/canonical sidecar、selected account-ad binding、destination asset/core/chat/title、destination config revision、campaign execution revision/digest、CTA snapshot、send payload kind和attribution_capability必须非空；来源标题缺失时写固定安全fallback `telegram:{source_canonical_telegram_chat_id}`。此时允许link type/fingerprint/resolved_at/rendered hash/version和media fingerprint为空。无法取得这些必填本地快照的失败必须发生在reservation前，按第11.3节不创建日志。
- 新目标型 reservation 固定写 `delivery_state_version=1`。text 的 media fingerprint 必须为空；media 的 fingerprint 必须在 fence 前非空。
- public_username 行必须 username 非空且 invite_link_id 为空；private_invite 行必须 invite_link_id 非空且 username 为空。完成 Resolver 后 fingerprint/key version/resolved_at 必须同时非空。
- 新目标型日志只要 `send_fence_committed=true`，则 link type/fingerprint/key version、`rendered_content_hash`、`rendered_content_version=1`、risk-content fingerprint/key version/simhash/algorithm version=1、send payload kind、destination_resolved_at 和 acquisition_gate_revision 全部必须非空；media 还要求 media fingerprint及其 key version同为空/同非空。数据库 CHECK 必须表达该蕴含。
- 风险摘要 CHECK 只约束新目标型状态机：当且仅当 `delivery_state_version=1 AND quota_state IN ('reserved','committed','released')` 时，risk settings/authorization digest、risk_preauthorized_at及完整rendered/media/risk安全摘要必须非空；`delivery_state_version=1 AND quota_state='not_reserved'` 时三项预授权字段必须为空。这些字段在 `not_reserved→reserved` CAS时首次冻结；确认释放并回到not_reserved时清authorization digest/settings/preauthorized_at，released/committed保留审计摘要，resume只重新签发内存对象且不修改冻结值。
- `delivery_state_version IN (0,2)` 的 legacy/历史日志允许且必须保持 risk settings/authorization digest、risk_preauthorized_at 为空，不得为了通过 CHECK 伪造或回填预授权证据；上述目标型 risk 摘要 CHECK 必须以 `delivery_state_version=1` predicate 包裹。
- pre-fence retry/paused 日志保持 `pending/not_attempted`，允许尚未解析到 link 字段；只有 Resolver 已成功时才填 link 字段。CHECK 不得要求所有 pending 行都已有 link。
- destination 为 null 的 legacy Campaign 新日志固定 `delivery_state_version=0`，不得写任何 destination/slot/rendered/media/risk 预授权快照；历史迁移行固定 version=2，仅按第 7.2.1 节保留原证据，不补造链接、渲染哈希或 risk 预授权摘要。

#### 7.2.1 历史日志保守迁移

历史回填必须在第 7.2.2 节广告 schema 维护闸门已关闭所有广告写入、exclusive permit 已排空 shared writer 后执行。旧日志禁止仅按 `status`、error 文本或 message_id 为空推断“未发送”。

1. 先以 nullable 方式添加新列，暂不加跨字段 CHECK。
2. 所有迁移前历史行先写 `delivery_state_version=2`；`status=success AND telegram_message_id IS NOT NULL AND sent_at IS NOT NULL`：回填 confirmed、send fence=true、fence time=sent_at、quota=committed、quota_committed_at=sent_at。
3. `status=skipped`：回填 not_attempted、send fence=false、quota=not_reserved。
4. 其他旧 pending/failed/不完整 success：先把原值写入 `legacy_status_snapshot`，统一改为 `status=unknown`、`delivery_outcome=legacy_unclassified`、send fence=true、fence time=`COALESCE(sent_at,created_at)`、quota=committed、quota_committed_at与fence time相等、reason=`LEGACY_DELIVERY_OUTCOME_UNCLASSIFIED`。绝不能回填 definite_failure。
5. 对每个 legacy raw `(campaign_id,account_id,telegram_group_id)`，只要最新日志在第4步被迁为legacy_unclassified，不论旧status是pending、failed或不完整success，都生成 `legacy:v1:{reservation_token-or-log-id}` slot；不回填source canonical sidecar。若已有ScheduleState，则写入current log/slot、清空lock token/lease，`next_due_at`保持NOT NULL并写 `send_fence_committed_at` 作为不可执行占位，status置paused。所有claim查询必须先限定 `status IN (idle,retry)`，不得仅按due time领取；更旧歧义日志只保留为历史。
6. 没有 ScheduleState 时不新建可执行任务；任何 legacy_unclassified 都不驱动同一次重试或未来周期。管理员只能 closed/cancel 旧计划，再按业务需要克隆为新 Campaign 和新 slot。
7. 输出各分类行数和受影响 ID 的安全报告；存在未知 status、重复 reservation token/Telegram message identity、无法唯一映射的 legacy candidate 时 migration abort，不自动猜测。
8. 回填完成后再加 NOT NULL/default/CHECK；新代码禁止创建 legacy_unclassified。

任何 legacy_unclassified 只允许 admin 转为 closed_unknown，不允许 confirmed（没有可靠 `rendered_content_hash`），quota 不释放；处理后仍按保守策略取消/克隆 Campaign，不恢复同一旧 slot。

#### 7.2.2 广告 schema 维护闸门

既有 `automation.ad_delivery_execution.enabled` 只约束 dispatcher，不足以保护 schema/backfill。P0 必须先上线一个独立、默认关闭的维护闸门：

- `SystemSetting.key=maintenance.ad_delivery_schema`，value 固定为 `{"enabled":false,"revision":0,"reason":null,"updated_by_user_id":null}`；时间真源使用 `SystemSetting.updated_at` 列，不在 JSON 内复制 `updated_at`。
- 固定 helper 为 `ad_delivery_schema_write_permit(action, timeout_seconds=3.0)` 与 `ad_delivery_schema_exclusive_permit(timeout_seconds)`；二者分别使用 `pg_try_advisory_lock_shared` / `pg_try_advisory_lock` 的独立 namespace `vngrd-ad-schema-maintenance`。SQLite 只可用进程内等价锁做单测。
- 下列入口在任何广告业务表读改写事务前都必须取得 shared permit，并在 permit 内复核 maintenance setting=false：Campaign/Binding/Creative 写 API、手动 `/ads/run`、dispatcher、存活检查、unknown scanner/reconcile/outbox dispatcher，以及所有会写 `AdDeliveryLog` 或 `AdDeliveryScheduleState` 的 repository/service。维护开启或状态不可读时，API 返回 503 `AD_DELIVERY_SCHEMA_MAINTENANCE`；Worker 不 claim 新工作并以相同稳定码告警。
- “所有直接写”指代码库内全部 repository/service 路径；生产运维禁止绕过服务执行手工广告 DML。迁移 runner 是唯一例外，但必须持有 exclusive permit并使用独立 migration connection。
- 阶段 2/3 `Speaker.send_owned_group_message` 和内部消息链禁止接入本闸门；维护阶段仍允许 growth 账号在自建群内按内部配置发言/宣传。

新增 `backend/scripts/run_phase4_ad_migration.py`，固定参数 `--mode alembic|sql --report <path> --expected-sha256 <hash>`；生产一次只选择一种 mode，禁止 SQL 与 Alembic 同跑。执行顺序固定为：

1. 预备版本先创建/校验 maintenance setting 行并完成全部 shared permit 接线，阶段 4功能保持关闭。
2. runner 以 canonical UUIDv4 request_id 和 reason CAS 把 maintenance enabled=true，等待 `job_lease_seconds + 2 × Telegram send timeout`，再取得 exclusive permit；若超时返回 `AD_DELIVERY_SCHEMA_MAINTENANCE_DRAIN_TIMEOUT`，setting 保持 true。
3. exclusive permit 持有期间依次执行 `052/038` 兼容扩表、校验并 apply canonical report、执行 `053/039` 历史回填/约束收紧和 verify；应用 writer 不可能与其中任何一步并发。
4. 任一步失败时回滚当前可回滚事务、释放连接和 exclusive permit，但 maintenance setting 继续为 true；只能按报告修复或按第 23.4 节回退，禁止 finally 自动关闭。
5. 迁移成功后先部署新应用并完成 schema/head/行数/canonical/隔离检查；再显式执行 runner `--finish --expected-revision <n> --request-id <uuid> --reason <text>` 关闭 setting。关闭动作使用 revision CAS 并审计；只有 setting=false 后广告 writer 才恢复。

锁顺序固定为 maintenance shared/exclusive permit → 其他广告 worker/source/destination/gate/row lock；已有代码在取得 maintenance permit 之前不得持数据库 row lock。维护 runner 持 exclusive permit时可用另一条专用 connection 执行 DDL/DML，但不得调用普通广告 service。

### 7.4 历史删除和素材修改语义

- 将 `ad_delivery_log.ad_campaign_id` 的 FK 从 `ON DELETE CASCADE` 改为 `ON DELETE RESTRICT`。
- 将 `ad_delivery_log.account_id` 从 `ON DELETE CASCADE` 改为 `ON DELETE RESTRICT`，`creative_id` 从 `ON DELETE SET NULL` 改为 `ON DELETE RESTRICT`；历史中的发送账号和素材引用不可被抹除。
- 同步移除会让 ORM 级联删除日志的 relationship cascade；删除逻辑先显式检查依赖，不得依靠数据库 500。
- `DELETE /ads/campaigns/{id}` 在存在任意 delivery log 时返回 409 `CAMPAIGN_HAS_DELIVERY_HISTORY`。
- 只有 draft、disabled、无 binding、无 schedule state、无 delivery log 的计划允许硬删除。
- 有历史计划通过 `status=cancelled` 保留，不删除日志。
- `OwnedGroupAsset` 已有软归档语义；被日志引用时不得硬删除。
- `OwnedGroupInviteLink` 被日志引用时不得硬删除，只能撤销。
- 删除 TelegramAccount 或 AdCreative 时若存在任意 DeliveryLog，分别返回 409 `ACCOUNT_HAS_DELIVERY_HISTORY`、`CREATIVE_HAS_DELIVERY_HISTORY`。
- 外部 `Group` 若没有目标型ScheduleState，仍可按现有语义让历史日志 `group_id SET NULL`；但任何目标型ScheduleState均先由应用和DB trigger以409 `GROUP_HAS_DELIVERY_SCHEDULE`阻止删除。新目标型日志必须写满 `source_core_group_id_snapshot`、`source_group_title_snapshot` 和不可空 `source_canonical_telegram_chat_id` sidecar；既有 `telegram_group_id` 继续写当前legacy兼容值但不用于Phase4身份。
- 业务槽唯一键和 reservation token 使用稳定 `source_canonical_telegram_chat_id`，因此同一 Telegram群删除并重新导入Group行也不能取得同一slot的第二次发送资格。
- Creative 被 active Campaign 引用或被 pending/unknown slot 冻结时禁止更新正文、link_url、类型或删除；先停用相关 Campaign，且 unknown 未关闭前仍不可删除。
- 目标型 Campaign 的每个 enabled binding 必须有非空 creative_id；禁止全局素材池 fallback。

### 7.5 指纹算法和密钥轮换

私链、公开 URL 和最终渲染正文分别使用独立域分隔 HMAC，禁止共用 domain tag：

~~~text
HMAC-SHA256(
  key = VANGUARD_DESTINATION_FINGERPRINT_KEYS[active_version],
  message = domain + canonical_value
)

private invite domain = "owned-group-private-invite:v1\0"
public URL domain    = "owned-group-public-url:v1\0"
rendered ad domain  = "owned-group-rendered-ad:v1\0"
media locator domain = "owned-group-media-locator:v1\0"
risk content domain  = "owned-group-risk-content-exact:v1\0"
risk shingle domain  = "owned-group-risk-content-shingle:v1\0"
~~~

要求：

- 环境变量固定为 `VANGUARD_DESTINATION_FINGERPRINT_ACTIVE_KEY_VERSION` 和 JSON 映射 `VANGUARD_DESTINATION_FINGERPRINT_KEYS`；每个 key 至少 32 随机字节。
- 禁止复用 `VANGUARD_SIGNING_SECRET`、JWT 或邀请链接加密密钥。
- destination/link/rendered/media 日志和 P1 归因分别保存实际 key version。轮换时先部署新旧 key 窗，再切 active version；历史关联窗口结束前不得删除旧 key。
- 风险内容使用独立 `VANGUARD_RISK_CONTENT_ACTIVE_KEY_VERSION` / `VANGUARD_RISK_CONTENT_KEYS`，不得复用 destination、邀请链接、JWT 或签名密钥；exact和shingle domain共享该专用 keyring但严格域分隔。
- 指纹仅用于一致性、轮换审计和内部关联，不作为认证凭证。
- API、前端、指标 label 和普通日志不返回完整指纹；必要时管理员排障只显示前 8 位。
- 私链 ciphertext 仍只保存在 `OwnedGroupInviteLink`，不得复制到广告表。

| `last_error_code` | VARCHAR(64) nullable，只允许稳定安全码 |
| `created_at/updated_at` | TIMESTAMP NOT NULL |

唯一约束为 `(delivery_log_id, alert_sequence)`。`alert_sequence=0` 在 fence 满 5 分钟后产生；只有前一 sequence 已 sent 且 `sent_at + 24h <= now` 才产生下一序号。扫描器只负责幂等插入 outbox，dispatcher 使用 `FOR UPDATE SKIP LOCKED` 和有期限 lease 投递。成功才标 sent；失败或 lease 过期按同一 outbox 行 5 分钟退避，不提前抑制下一次投递。通知语义是 at-least-once：若外部告警系统已接收但响应丢失，允许带同一 dedupe key `ad-unknown:{delivery_log_id}:{alert_sequence}` 重复一次，接收端据此去重；规格不伪称跨外部系统 exactly-once。

#### 7.6.2 通用 OwnedGroup 审计字段扩展

为实现 runtime setting 的 reason/idempotency和 reveal 的 reason审计，P0 同一迁移向 `owned_group_audit_events` 增加 nullable `reason VARCHAR(200)`、`request_id CHAR(36)`、`request_fingerprint CHAR(64)`，并增加部分唯一索引 `(resource_type, request_id) WHERE request_id IS NOT NULL`。历史行保持 null。setting request_id 必须先通过第 14 节 UUIDv4/秘密校验；reveal 不使用 request_id/fingerprint。before_state/after_state 只存排序后的安全 JSON，不复制私链或完整正文。

### 7.7 时间类型

阶段 4 增量字段统一沿用当前代码的 UTC-naive `SQLAlchemy DateTime(timezone=False)` / PostgreSQL `TIMESTAMP WITHOUT TIME ZONE` 和 `datetime.utcnow()`。API 把其解释为 UTC 并输出带 Z 的 ISO-8601。禁止在同一状态机混用 aware/naive；全系统 TIMESTAMPTZ 改造另行立项。

### 8.2 本地资格条件

解析时必须同时满足：

1. Campaign destination 非空且 revision 与加载值一致。
2. `OwnedGroupAsset` 存在。
3. `asset.status == ready`。
4. `asset.archived_at IS NULL`。
5. `core_group_id`、`telegram_chat_id`、`managed_binding_id`、`guardian_bot_account_id`、`owner_account_id` 均存在。
6. `Group.id == asset.core_group_id`。
7. `Group.canonical_telegram_chat_id == canonical_telegram_chat_id(asset.telegram_chat_id, trusted_asset_peer_kind)`；禁止比较 raw `Group.group_id`。
8. `ManagedGroupBinding.id == asset.managed_binding_id`。
9. Binding 的 core group、经同一 helper规范化后的 Telegram Chat ID 和 Guardian Bot 均与 asset一致；raw bare ID与对应 `-100...` 必须判为同一实体。
10. `binding_status == active`。
11. `get_governance_status()` 的有效结果为 `managed`；不能只读 `asset.governance_status`。
12. Telegram 远端对象为 supergroup/megagroup，`broadcast == false`。
13. source core ID 和 Telegram Chat ID 均不能等于 destination。
14. 存在符合优先级的有效链接。

任一映射不一致都失败关闭；不得自动修复、选择 owner 的第一个群、使用历史快照或更换目标。

### 8.3 公开用户名路径

只有以下条件同时满足才选择公开路径：

- `visibility == public`。
- `telegram_username` 经 trim、去 `@`、小写规范化后匹配 Telegram username 白名单。
- `public_link` 若存在，其 username 与规范化值一致；不一致阻止，不能信任其中任一个。
- 使用 `owner_account_id` 对应的用户 session 解析 username。
- 远端解析到的 Chat ID 与 `asset.telegram_chat_id` 完全一致。
- 远端对象为 supergroup/megagroup 且不是 broadcast channel。

最终 URL 只能由代码构造：

~~~text
https://t.me/{normalized_username}
~~~

不得直接使用数据库中的任意 `public_link` 原文。

公开 username 缺失或格式非法时可以尝试已验证的 join-request 私链，并记录安全 warning；若私链也不可用，返回 `DESTINATION_PUBLIC_USERNAME_INVALID`。公开 username 明确返回 not occupied/not found 时同样可以尝试私链。public_link 不一致、网络错误、超时、权限错误或解析到别的 Chat ID 时必须阻止，不得以私链静默掩盖异常。

### 8.4 私有邀请链接路径

公开路径不适用或被 Telegram 明确判定不存在时：

1. 在承接链接锁内查询该 asset 唯一 `is_active=true` 的 `OwnedGroupInviteLink`。
2. 在内存解密。
3. 规范化为 `https://t.me/+{invite_hash}`；兼容读取旧 `joinchat` 形式，但不再输出旧形式。
4. 使用 owner 用户 session 查询该群的 exported invite 状态。
5. 校验邀请属于当前 Chat，未 revoked、未 expired；若远端有 expire_date，发送时剩余有效期必须 `>= 3600` 秒，否则 `DESTINATION_INVITE_EXPIRING_SOON`；若有 usage_limit，剩余次数 `usage_limit - usage >= 20`，否则 `DESTINATION_INVITE_CAPACITY_LOW`。无过期或无次数上限分别视为不受该项限制。
6. P0 外部公开投放只接受 `link_type=join_request` 且远端 `request_needed=true`；`member_invite` 返回 `DESTINATION_INVITE_JOIN_REQUEST_REQUIRED`。
7. Vanguard 不自动批准 join request，由现有 Guardian/人工审批链处理。
8. 计算 HMAC 指纹后，仅将 SecretStr 传给渲染/发送函数。

P0 常量固定为 `MIN_DESTINATION_INVITE_VALIDITY_SECONDS=3600`、`MIN_DESTINATION_INVITE_REMAINING_USES=20`，不接入增长中心广告配置；以后调整需版本化发布并重新跑 private E2E。

禁止：

- 使用 Growth 推广账号验证或创建承接链接。
- 使用 Guardian Bot 猜测其他管理员创建的完整私链。
- 因链接缺失自动创建新链接。
- 因远端查询失败使用本地 active 状态继续发送。
- 把明文 URL 放进缓存、exception、task result 或结构化日志。
- 在 Resolver、preview 或 dry-run 中调用 create/export/edit/revoke/import invite；这些路径严格只读。

### 8.6 远端验证缓存

Redis 缓存只能服务 selector、draft 保存、列表摘要和默认 `verify_destination=false` 的 dry-run，属于提示性 UX，绝不能授权真实发送。正缓存最长 15 分钟，只允许保存：

~~~json
{
  "asset_id": 18,
  "telegram_chat_id": -1001234567890,
  "link_type": "private_invite",
  "local_identity_digest": "<internal-only>",
  "eligible": true,
  "verified_at": "2026-09-11T02:00:00Z",
  "expires_at": null
}
~~~

- `local_identity_digest` 的输入固定为 asset/chat/binding/guardian 字段、`owner TelegramAccount.session_hash + updated_at`、link type/public username，或 active invite 的 `id + created_at + revoked_at + is_active + fingerprint`；不得引用模型中不存在的 revision/updated_at 字段。
- key 固定 `owned_group:destination:verify:v1:{asset_id}:{local_identity_digest_prefix}`，不包含明文 URL/hash。
- value 不含明文 URL、密文或 username 之外的 bearer secret。
- 链接 revoke/regenerate、asset 归档、治理状态变化、username 修改时主动删缓存。
- selector/preview/启用检查在 Redis 不可用时可直接实时探测；实时探测也失败则返回 blocked。
- 负缓存最长 60 秒，避免修复后长时间不可用。
- 每一次真实发送都必须忽略 eligible 正缓存：在 destination lock 内重新读取本地状态，再用 owner session 做新的 Telegram 远端 RPC。public 必须重新 resolve username 并精确比对 Chat ID；private 必须重新读取 exported invite 的 Chat、revoked、expire、usage/limit 和 request_needed。
- 负缓存可在 60 秒内保守阻止真实发送；不得用任何正缓存跳过最终远端 RPC。最终远端验证后、提交 send fence 前再比较 local identity digest，任一变化即失败关闭并重新排队。
- 正缓存只表达“曾验证通过”，不表达“当前可发送”。

## 9. CTA 与素材渲染合同

### 9.1 CTA 文案

`destination_cta_text` 规范化：

- Unicode NFKC。
- trim 首尾空白，连续空白压为一个普通空格。
- 只允许单行，禁止 CR/LF、NUL、控制字符和 bidi 控制字符。
- 1–80 个 Unicode 字符。
- 禁止 URL、`@username`、`{{...}}` 和 Markdown 链接语法。
- 默认写入 `加入交流群`。

CTA 文案是确定性配置，不送入 LLM。

### 9.2 占位符

目标型 Campaign 只支持：

~~~text
{{destination_url}}
{{destination_cta}}
{{link_url}}  # 仅作为 destination_url 的兼容别名
~~~

规则：

1. `{{destination_url}}` 与 `{{link_url}}` 的总出现次数最多 1；同时出现或多次出现均拒绝。
2. `{{destination_cta}}` 最多出现 1 次。
3. 先替换 CTA，再替换 URL。
4. 没有 URL 占位符时：
   - 没有 CTA 占位符：追加 `\n\n{cta_text}\n{destination_url}`。
   - 已有 CTA 占位符：只在末尾追加 `\n{destination_url}`。
5. 替换后若仍包含 `{{...}}`，返回 `CTA_UNRESOLVED_PLACEHOLDER`。
6. 不修改、不保存原始 `AdCreative.content`。

### 9.3 素材兼容规则

目标型 Campaign 的每个启用绑定在“启用时”和“每次发送时”都必须满足：

- 当前 `(account_id,campaign_id)` 下至少一条 enabled `AccountAdBinding.creative_id` 非空；禁止调用全局 `_choose_creative()` fallback。
- 现模型是一条 binding 对应一个 creative，多素材池由同一 `(account_id,campaign_id)` 的多条 enabled binding组成。dispatcher必须先按 `(account_id,campaign_id)` 去重，不能按每条 outer binding重复运行同一计划。
- reservation winner用现有权重从上述池选择后，同时冻结 `selected_account_ad_binding_id` 与 Creative ID；Creative 必须存在且 enabled，所选 binding 的 account/campaign/creative 三元组必须精确匹配。不得把触发循环的 outer binding误当成 winner。
- `creative.link_url IS NULL`。
- 正文不包含硬编码 Telegram 群/频道/邀请 URL，包括 `t.me`、`telegram.me`、`joinchat`、`tg://join`。
- 允许现有内容策略认可的非 Telegram URL，但不把它当作承接 CTA。
- 正文的目标占位符符合 9.2。
- AI 素材生成进入 `owned_group_destination` 模式时只生成正文/占位符，生成结果强制 `link_url=NULL`。
- 生成 Prompt 不包含私链、公开链接或承接群 username。

同一 Creative 可以绑定多个目标不同的 Campaign；发送时使用各自 Campaign 的 destination，不得写回 Creative。

### 9.4 渲染结果校验

渲染后、调用风控和 Telegram 前必须校验：

- `creative_type=text` 且走 send_message 的正文不超过 4096。
- `creative_type=image|mixed` 且走现有 send_file/caption 分支时 caption 不超过 1024。
- 不能为空或只有 CTA。
- 最终 URL 仅出现一次，且与 Resolver 指纹一致。
- 不存在其他 Telegram 群邀请 URL。
- 不静默截断；超限返回 `CTA_RENDERED_CONTENT_TOO_LONG`。
- Persona 不参与渲染。

长度使用目标型广告的 `plain_text_v1` UTF-16 code-unit/entity limit 计量函数；加入 emoji、组合字符和边界值测试，禁止仅凭前端字符计数决定可发送。

新增纯函数建议：

~~~python
def render_owned_group_ad_content(
    *,
    creative: AdCreative,
    destination_cta_text: str,
    destination_url: SecretStr,
) -> RenderedOwnedGroupAd:
    ...
~~~

返回正文只能直接交给发送适配器；其 `repr`、日志和异常必须脱敏。

### 9.5 `plain_text_v1` 发送与内容证明

为使响应丢失后的人工对账可证明，所有 `destination_mode=owned_destination_bound` 的目标型广告固定为纯文本语义；只有 destination=null且revision=0 的 legacy 发送保持现有 parse mode，unbound 不允许发送：

1. Renderer 最终输出先把 CRLF/CR 统一为 LF，再做 Unicode NFC；除 9.1 已规定的 CTA trim 外，不删除正文空格或换行。
2. 文本广告 canonical kind 为 `text`，image/mixed caption 为 `caption`；canonical bytes 固定为 `UTF8("plain_text_v1\0" + kind + "\0" + normalized_text)`。
3. `rendered_content_hash = HMAC-SHA256(destination fingerprint key version, "owned-group-rendered-ad:v1\0" + canonical_bytes)`，同时写 `rendered_content_version=1`。
4. 目标型 `_send_ad` 调用 `client.send_message(..., parse_mode=None)`；媒体调用 `client.send_file(..., caption=..., parse_mode=None)`。不得依赖 client 默认 parse mode，也不得传 formatting entities。
5. Markdown/HTML 样式字符按字面发送；例如 `**文字**` 在 Telegram 中仍显示星号。前端预览必须与此一致，不得渲染富文本。
6. risk guard 仍在 fence 前检查完整内存正文，但不得把正文塞进 `TelegramExecutionService._risk_operation.details`；阶段 4使用第 9.6 节分离的 `content_for_policy` 与 `audit_details`，后者只能含 content fingerprint、长度、media flag和 delivery policy，禁止完整 content、私链或原始 media URL。
7. 媒体发送一旦 outcome=unknown，本阶段不允许仅凭相同 caption 转 confirmed，因为无法证明媒体本体一致；只能保持 unknown 或人工 closed_unknown。文本广告才允许按第 11.5 节远端正文证据转 confirmed。

### 9.6 冻结发送载荷与一次性风险预授权

目标型广告不得调用现有会在内部无条件 `check_and_reserve()` 的 `TelegramExecutionService.send_ad()`。新增专用合同：

~~~python
@dataclass(frozen=True)

    payload_kind: Literal["text", "media"]
    _content: SecretStr
    _media_locator: SecretStr | None

    media_locator_fingerprint: str | None

    risk_content_fingerprint_key_version: int
    risk_content_simhash: int

    def reveal_for_send(self) -> tuple[str, str | None]: ...
    def to_safe_risk_details(self) -> dict[str, object]: ...

@dataclass(frozen=True)
class AdDeliveryRiskAuthorization:
    reservation_id: str
    account_id: int

    risk_settings_digest: str

    def __reduce__(self): raise TypeError("risk authorization is not serializable")

async def preauthorize_ad_delivery(
    account: object,
    canonical_source_telegram_chat_id: int,
    *,
    content_for_policy: SecretStr,
    audit_details: dict[str, object],
    reservation_token: str,
    payload_hash: str,
) -> AdDeliveryRiskAuthorization: ...

async def resume_ad_delivery_preauthorization(
    account: object,
    canonical_source_telegram_chat_id: int,

    reservation_token: str,

async def send_ad_preauthorized(
    account: object,
    canonical_source_telegram_chat_id: int,
    payload: FrozenAdSendPayload,
    authorization: AdDeliveryRiskAuthorization,
    *,
    on_send_attempted: Callable[[], None],
) -> int: ...
~~~

固定实现语义：

1. `FrozenAdSendPayload` 在 sender acquisition shared permit 内、final fence 前构造。text 的 media locator/fingerprint 均为空；image/mixed 的 locator 取锁内读取的 `Creative.media_url` 并包装为 `SecretStr`，fingerprint 使用第 7.5 节独立 media domain。对象不进入 Celery、Redis、DB、repr、日志或异常。
2. `preauthorize_ad_delivery()` 必须拆分现有 content policy：`content_for_policy` 只在短生命周期内存中供 `_check_content_policy_read_only()` 检查，`audit_details` 才可写事件。预授权阶段不得写“内容已发送/已见”相似度 marker；exact/similar 检查查询 DB committed 的独立 `risk_content_fingerprint/risk_content_simhash` 与 Redis committed cache，DB 为真源，绝不能用含实际目标 URL 的 `rendered_content_hash` 代替。
3. 风险预算 reservation ID 固定由既有业务 `reservation_token` 派生；这里的 `canonical_source_telegram_chat_id` 是实际接收广告的外部来源群，不是承接自建群。目标型路径不再使用会把 public 群变成 `@username` 的 `_ad_send_target()`；必须用 sender session 从 canonical numeric source ID 解析 peer，核对解析后的 canonical Chat ID 完全一致，再把该 peer 同时作为风险 target 与 Telegram RPC recipient。任何路径都绝不能把 `destination_owned_group_asset_id` 对应群作为广告 recipient。同 token + 同 account/source/payload/settings digest 的 Redis Lua 重放只返回原授权、不重复增量。同 token 不同指纹返回 `AD_RISK_RESERVATION_CONFLICT`。marker 保存安全 digest、所占 counter key和 `reserved/committed` 状态，不含正文/media/link。
4. 首次预授权成功后用短事务 CAS 当前 DeliveryLog `not_reserved → reserved`，同事务冻结rendered/media/risk安全摘要、risk settings/authorization digest和risk_preauthorized_at。若CAS影响0行或commit结果未知，必须在仍持token lock时重读DB与marker：DB已是reserved且token/account/source/全部digest完全匹配视为幂等成功，保留reservation并继续，绝不能release；DB仍not_reserved或已skipped且marker仅reserved时才原子release。不同token/digest、缺marker或无法证明的组合保守为reserved/orphaned并禁止发送。
5. final fence 锁内重新计算 payload hash、媒体 fingerprint及其 key version、risk exact/simhash/settings/authorization digest；必须与DB冻结值和内存 payload/authorization完全一致且授权未过期。随后同事务 `reserved → committed`、写 unknown fence；不得覆盖reserved阶段冻结的摘要。DB commit 后把 Redis risk marker及内容相似度 cache 标为 committed；该缓存写失败不回滚 fence，由 reconciler从 committed DeliveryLog 修复。
6. fence 前因 gate/config/CAS/本地条件失败时，只有确认同 token Redis reservation 已释放后，才允许 `reserved → not_reserved` 并保留当前 pending slot；若该变化属于明确配置取消，则 `reserved → released`、日志 skipped并清槽。`released` 是终态，不能恢复为 pending。
7. fence 一旦 committed，无论 Telegram confirmed、definite_failure、unknown、进程崩溃或风险审计失败，风险预算和 DeliveryLog quota 都不得释放。
8. `send_ad_preauthorized()` 必须校验 authorization account/canonical source/payload hash/有效期且只允许内存消费一次；它禁止再次调用 `check_and_reserve()`，只负责风险结果审计和一次 Telegram RPC。RPC recipient 与风险 target 必须是同一个已验证的外部来源群 peer；承接自建群只出现在冻结 CTA 中。legacy Campaign 继续调用原 `send_ad()`，行为不变。
9. Creative 的 content、creative_type、media_url、link_url 任一更新都必须经过 `finalize_pre_fence_slots_for_config_change()`；pending/unknown 冻结时不得绕过。媒体 URL/file_id 绝不复制到 DeliveryLog。
10. 每次dispatcher进入风险步骤先在token advisory lock内读取DB quota：not_reserved走 `preauthorize_ad_delivery()`；reserved且marker/全部冻结digest完整匹配时，由当前dispatcher调用 `resume_ad_delivery_preauthorization()` 重新签发一次性短生命周期内存authorization，不增加counter、不修改risk_preauthorized_at，并直达本attempt final fence；committed/released不得再发。初次预授权依赖不可用返回 `AD_RISK_PREAUTH_UNAVAILABLE`；reserved但marker缺失/不一致返回 `AD_RISK_RESERVATION_ORPHANED` 并paused。后台reconciler不签发、存储或传递authorization，只负责修复marker/唤醒原slot。
11. 现有 risk reason 必须在 adapter 边界映射为稳定码：`content_repeat_account/content_repeat_target/content_similar_target → AD_RISK_CONTENT_DUPLICATE`（paused_creative，等待 Creative/CTA 配置变化）；`account_outbound_message_hard_cap → AD_RISK_ACCOUNT_DAILY_HARD_CAP`（pending/not_reserved，下一 UTC 日加 jitter）；有明确 retry_after 的 cooldown → `AD_RISK_COOLDOWN_ACTIVE`（同一 pending log按该时间重试）；账号封禁/隔离/全局 group-write ban → `AD_RISK_ACCOUNT_BLOCKED`（paused，等待账号风险状态恢复）。原始 risk 文本只作脱敏 detail，不进入调度判断。
12. 新增 `try_ad_risk_reservation_advisory_lock(reservation_token, timeout_seconds=3.0)`，namespace固定 `vngrd-ad-risk-reservation`。preauthorize/commit/release/reconcile同一 token都必须先取该锁；不得持 ScheduleState/DeliveryLog row lock等待它。

### 10.2 `acquisition_stop`

新增 DB 持久真源、Redis 低延迟镜像且失败关闭的 acquisition 安全门：

~~~text
backend/app/core/acquisition_gate.py
~~~

本阶段固定覆盖：

- 外部群搜索。
- 自动加群。
- 广告许可探测。
- 外部广告发送。
- AD_ONLY 交接过程中与外部获客直接相关的加群和退群。

不覆盖：

- 阶段 1 Guardian 治理。
- 阶段 2/3 自建群内部 community/promotion 消息。
- 已真实发生事件的只读存活检查和 P1 被动入群记录。
- 关键词回复、外部群常规暖场和私聊 CRM 等既有独立功能；若以后也要求统一停止，须另做完整入口审计。

检查时点：

1. 通用覆盖动作在 Worker/action 开始前。
2. 每次 Telegram RPC 前取得 acquisition shared permit，持锁复核 DB/Redis 后把 shared permit 一直持有到该 RPC 结果完成持久化。
3. `run_ad_delivery` 是唯一入口例外：task 入口只读取并记录 gate snapshot，不得因此跳过第 10.2 节明确排除的外部群常规暖场；进入广告许可探测或广告发送分支时再强制 assert。

Redis 或 DB 任一不可读、行/Redis key 缺失、payload 非法，或二者 revision 无法安全收敛时，acquisition 新动作失败关闭，返回 `ACQUISITION_GATE_UNAVAILABLE` 或 `ACQUISITION_GATE_SYNC_PENDING`；内部消息链不得调用该 gate。

API：

~~~http
GET  /api/safety-gate/acquisition/state
POST /api/safety-gate/acquisition/stop
~~~

POST：

~~~json
{
  "stopped": true,
  "reason": "incident-20260910",
  "expected_revision": 3,
  "request_id": "4c572f28-11c4-4ea8-84d7-c83a1de529f3"
}
~~~

`SystemSetting.key` 单独保存 `automation.owned_group_ad_destination`，上方 JSON 只是 value。运行时设置首次并发创建使用 key 唯一约束 upsert + row lock。

stop 和 resume 均要求 reason 1–200 字符、expected revision、幂等 request_id；只有 admin 可写。请求模型固定 `ConfigDict(extra="forbid")`。`request_id` 只接受小写 canonical UUIDv4（36 字符），验证必须发生在日志绑定、fingerprint、Redis 或 DB 操作之前；格式/版本/control/bidi 不合法返回 422 `REQUEST_ID_INVALID`，命中私链、token、password、session/access-hash 等秘密模式返回 422 `REQUEST_ID_CONTAINS_SECRET`，原值不得进入任何持久面或日志。

### 10.2.1 Redis 与 DB 状态合同

~~~text
Redis key = vanguard:acquisition_gate:v1
TTL = none
DB source of truth = acquisition_gate_state(id=1)
~~~

Redis value 固定为：

~~~json
{
  "schema_version": 1,
  "stopped": false,
  "revision": 0,
  "reason": null,
  "last_request_id": null,
  "last_request_fingerprint": null,
  "updated_at": "2026-09-11T02:00:00Z"
}
~~~

1. DB 行是持久真源，Redis 是低延迟执行镜像。
2. 进程启动先读 DB，再以相同 revision 装载 Redis；完成前本进程视为 stopped。
3. Redis key 缺失时执行一次 DB read-through 并原子恢复；完成前当前 action 阻止。
4. Redis 与 DB revision/值冲突时 effective 选择更安全的 stopped 状态并告警；只有 DB 中已提交且 request/fingerprint 完整匹配的 authorized resume event 可被 reconciler 精确重放到 Redis，其他情况禁止自动开放。
5. Redis 不可读、DB 不可读、行缺失或 payload 非法均视为 stopped。
6. Redis key 无 TTL；Redis flush/重启后按第 3 条恢复。
7. 本地进程不得无限缓存 open；每个 Telegram RPC 在 acquisition shared permit 内同时复核 DB 真源和 Redis 镜像，不能只读本地缓存或 Redis。
8. 新增每分钟运行的 `reconcile_acquisition_gate_mirror_task`：只允许从 DB 真源向 Redis 同步同一或更高 revision，绝不根据 Redis 自动打开 DB。revision 未收敛时 action 维持 `ACQUISITION_GATE_SYNC_PENDING` no-claim；该原因不创建广告 schedule 5 分钟 retry。

### 10.2.2 唯一接线清单

门禁必须接在 service 内部，不能只拦 API 或 Celery wrapper：

| 动作 | 当前主要入口 | 检查时点 |
| --- | --- | --- |
| 外部群搜索网络请求 | `GroupFinder.search_by_keyword/search_by_username` | Telegram search 前 |
| 自动加群 | `run_auto_join/_attempt_join_queued_group/_join_group` | task 入口 + join RPC 前 |
| 加群验证回复 | `_execute_join_verification_decision` 的 Telegram 写 | 写入前 |
| 广告许可探测 | `auto_probe_unknown_group_ad_policies/_send_ad_probe/send_group_ad_policy_probe` | task 入口 + probe send 前 |
| 外部广告投放 | `run_ad_delivery/_send_ad` | task 入口只观测；完成既有 warmup 判断后，广告分支 assert；send RPC 前 shared permit 内最终检查 |
| AD_ONLY 交接 | `_join_direct_target/_join_target/_leave_source_growth` | 每个 join/leave RPC 前 |

Scheduler、手动 API、Celery task 和 direct service 调用最终都经过同一个 `assert_acquisition_open(action)`；实际 Telegram RPC 固定经过 `acquisition_action_shared_permit(action)`。阶段 2/3的 `Speaker.send_owned_group_message` 明确列入禁止接线清单，即使文件位于 acquisition 目录也不能调用该 gate。

本地 dry-run 可以在 stop 时执行，但不得发起任何 Telegram 网络请求，只返回 gate 状态和本地判断。每次实际 action 在入口和 shared permit 内检查两次；`AdDeliveryLog.acquisition_gate_revision`、`AutoJoinAttempt.acquisition_gate_revision`、`GroupAdPolicyEvent.acquisition_gate_revision`、`GroupAdOnlyEvent.acquisition_gate_revision` 记录 permit 内检查读到的 revision。任何新覆盖动作缺 revision 视为实现错误并失败关闭。广告任务在 gate stopped 时仍可按既有配置完成明确排除的外部暖场，但广告 probe/send 调用次数必须为 0。

### 10.2.3 Lua CAS、审计和恢复

POST 请求补充：

~~~json
{
  "stopped": true,
  "reason": "incident-20260911",
  "expected_revision": 3,
  "request_id": "4c572f28-11c4-4ea8-84d7-c83a1de529f3"
}
~~~

- request fingerprint 固定为 `SHA256("acquisition-gate-request:v1\0" + canonical(stopped, normalized_reason, actor_user_id, expected_revision))`；canonical 使用 UTF-8、固定字段顺序和显式分隔。相同 request_id 但 fingerprint 不同返回 409 `ACQUISITION_GATE_IDEMPOTENCY_CONFLICT`。
- 新增两个 session-level PostgreSQL advisory namespace：`vngrd-acq-gate-transition` 是 stop/resume 共用的 exclusive transition mutex；`vngrd-acq-gate` 是 action shared / drain exclusive RW lock。SQLite 仅用于单测的进程内等价锁，生产验收必须 PostgreSQL。
- stop/resume 请求从读取幂等事件之前就取得 transition mutex，并持有至完整响应结果确定；3 秒内取不到返回 409 `ACQUISITION_GATE_TRANSITION_BUSY`。统一锁序只能是 transition mutex → gate exclusive，action 永远不取 transition mutex。
- stop 顺序固定为：transition mutex → DB `SELECT FOR UPDATE` CAS 到 stopped/revision+1并追加 event且提交 → 尝试 Redis Lua 同步同 revision stopped → 无论 Redis 成败都继续尝试 gate exclusive lock并等待所有已获 shared permit 的 RPC 完成。DB 一旦 stopped，后续 shared permit 复核即失败关闭。
- stop 等待上限固定取配置 `ACQUISITION_GATE_DRAIN_TIMEOUT_SECONDS`，默认 65 秒且必须大于单次 Telegram RPC timeout。只有 Redis mirror 已同步且 drain成功才能返回 200；drain超时返回 503 `ACQUISITION_STOP_DRAIN_TIMEOUT`，drain成功但 Redis未同步返回 503 `ACQUISITION_GATE_SYNC_PENDING`，二者都保留 DB stopped且响应给出安全的 `drained`。
- 相同 stop request_id 重试只在当前 `acquisition_gate_state.revision/stopped` 仍精确等于原 event 的 `revision/after_stopped` 时补 Redis和再次 drain，不加 revision、不追加 event。若已有更高 revision（例如 timeout 后已 resume），原请求已被超越，返回 409 `ACQUISITION_GATE_REQUEST_SUPERSEDED` 与安全 current state；绝不回放旧 stopped、改写当前状态或返回旧 200。
- 成功 stop 响应是本合同的线性化点：响应返回后，第 10.2.2 节覆盖动作没有仍持有的 shared permit，且新动作因 stopped 不能开始 RPC。已在 Telegram 网络栈中的请求不能强制撤回，所以 stop 必须等待它以 confirmed/definite_failure/unknown 之一完成持久化。
- resume 顺序固定为：transition mutex → gate exclusive lock → DB transaction 从 expected revision 写 open/revision+1和唯一 event → Redis Lua 同步精确 revision → 仅在两者一致后释放 gate exclusive/transition mutex并返回 200。Redis 失败则 DB 已 open但 effective 仍 stopped，返回 503 `ACQUISITION_GATE_SYNC_PENDING`；相同 request_id 重试同样只在 current state仍等于该 event.after 时补同步，已被更高 revision 超越则返回 `ACQUISITION_GATE_REQUEST_SUPERSEDED`。
- 普通 revision 冲突返回 409 `ACQUISITION_GATE_REVISION_CONFLICT` 并只返回安全 current revision/effective state。
- 每次变更写 before/after、actor、normalized reason、request_id、request_fingerprint、previous/new revision；禁止直接删 Redis key 作为 resume。
- stop/resume、阶段 4 runtime setting、reconcile 和 reveal 的 reason 全部先经过第 14 节统一 `normalize_admin_reason()`；验证失败不得写 gate/event/audit。
- `GET state` 返回 DB、Redis 和 effective；只有两者均可读、revision 相同且 stopped=false 时 effective_stopped=false。
- 所有 shared/exclusive permit 必须使用 dedicated connection，在 cancel/timeout/exception/正常退出时 unlock并关闭。可以在无 permit 时完成不跨 RPC 的 reservation 短事务，但同一次受保护 RPC 的 final fence row lock 和 AccountPool lease 必须在 shared permit 之后取得；严禁持任意 row lock等待 permit。
- helper 固定为 `acquisition_transition_mutex(timeout_seconds=3.0)`、`acquisition_action_shared_permit(action, timeout_seconds=3.0)` 与 `acquisition_gate_exclusive_permit(timeout_seconds)`；后两者分别使用 `pg_try_advisory_lock_shared` / `pg_try_advisory_lock` 同一个 gate 64-bit key，transition 使用另一个固定 key。
- action 3 秒内取不到 shared permit按 gate unavailable 失败关闭；stop/resume 3 秒内取不到 transition mutex 返回 409 `ACQUISITION_GATE_TRANSITION_BUSY`；resume gate exclusive 等待上限 3 秒，stop gate exclusive使用 65 秒 drain timeout。

成功 POST 响应的 data 固定包含 `{stopped,revision,effective_stopped,drained,request_id,updated_at}`。stop 只有 `drained=true` 才可返回 200；resume 成功固定 `drained=null`。GET 另返回脱敏的 `db_state`/`redis_state` revision 和 readable，不返回 request fingerprint。

| `provisioning_stop` | 不直接影响 | 不直接影响 |
| `governance_stop` | 不直接影响；有效治理已 degraded 时阻止 | 按阶段 2 契约 |
| `OWNED_GROUP_MESSAGING_ENABLED` | 不受影响 | 停止内部消息 |
| Persona 开关 | 不受影响 | 只影响内部 AI |

共享账号的物理 session lease、封禁状态和系统级出站硬上限仍可产生技术串行或全局安全阻断；这不等于继承增长广告业务配置。

## 11. 外部投放执行链

### 11.1 固定执行顺序

目标型 Campaign 单次投放顺序固定为：

1. 在读取或改写 Campaign、Binding、Creative、GroupAdProfile、ScheduleState、DeliveryLog 等广告业务表前，先取得第 7.2.2 节 maintenance shared permit并复核 schema 非维护状态，持有至本 attempt outcome 安全落地。只读 acquisition gate snapshot可在 permit 前读取；阶段 2/3内部消息不走此 permit。
2. 加载 Campaign、精确 account，以及该 `(account_id,campaign_id)` 下所有 enabled/non-null creative binding；候选执行先按该二元组去重，目标型素材池不得使用循环入口的单条 outer binding。
3. 检查 Campaign `enabled/status/time window/send_mode`。
4. 检查阶段 4 双开关。
5. 获取推广账号已加入的外部群候选，并只读加载该 tuple 的 `ScheduleState.current_delivery_log_id`。
6. 调用新增纯读 `evaluate_ad_static_skip_reason(..., exclude_delivery_log_id=current_delivery_log_id)` 检查 operation mode、Growth/AD_ONLY、`auto_ads_enabled`、安静时段、风险、外部群广告许可、容量和冷却；不得直接调用当前带 `_get_or_create_group_ad_profile()`/warmup副作用的 `_ad_skip_reason()`。inflight查询必须排除本 tuple 的 current log，使同一 pending slot 可恢复；其他 pending log仍应阻断。
7. 候选查询层按 canonical Telegram Chat ID 排除自建群。
8. 取得现有 ad account worker Redis 锁（只串行化该 sender 的 dispatcher，不是 AccountPool operation lease）和外部来源 `telegram_chat_advisory_lock(source_canonical_telegram_chat_id)`。
9. 再次按 canonical Telegram Chat ID 执行自建群 recipient 排除。
10. 在一个reservation短事务中锁ScheduleState：完成本地Campaign/binding pool/Creative静态资格后，claim并持久化 `delivery_slot_key`，首次winner从同一 `(account,campaign)` 的全部eligible binding加权选择一次，创建唯一pending/not_attempted log并同时冻结selected binding/creative、source/destination安全快照、destination revision、campaign execution revision/digest、slot/token；若既有current log则只加载它。此事务必须在任何destination lock/Resolver/RPC前完成。
11. 以 3 秒 try-lock 取得 destination link advisory lock。
12. 短事务重新加载 Campaign、Binding、account、source membership、Asset/Binding/Invite 行并核对 revision；不得跨 Telegram I/O 持 row lock。
13. 加载第 10 步 winner 的既有 pending log；禁止在取得 destination lock 后再新建 log、重选 Creative 或更换 slot。link lock busy和此后的 Resolver/Renderer retry均更新并复用该行。
14. 释放数据库 row lock 后，在 destination advisory lock 内取得一次 acquisition shared permit；permit 内再次复核 gate，再领取 owner 单次 AccountPool lease做只读远端目标验证。释放 owner lease和该 permit 后，按 `plain_text_v1` 渲染正文。
15. 取得 sender send 专用 acquisition shared permit并复核 gate；从此持有到第 23 步结束。若 gate closed，不取得风险 reservation/quota/fence，也不调用 Telegram。
16. 按第9.6节构造 `FrozenAdSendPayload` 并持有risk token advisory lock：当前日志为not_reserved时调用 `preauthorize_ad_delivery()`，再以短事务CAS到reserved并冻结全部安全摘要；当前日志已为reserved时必须验证DB/Redis marker/digest后调用 `resume_ad_delivery_preauthorization()`，重新取得只供本attempt使用的内存authorization。CAS影响0行但重读为同token同digest reserved属于幂等成功，禁止release；只有可证明DB未接受reservation时才release。任何拒绝、orphan或摘要冲突都不进入fence。
17. 在一个发送围栏短事务中按固定顺序 `SELECT ... FOR UPDATE` 锁 Campaign、日志冻结的 selected AccountAdBinding、Creative、TelegramAccount、AccountOperationConfig、source Group/Membership/GroupAdProfile、OwnedGroupAsset/ManagedGroupBinding/Invite、AcquisitionGateState、按 key 排序的相关 SystemSetting、ScheduleState 和 DeliveryLog；重新校验本节下方列出的全部条件、canonical source≠destination、目标/link/payload/risk digest、双开关和 permit 内 gate revision。
18. 同一事务领取 durable dispatcher/account/group quota，把 quota 从 reserved 转为 committed，并写 `status=unknown`、`send_fence_committed_at=now`、`send_fence_committed=true`、`delivery_outcome=unknown`、gate revision、plain-text/media hash/version 后提交。任一条件/CAS 失败整体回滚，不调用 Telegram，并按第 9.6 节处理风险 reservation。
19. fence commit 是配置资格的线性化点：若禁用/解绑/素材/许可/设置修改先提交，第 17 步失败；若 fence 先提交，该单次 attempt 已在途，之后的普通配置修改只对下一次 attempt 生效，不能撤回本次。`acquisition_stop` 例外，它等待本 shared permit 排空后才返回成功。
20. 调用 `send_ad_preauthorized()` 并传入冻结 payload/authorization；在仍持有 source/destination locks与 acquisition shared permit时领取 sender 的单次 AccountPool lease。该方法从日志冻结的 canonical numeric source ID 解析并验证 peer，Telegram RPC recipient 与 risk target都固定为外部来源群，绝不能是 destination owned group。内部不得再次风险预占、读取 Creative、重新选素材或再次渲染。
21. Telegram 明确成功：写 message ID、sent_at、`status=success`、`delivery_outcome=confirmed`，进入现有存活检查。
22. send fence 后只有第 11.4 节列出的 typed Telegram 拒绝才能写 `status=failed`、`delivery_outcome=definite_failure` 和 proof code；quota 保持 committed，同一 slot 永不重试。未在白名单的异常一律保持 unknown。
23. 请求超时、连接中断、进程崩溃或结果无法证明：预提交的 unknown/quota/fence 已是安全终态，ScheduleState 转 paused；finalize 写失败也保持 unknown。随后释放 sender lease和 acquisition shared permit。
24. 释放 destination link lock、外部群锁、account worker 锁和 maintenance shared permit。

现有 `_ad_skip_reason()` 中会创建 GroupAdProfile或触发 `_ad_warmup_skip_reason(..., dry_run=false)` 的分支必须拆开：外部群常规暖场仍不受 acquisition gate控制，但凡会触碰本次迁移涉及的广告业务表，也必须先取得 maintenance shared permit；纯广告资格 evaluator不得写 DB、Redis或调用 Telegram。阶段 2/3自建群内部消息既不调用该 evaluator，也不取得 maintenance permit。

第 17–18 步是 durable send fence 提交前的最终 fail-closed 确认，校验和 fence 必须在同一事务，不允许先校验、提交、再开另一事务写 fence：

- `TelegramAccount.account_type=promoter`、`is_active=true`、status 非 banned/error、session 健康。
- AccountOperationConfig 存在、enabled、`auto_ads_enabled=true`，operation_mode 与 Campaign delivery policy 相容。
- 日志与 ScheduleState 冻结的 selected AccountAdBinding ID一致；该行仍 enabled，account/campaign/creative三元组精确匹配冻结值。
- Creative 仍 enabled，content/type/media_url/link_url 与冻结 payload 完全一致；所有相关更新入口使用同一 row lock/CAS。
- source membership 仍为 joined、canonical Chat ID 一致且本地状态 writable。
- source GroupAdProfile 的广告许可 mode/confidence/expiry、tier/capacity/cooldown 在当前 fence time 仍满足现有规则。
- source canonical Chat ID 仍不是任何未归档 OwnedGroupAsset，且不等于 destination canonical Chat ID。
- Campaign仍active/enabled、当前UTC仍在time window；execution revision/digest、send_mode和目标revision与reservation一致；source core Group仍命中当前target_group_ids或target_group_levels。
- `automation.ad_delivery_execution`、`automation.owned_group_ad_destination` 与 `maintenance.ad_delivery_schema` 对应 SystemSetting 行仍允许；静态 `OWNED_GROUP_AD_DESTINATION_ENABLED` 重新读取仍为 true。
- AcquisitionGateState 与 Redis mirror revision一致且 open；risk authorization 未过期，account/target/payload/settings digest 均一致。
- 账号/来源群间隔和当日 durable quota 按当前 `send_fence_committed_at` 真源重算仍有容量。

AccountOperationConfig、GroupAdProfile、Campaign/Binding/Creative 和上述 SystemSetting 的写入口必须取得同一行锁或 revision CAS；这样 updater 与 fence 的提交顺序可线性解释。手工改库或绕过 API 的脏数据不得越过上述检查。

### 11.2 旧计划兼容旁路

仅 `destination_owned_group_asset_id IS NULL AND destination_config_revision=0` 时进入 legacy 旁路。若 destination为空但revision>0，立即 no-claim `OWNED_DESTINATION_UNBOUND`，不得执行以下任何一项：

- 不检查阶段 4 双开关。
- 不调用 Resolver。
- 不取得承接链接锁。
- `_render_ad_content()` 保持原 `creative.link_url` 行为。
- 新日志写 `delivery_state_version=0`、`delivery_outcome=not_attempted`、`send_fence_committed=false`、`quota_state=not_reserved`；其他目标/slot/rendered/media/risk字段为空。status/message_id/sent_at/survival仍由既有 legacy `_record_ad_delivery/_finalize_ad_delivery_log` 维护，version-scoped CHECK 不约束其 status/outcome 组合。
- 仍受 `acquisition_stop`，因为 legacy 广告发送属于第 10.2.2 节明确列出的外部广告动作；该门不扩展到第 10.2 节明确排除的其他功能。

### 11.3 目标失败处理

send fence 前失败分为两个边界，禁止混用：

- 第 10 步 reservation 之前的本地静态失败（资产不存在/未 READY、core/chat/binding/canonical 映射缺失、source=destination、无合格绑定素材）不创建 DeliveryLog、不生成 slot/token、不调用 Resolver；ScheduleState 如已存在则 `current_delivery_log_id/delivery_slot_key/selected_creative_id` 保持空，并按第 13 节记录 paused/no_claim 原因。
- 第 10 步已创建 reservation 后的 destination link lock、远端 Resolver、Renderer、risk preauthorization、final-check 或基础设施失败，必须复用同一条 `status=pending`、`delivery_outcome=not_attempted` 日志和同一 slot/token/creative/revision；不得另建第二条日志。
- 如果失败发生在风险 reservation 已取得之后，先按第 9.6 节原子 commit/release其 quota 状态；release 未确认时进入专用 paused 状态，绝不能直接重试。

对已存在 reservation 的 retry/paused 处理固定如下：

- retry/paused disposition 保持同一条 `status=pending`、`delivery_outcome=not_attempted` 日志，记录当时已知的安全目标 ID/revision 和稳定 reason code；ScheduleState 保留 current log/slot/creative。
- `send_fence_committed_at`、Telegram message ID 为空。
- 不调用 Telegram。
- 未进入第 9.6 节时不调用风险预占；已预占时必须按其 token 状态机处理，禁止第二次扣减。
- 不消耗成功/待发送日额度。
- 不回退到素材链接、另一个资产或历史链接。
- 不自动更换发送账号。
- 不因目标问题增加外部群或账号的广告失败计数。
- 根据第 13 节更新 schedule retry/paused；依赖恢复后以 CAS 把 ScheduleState 重新 claim，清理该 pending log 的旧 reason，并复用同一 delivery_log_id、slot、token、creative 和目标 revision。
- `status=skipped/not_attempted` 只用于管理员取消、配置在 fence 前变化或其他明确终止当前 slot 的路径；skipped 不可自动恢复为 pending。

### 11.4 发送结果语义

| `delivery_outcome` | 含义 | 自动重试 |
| --- | --- | --- |
| `not_attempted` | 可证明未调用 Telegram | 可按 schedule 规则重试 |
| `confirmed` | Telegram 返回成功且有 message ID | 否；进入存活检查 |
| `definite_failure` | send fence 后 Telegram 返回下方白名单中的 typed 明确拒绝 | 同一 slot 永不重试；仅由原 schedule 产生下一正常业务周期 |
| `unknown` | 请求可能已送达但无法证明 | 禁止自动重发，需人工对账 |
| `closed_unknown` | 人工关闭但仍无法证明是否送达 | 永久禁止重发，quota 不释放 |
| `legacy_unclassified` | 迁移前旧日志无法证明是否调用/送达 | 仅可人工关闭，原计划取消后克隆 |

unknown/closed_unknown 的 durable quota consumption 不依赖 Redis reservation TTL；TTL 到期不得回补额度或生成新 slot。definite_failure 也保持 committed。不得通过“日志里没有 message ID”、异常字符串或“后来找不到消息”推断未发送。

所有目标型 fence 后 outcome 使用 `attempt_anchor_at := send_fence_committed_at` 作为保守投放时间。账号最小间隔、外部群冷却、每日 account/group quota 和 definite_failure/closed_unknown 后下一正常周期都必须查询 committed 日志的 attempt anchor，不能再只查询 `status=success AND sent_at IS NOT NULL`。fence 事务同步写 Redis cooldown；Redis 写失败不回滚 durable fence，下一次检查必须以 DB committed anchor 为真源并修复缓存。confirmed 的存活检查仍以真实 `sent_at` 为准。pre-fence not_attempted 不占用 attempt interval；只有 destination=null且revision=0 的 legacy 计划继续沿用原逻辑。

`non_delivery_proof_code` 和 adapter 映射固定如下；只能按 Telethon typed RPCError 类/Telegram 结构化 error code 映射，禁止解析 message 文本：

| proof code | Telethon/Telegram 结构化来源 | outcome | quota |
| --- | --- | --- | --- |
| `TG_CHAT_WRITE_FORBIDDEN` | `ChatWriteForbiddenError` | definite_failure | committed |
| `TG_USER_BANNED_IN_CHANNEL` | `UserBannedInChannelError` | definite_failure | committed |
| `TG_CHAT_ADMIN_REQUIRED` | `ChatAdminRequiredError` | definite_failure | committed |
| `TG_PEER_ID_INVALID` | `PeerIdInvalidError` | definite_failure | committed |
| `TG_MESSAGE_TOO_LONG` | `MessageTooLongError` | definite_failure | committed |
| `TG_FLOOD_WAIT_REJECTED` | `FloodWaitError`，且本调用未由 client 自动重试 | definite_failure | committed |

输入/正文/媒体的本地校验必须在 send fence 前完成，失败写 not_attempted 并允许 reserved→released；不得伪造成 definite_failure。timeout、connection reset、cancellation、进程崩溃、5xx、反序列化错误、所有 media RPCError、未知/新 RPCError、`RandomIdDuplicate` 或任何仅有字符串证据的异常全部默认 unknown + committed + paused。`non_delivery_proof_code` 的数据库 CHECK 只允许上表六个值或 null；新增 typed error 若未同时更新集中映射、CHECK 和参数化测试，测试必须失败。

### 11.5 人工对账

新增：

~~~http
POST /api/automation/ads/delivery-logs/{delivery_log_id}/reconcile
~~~

请求：

~~~json
{
  "expected_delivery_outcome": "unknown",
  "resolved_outcome": "confirmed",
  "telegram_message_id": 98765,
  "reason": "verified_in_source_group"
}
~~~

规则：

- admin-only。
- unknown 允许转为 confirmed 或 closed_unknown；legacy_unclassified 只允许转为 closed_unknown。其他来源 outcome 不可对账。
- confirmed 必须提供正整数 Telegram message ID。服务端只能用日志冻结的原 sender account session，在外部 source chat lock 内调用 `get_me()` 和读取日志冻结 `source_canonical_telegram_chat_id` 的该 message；返回 chat canonical ID必须等于该sidecar，`message.sender_id` 必须等于本次 `get_me().id`，不得使用legacy raw `telegram_group_id`或把内部 `TelegramAccount.id` 当远端 sender ID。
- 只对 text creative 允许 confirmed：按 9.5 的 `plain_text_v1` 对读取回的 `message.message` 规范化，要求远端 entities 为空，再用日志 `rendered_content_version` 和 `destination_fingerprint_key_version` 对应旧 parser/key 计算 HMAC，必须等于 `rendered_content_hash`。
- image/mixed creative 的 unknown 请求 confirmed 固定返回 409 `DELIVERY_RECONCILIATION_MEDIA_NOT_PROVABLE` 并保持 unknown；相同 caption 不能证明媒体本体相同。
- Telegram `message.date` 必须位于 `[send_fence_committed_at - 30 秒, send_fence_committed_at + 10 分钟]`。读取失败、字段缺失、正文/caption/时间/sender/chat 任一不匹配、旧 key 不可用或 message ID 已被另一日志占用时保持 unknown，返回安全错误码，不部分更新。
- 验证成功后在一个事务内 CAS：写 `telegram_message_id`、`sent_at=message.date`、status=success、outcome=confirmed；按现有 `_finalize_ad_delivery_log(..., survival_required=True)` 语义初始化 `survival_status=pending`、`survival_stage=two_minute`、`survival_check_due_at=message.date + survival_check_delay_seconds`。若 due 已过则置为 `now_utc` 以便立即检查。
- 同一事务按 expected current log/slot CAS 清理 ScheduleState 的 unknown pause/current 指针，并基于原 send_mode 计算下一正常 due；该事务绝不调用 Telegram send。任一 CAS 冲突整体回滚。
- closed_unknown 不提供 message ID，表示永久关闭本 slot；不释放 quota，也不允许重新发送该 slot。unknown→closed_unknown 成功时在同一事务清 ScheduleState 的 current log/slot/creative，并按原 send_mode、以 `attempt_anchor_at` 计算下一正常周期；不创建即时补发。legacy_unclassified→closed_unknown 仍必须取消旧 Campaign 后克隆，不生成原计划下一周期。
- 使用行锁和 expected outcome；重复同值安全重放。
- 记录审计，不触发再次发送。
- 人工 reason 不能生成 definite_failure。definite_failure 只能由本次 adapter 调用返回的机器 proof code 直接产生。
- 本阶段不提供 force resend；如以后增加，必须为独立高危流程、新 slot/token、二次确认并明确可能重复。

### 11.6 Stale unknown 扫描

新增每 5 分钟运行的 `scan_unknown_ad_deliveries_task` 和独立 `dispatch_unknown_ad_alerts_task`：

~~~text
WHERE send_fence_committed = true
  AND delivery_outcome = 'unknown'
  AND send_fence_committed_at < now_utc - 5 minutes
~~~

- 把对应 ScheduleState 保持/修正为 paused，`last_reason_code=DELIVERY_OUTCOME_UNKNOWN`。
- 不改变 outcome、quota、slot、token 或 message ID，不调用 Telegram send。
- 扫描器按第 7.6.1 节规则只插入唯一 outbox，不直接发通知、也不先更新“已告警”时间。
- dispatcher 以 lease 领取 outbox；进程在 DB commit 后、通知前崩溃时由 lease expiry 恢复，同一 sequence 继续重试。连续失败仍每 5 分钟重试同一行，不提前创建下一 sequence。
- outbox 的创建、投递和重试均不得改变 DeliveryLog outcome/quota/slot；对账已完成后尚未领取的 pending outbox 标记 cancelled，不再发新提醒，已经在途的通知允许到达。
- 会修正/清理 ScheduleState 的 scanner 和 reconcile 必须先无锁定位 `(schedule_state_id,delivery_log_id)`，再按 `ScheduleState FOR UPDATE → DeliveryLog FOR UPDATE → 对应 outbox 行` 取得行锁并重检三者关联、current pointer及 outcome；不存在 ScheduleState 的历史日志才可直接 `DeliveryLog → outbox`。禁止先持有 DeliveryLog 再等待 ScheduleState，避免与 final fence、风险 reconciler形成反序。
- 纯 alert dispatcher 不修改 ScheduleState，可按 `DeliveryLog FOR UPDATE → outbox`。它在 claim 事务和实际投递前各重读并锁定 DeliveryLog；只要 outcome 已非 unknown，就把 outbox CAS 为 cancelled并不调用通知适配器。这样 reconcile 即使先于 scanner commit，也不会产生可领取的过期告警；若通知 RPC 已开始则只能按 at-least-once 接受其到达。
- PostgreSQL barrier test必须覆盖 final fence/risk reconciler 已持有 ScheduleState等待 DeliveryLog时，scanner/reconcile 绝不能已持有 DeliveryLog反向等待 ScheduleState；最终两方可完成且状态满足唯一 current pointer。
- 人工处理 SLA 为 24 小时；超时不自动 closed。
- Worker 启动恢复先运行同一逻辑；现有 expired sending claim 必须显式排除 unknown/closed_unknown slot。

## 12. 并发、锁和幂等

### 12.1 新增承接链接锁

在 `backend/app/core/telegram_chat_lock.py` 增加独立 namespace 和非阻塞接口：

~~~python
try_owned_group_destination_link_advisory_lock(
    asset_id: int,
    *,
    timeout_seconds: float = 3.0,
)
# PostgreSQL advisory namespace: "vngrd-dst-link"
~~~

不得复用 destination 的 `telegram_chat_advisory_lock`，否则阶段 4 外部广告会无谓阻塞阶段 2/3 自建群内部消息。

- PostgreSQL 使用 dedicated connection 上的 session-level `pg_try_advisory_lock`，100–250ms jitter 轮询，最多 3 秒。
- 超时映射 `DESTINATION_LINK_LOCK_BUSY`；不是无限阻塞。
- context manager 在 cancel/timeout/exception/正常退出时均 unlock 并关闭 dedicated connection。
- session lock 跨业务事务 commit 保持；SQLite 只用进程内 keyed lock adapter，最终并发仍须 PostgreSQL 验证。

### 12.2 统一锁顺序

~~~text
ad_delivery_schema_write_permit（maintenance shared，持有至 outcome 安全落地）
  → ad account worker Redis lock（仅 dispatcher；不是 AccountPool lease）
    → external source telegram_chat_advisory_lock
      → reservation short row locks → commit/release（此时尚未取 destination lock）
      → try_owned_group_destination_link_advisory_lock
        ├→ acquisition_action_shared_permit（owner probe）
        │   → one owner AccountPool operation lease → one Telegram RPC → release
        └→ acquisition_action_shared_permit（sender send，持有至 outcome 安全落地）
            → try_ad_risk_reservation_advisory_lock
              → risk preauthorize + quota reserved short transaction → release rows
              → final fence short row locks → commit/release
              → one sender AccountPool operation lease → one Telegram RPC → finalize/release
~~~

AccountPool operation lease 与 account worker lock 是两套不同机制。阶段 4禁止在取得 destination link lock和对应 acquisition shared permit前调用 `AccountPool.acquire_by_id()`；禁止同时持有 owner和sender两个 wrapper/operation lease。risk token lock必须在 acquisition sender permit之后、row lock之前取得。这样 sender==owner时也不会形成 account↔destination循环。`acquisition_stop`只取得 gate exclusive lock，不取得 maintenance/account/source/destination/risk/row lock，因此不会形成反向等待。

邀请链接 revoke/regenerate：

~~~text
try_owned_group_destination_link_advisory_lock
  → 短事务读取 asset/active invite 后释放 row lock
  → owner AccountPool operation lease → Telegram revoke/create → release
  → 短事务写入 database state
~~~

轮换 API 不取得 ad account worker lock 或 external source chat lock，也不得在 destination lock 前领取 owner AccountPool lease。所有代码必须遵守同一顺序，禁止持有 Campaign/Asset/Invite row lock 等待 destination lock，也禁止跨 Telegram 网络 I/O 持有 row lock。

Campaign 绑定、解绑或启用先取得 maintenance shared permit，再使用以下固定锁序：

1. 无锁读取当前 destination ID/revision。
2. 将旧、新 asset ID 去重排序并按升序取得 destination locks；解绑只锁旧 asset。
3. 再 `SELECT Campaign FOR UPDATE`，复核 ID/revision；变化则释放并有限重试一次，仍冲突返回 409。
4. 短事务冻结安全快照后释放 row lock。
5. 如需远端验证，在 advisory lock 下、事务外执行。
6. 再次短事务锁 Campaign 并复核 revision 后提交。

任何 API 不得先锁 Campaign 再等待 destination lock，避免与发送/轮换形成反向等待。

### 12.3 线性化语义

- 发送先获得链接锁：该次发送可以使用锁内验证的旧链接直至 Telegram 调用返回；轮换随后撤销。
- 轮换先获得链接锁：撤销/创建完成后，新发送只能读取新链接。
- 轮换失败且没有 active link：后续投放全部 `DESTINATION_LINK_UNAVAILABLE`。
- 新发送日志保存当次 invite row ID 和 fingerprint，历史日志不可改写。
- 系统不承诺轮换后外部群历史消息中的旧链接仍可用。
- final fence 事务是 Campaign/Binding/Creative/account/membership/目标资格的线性化点；全部行锁和条件重检必须位于该事务。禁止把“最终校验”和“写 fence”拆成两个 commit。
- 普通配置更新先提交时，fence CAS 失败且 Telegram 调用数为 0；fence 先提交时，该 attempt 被视为在途，随后账号禁用或 membership 变化仅影响下一次 attempt。目标/素材配置更新若发现 current log 已 fenced，返回 409，不改写本次快照。
- 第6.3节单向安全暂停与final fence共用 Campaign 行锁：暂停先提交时当前attempt不得提交fence/RPC；fence先提交时只允许该attempt安全落地，暂停提交后所有其他tuple及下一周期claim为0。安全暂停不清理未终结current状态、不释放quota，也不提供全局drain承诺。
- stop 的线性化点不是 DB stopped commit，而是成功取得 gate exclusive lock并确认 shared permit 已排空的时刻；只有该时刻之后才可对调用方返回 200。

### 12.4 业务调度槽

`delivery_slot_key` 在 ScheduleState 行锁内首次生成并立即持久化，直到该业务槽终结前不得变化：

| send_mode | slot 生成规则 |
| --- | --- |
| after_join | `after_join:v1:{membership_id}:{joined_at_utc_microseconds}` |
| interval | 首次进入该 due cycle 时用 Python stdlib `uuid.uuid4()` 生成 `interval:v1:{uuid}`，retry 不重建 |
| scheduled | 使用已持久化的本次 `next_due_at`：`scheduled:v1:{next_due_at_utc_microseconds}` |

- scheduled 的时区换算继续使用现有 scheduler；slot 只用换算后已持久化的 UTC-naive due time。
- retry 改变 next retry time，不改变 slot。
- 只有 confirmed、definite_failure 终结当前 slot，或管理员按 pre-fence CAS 取消配置，才清理 current slot；confirmed/definite_failure 只能按原 schedule 产生下一正常业务周期，不能立即重试原 slot。
- unknown保持ScheduleState paused并保留current pointer/slot，等待人工对账。unknown→closed_unknown后，DeliveryLog永久保留旧slot/fence/quota作为不可重用围栏，但ScheduleState同事务清current并按attempt anchor进入下一正常周期；不即时补发。legacy_unclassified继续paused，关闭后仍取消/克隆旧Campaign，不产生下一周期。

### 12.5 Reservation 和素材冻结

`reservation_token` 只由稳定业务身份生成，不含随机素材或可变化目标：

~~~text
SHA256(
  "ad-delivery-slot:v1" |
  campaign_id | account_id | source_canonical_telegram_chat_id | delivery_slot_key
)
~~~

reservation token 只用于幂等，不是认证凭证，因此不使用秘密密钥或 key version；canonical 输入固定 UTF-8、字段分隔和十进制 marked peer ID，输出 64 位小写十六进制。禁止加入 creative_id、destination revision、当前时间或随机数。

首次 reservation 在一个短事务内：

1. 锁 ScheduleState。
2. 以唯一业务槽查询/insert DeliveryLog。
3. 只有 insert winner 执行一次现有加权素材选择。
4. 把 `selected_account_ad_binding_id`、`creative_id`、destination revision、slot、token 同时写入 DeliveryLog 和 ScheduleState。
5. 提交后才进入 Resolver；竞争者加载 winner 的既有记录。

- 目标型 eligible binding 的 creative_id 必须非空；素材池只取同一 `(account_id,campaign_id)` 的 enabled binding，禁止全局素材 fallback。
- Binding 新增/禁用/改 creative/改 weight时，finalizer按受影响的 `(account_id,campaign_id,creative_id)` 和 frozen selected binding找到 pre-fence slot；weight只影响未 reservation槽，其余变化按第 6.3 节取消规则。
- 重试、Celery redelivery、lease 过期和进程重启只加载 `current_delivery_log_id`，禁止重选素材。
- destination revision、链接轮换或 Creative 权重变化都不能绕过 unknown/confirmed slot。
- 配置更新只允许对 `not_attempted AND send_fence_committed=false` 的 current log 执行单事务 CAS：pending→skipped、reason=`CAMPAIGN_CONFIG_CHANGED_BEFORE_SEND`；not_reserved保持不变，reserved只有在同 token Redis reservation释放确认后才转 released；随后清 current log/slot/creative并按第 6.3 节推进下一正常周期，再更新配置。CAS 发现其他 quota、fence=true、outcome变化或 current指针变化则返回409；unknown/legacy_unclassified永不借此清理，current指向closed_unknown按 `CAMPAIGN_SCHEDULE_STATE_INCONSISTENT` 失败关闭。
- 数据库唯一索引是最终防线，Redis worker lock 不是幂等真源。

### 12.6 Durable quota 围栏

- Redis quota reservation 只是短暂协调；发送前必须在 DeliveryLog 把 `quota_state=committed`、`quota_committed_at` 与 unknown send fence 同事务提交。
- 当日额度计算必须计入 committed 的 confirmed/unknown/closed_unknown/definite_failure/legacy_unclassified，不因 Redis TTL 过期而消失。
- 目标型账号最小间隔和来源群冷却同样按 `send_fence_committed_at` 查询所有 committed outcome；数据库是真源，Redis 只是可修复缓存。
- `released` 只允许在 send fence 前由 `quota_state=reserved` CAS 产生；一旦 committed，任何代码路径都不得转为 released。
- Telegram 已接收、typed 明确拒绝、结果 unknown、人工 closed_unknown、legacy_unclassified、日志 finalize 失败均不得释放。

### 12.7 风险 reservation 恢复任务

新增 `reconcile_ad_risk_reservations_task`，每 5 分钟执行、batch size=100；进程级任务锁固定 `vngrd-ad-risk-reconcile`，每行再按第 9.6 节取得 token advisory lock。任务先无锁读取候选和 Redis marker，再以 `ScheduleState FOR UPDATE → DeliveryLog FOR UPDATE` 重检相同 token/quota/outcome/fence 后 CAS，禁止持 row lock跨 Redis I/O：

- `pending/not_attempted + quota=not_reserved` 但存在同 token reserved marker：这是 Redis成功/DB CAS前崩溃，确认 marker未 committed后原子释放 marker，DB保持 not_reserved并按原 reason重排。
- `pending/not_attempted + quota=reserved` 且 marker与DB冻结digest完整匹配：不再次扣减、不签发authorization，只把同一ScheduleState/slot从orphaned校正为可重试并唤醒dispatcher；实际拿到该slot的当前dispatcher在token lock内调用 `resume_ad_delivery_preauthorization()` 后直达fence。marker缺失、digest冲突或counter无法证明时保持 reserved/paused，reason=`AD_RISK_RESERVATION_ORPHANED`并告警。
- `skipped + quota=released` 如仍有 reserved marker，按同 token幂等释放；无法确认则告警但不得把日志恢复为 pending。
- `send_fence_committed=true + quota=committed`：只允许把同 token marker推进/修复为 committed，并从 DeliveryLog安全 risk字段重建 Redis exact/simhash cache；绝不 decrement或改 outcome。
- 其他组合视为数据损坏，记录稳定安全码并失败关闭；任务本身不调用 Telegram、不解析私链、不改变 creative/slot。

任务 crash/redelivery必须幂等。只有 exact marker状态和 DB CAS均可证明时才自动恢复；无法证明的 orphan保留人工处置，不允许以 TTL到期推断释放。reconciler、Celery消息、数据库和Redis均不得保存/传递 `AdDeliveryRiskAuthorization`；authorization只能由即将执行final fence的当前dispatcher在内存重新签发。

- ScheduleState 使用 `last_reason_code` 保存大写枚举，不按 `last_reason` 文本或大小写前缀判断。
- retry/paused_config/paused_link/paused_security/paused_creative的current DeliveryLog必须保持 `pending/not_attempted`；paused_unknown保持unknown日志和current pointer；terminal_closed_unknown清current但绝不改变旧日志slot/quota；只有cancelled_pre_fence可把not_attempted改为skipped。
- `ACQUISITION_GATE_SYNC_PENDING` 只由 gate mirror reconciler、相同 request_id 补同步或管理员后续变更唤醒，不创建 5 分钟广告 retry；`ACQUISITION_GATE_UNAVAILABLE` 才使用 5 分钟 retry。
- 修改配置成功后，只能按上表精确枚举恢复当前 Campaign 的 paused_config/paused_link/paused_creative；paused_security 需人工确认，paused_unknown 不自动恢复。
- 禁止自动恢复由账号风险、封禁、外部群风控、广告许可或全局安全策略造成的 paused state。
- 资产状态、治理状态或链接恢复事件可以 enqueue 一次去重的 destination recheck，不直接发送。
- retry 时间使用 UTC，加入 10% jitter，避免多 Campaign 同时击穿 Telegram。
- 实现一个集中 `DESTINATION_FAILURE_DISPOSITIONS` 映射；参数化测试断言所有 Resolver/Renderer/Gate/Delivery 枚举恰好有一个 disposition，新增错误码漏配时测试失败。

}
~~~

所有新接口可接受可选 `X-Correlation-ID`，只认可小写 canonical UUIDv4（36 字符）；不合规时忽略原值并用 Python stdlib `uuid.uuid4()` 生成新值，原值不得进入任何日志/DB/响应。响应 header 和 data/error 只返回验证后的同一值。本阶段不引入 ULID 依赖。

所有会持久化的 `reason` 共用 `normalize_admin_reason()`：Unicode NFKC、trim、单行、1–200 字符、拒绝 NUL/控制/bidi 字符；对 Telegram 私链、invite hash、password/token/session/access-hash 等模式先执行 `redact_sensitive_text()` 检测，命中时整请求返回 422 `REQUEST_REASON_CONTAINS_SECRET`，既不保存原文也不保存脱敏副本。普通格式失败返回 422 `REQUEST_REASON_INVALID`。

`AdCampaignCreate`、`AdCampaignUpdate`、DestinationUpdate、Preview、DryRun、Reconcile、InviteReveal、AcquisitionGateUpdate 和 OwnedGroupAdDestinationSettingUpdate 的 Pydantic 模型全部设置 `ConfigDict(extra="forbid")`。因此通用 Campaign PUT 携带任何 `destination_*` 或未知字段时确定返回 422，不会被 Pydantic 静默忽略。

#### 14.1.1 通用 Campaign PUT

现有 `PUT /api/automation/ads/campaigns/{campaign_id}` 对目标型/unbound Campaign的执行字段更新新增必填 `expected_execution_config_revision`；缺失为422 `CAMPAIGN_EXECUTION_REVISION_REQUIRED`，不匹配为409 `CAMPAIGN_EXECUTION_REVISION_CONFLICT`并返回安全current revision。目标字段仍禁止出现在该请求。legacy revision=0路径保持现有客户端兼容，但服务端同样以行锁递增execution revision。

规范化后无执行字段变化时返回200且revision不增、不终结slot；实际变化通常必须在同一maintenance permit和事务内：锁Campaign/Schedule/current Log → 调用finalizer → 更新字段并revision+1 → 写安全审计。若current为unknown/legacy_unclassified或fence竞争获胜，整体409回滚；current为closed_unknown是状态不一致。唯一例外是第6.3节单向安全暂停：仅admin可用，请求必须带 `expected_execution_config_revision,reason,request_id` 且除 `enabled=false,status=paused` 外不得包含其他执行变化；事务不调用finalizer、不改current/log/slot/quota，只禁用Campaign、revision+1并写审计。混合变更返回422 `CAMPAIGN_SAFETY_PAUSE_ONLY`，重新启用/取消/其他变更仍409。响应始终返回当前execution revision。

安全暂停request fingerprint固定为 `SHA256("ad-campaign-safety-pause:v1\\0" + canonical(campaign_id,expected_execution_config_revision,false,"paused",normalized_reason,actor_id))`。锁Campaign后先按 `OwnedGroupAuditEvent(resource_type=ad_campaign_safety_pause,request_id)` 查幂等事件：同fingerprint返回已保存after_state，即使原expected revision现已过期也不重复增revision/审计；同ID异fingerprint返回409 `CAMPAIGN_SAFETY_PAUSE_IDEMPOTENCY_CONFLICT`。首次changed或新request_id的already-paused noop都与Campaign同事务写 `event_type=ad_campaign_safety_pause_changed|ad_campaign_safety_pause_noop`、resource_id=campaign_id、before/after、reason/request/fingerprint；审计失败整体回滚。

### 14.4 启用资格检查

`destination_mode=owned_destination_bound` 的 Campaign update 将 `enabled` 改为 true 时必须：

1. 无锁读取 destination ID/revision。
2. 取得 destination try-lock；不能先锁 Campaign。
3. 短事务锁 Campaign 并复核 revision/status，验证每个 enabled binding 的 creative_id 非空及素材静态规则，然后释放 row lock。
4. 在不持数据库 row lock时执行完整远端 Resolver。
5. 再次短事务锁 Campaign，复核 revision、目标、binding/creative 和 unresolved slot。
6. 通过后原子设为 enabled/active 并写审计。

任一步失败计划保持 disabled，不能部分启用。

只有 `destination_mode=legacy` 的启用继续走现有语义，不新增阶段 4远端校验或非空绑定要求。`owned_destination_unbound` 启用固定返回 409 `OWNED_DESTINATION_UNBOUND`，重绑成功前不得运行。

### 14.6 Dry-run 合同

现有真实运行入口保持异步：

~~~http
POST /api/automation/ads/run
HTTP 202
{"max_deliveries": 20, "dry_run": false}
~~~

202 后端响应保持当前 `_queued_automation_result()` 的完整 superset：除 queued/status/task_name/task_id/payload 外，继续返回数值为 0 的 processed/created/updated/succeeded/skipped/failed、空 errors 以及现有 `details=[{action:"task_queued",...}]`。不得收窄共享 helper 或改变其他 automation endpoint。为避免前端等待 Celery 结果，新增长度受限的同步预演：

~~~http
POST /api/automation/ads/dry-run
HTTP 200
~~~

~~~json
{
  "max_deliveries": 20,
  "verify_destination": false
}
~~~

同步 dry-run：

- 执行候选、现有广告准入、本地目标资格和安全预览。
- 默认不执行私链解密和 Telegram 远端探测；返回 `remote_verification_required=true`。
- 明确传入 admin-only `verify_destination=true` 时仅在 acquisition gate有效 open时可远端只读探测，仍不发送。gate stopped/sync pending/unavailable 时 Telegram RPC固定为 0，detail保留 `remote_verification_required=true` 并返回对应稳定 gate reason。
- Telegram send 调用次数必须为 0。
- 不 claim 真实 quota、不创建 delivery log、不改变 schedule state。
- 返回 details 只能包含 asset ID、link type、reason code、长度和 masked preview。
- dry-run 不写 destination verify正/负缓存、不写任何 Redis key；即使远端验证成功也只存在于本次响应内存。
- 固定调用专用 `evaluate_ad_delivery_read_only()`，禁止复用会写状态的 `_ad_skip_reason()`、`_ad_warmup_skip_reason()`、`_get_or_create_group_ad_profile()` 或会生成素材的 `_choose_delivery_creative()`。
- evaluator 使用 `autoflush=false` 的 read-only transaction；缺少 GroupAdProfile 时只在内存使用默认值，不 insert；Membership 只读快照，不同步；绝不调用 `_maybe_send_ad_interaction()`。
- 素材选择固定调用 `select_existing_creative_read_only()`：只读已有 enabled binding/creative并执行相同静态资格和权重计算，不调用 LLM，不创建 Creative/Binding。若真实链可能生成素材，dry-run 返回 `DRY_RUN_CREATIVE_GENERATION_REQUIRED`，不代替真实生成。
- 两个 dry-run 路径的 LLM、session add/flush/commit、Profile/Membership/Creative/Binding/DeliveryLog/ScheduleState 写入、Redis set/reserve 和 Telegram send spy 次数全部必须为 0。

- `max_deliveries` 上限 100；候选本地计算串行，远端 verify 使用固定并发上限 5、每项 5 秒 monotonic timeout，整个请求固定 30 秒 monotonic deadline。
- deadline 到达时取消尚未完成的 probe并等待其 destination lock/acquisition permit/AccountPool lease释放；未开始或被取消的候选各返回 `DRY_RUN_DEADLINE_EXCEEDED`。HTTP仍为 200 partial result，顶层 `completed=false`、`deadline_exceeded` 为该数量；全部完成时分别为 true/0。
- `processed` 是已经完成本地 evaluator 的候选数，包含远端 deadline item；`eligible` 只计本地和已请求远端验证均通过的项，`skipped` 包含所有 reason非空项，三者口径在同步/异步 dry-run保持一致。
- 现有 `/ads/run` 的 `dry_run=true` 为兼容路径，仍然 202 异步；新前端必须调用 `/ads/dry-run` 获取即时详情。
- 实际发送固定执行完整验证，不接受 `verify_destination` 参数。

前端类型必须拆开，不再让同步详情与异步入队共用 `AutomationRunResult`：

~~~typescript
export interface AutomationTaskEnqueueResult extends AutomationRunResult {
  queued: true
  status: 'queued'
  task_name: string
  task_id: string
  payload: { max_deliveries: number; dry_run: boolean }
}

export interface AdDryRunResult {
  processed: number
  eligible: number
  skipped: number
  completed: boolean
  deadline_exceeded: number
  details: Array<{
    campaign_id: number
    account_id: number
    source_group_id: number
    destination_asset_id: number | null
    link_type: 'public_username' | 'private_invite' | null
    locally_eligible: boolean
    remote_verification_required: boolean
    reason_code: string | null
    rendered_length: number | null
    masked_preview: string | null
  }>
}
~~~

`runAds()` 返回 `AutomationTaskEnqueueResult`（202），该类型保留 `AutomationRunResult` 当前全部必填计数字段和 details；新增 `dryRunAds()` 返回 `AdDryRunResult`（200）。两种响应不可用 union 后靠可选字段猜测。

1. key 固定 `automation.owned_group_ad_destination`；value 固定安全 JSON `{enabled,revision,updated_by_user_id}`。`updated_at` 唯一真源是 `SystemSetting.updated_at` 列，GET/PUT 响应由该列拼装；首次创建用 key 唯一约束 upsert，再 `SELECT FOR UPDATE`，禁止先查无再无保护 insert。
2. 先按第 14 节验证 `request_id`/reason，再计算 `SHA256("owned-group-ad-destination-setting:v1\0" + canonical(enabled,expected_revision,normalized_reason,actor_id))`。
3. 事务内先按 `(resource_type=automation_setting,request_id)` 查 changed/noop 幂等事件：同 fingerprint 返回事件的 after_state，revision 不增加且不新增审计；不同 fingerprint 返回 409 `OWNED_GROUP_AD_DESTINATION_IDEMPOTENCY_CONFLICT`。
4. 然后锁 SystemSetting 行并比较 expected_revision；不一致返回 409 `OWNED_GROUP_AD_DESTINATION_REVISION_CONFLICT`，details 只含 current revision/effective_enabled。
5. 值变化时 revision 精确 +1；同值的新 request_id 是审计型 no-op，revision 不变。两者均写一条 OwnedGroupAuditEvent，与 Setting 在同一事务提交；审计写失败则 Setting 回滚。
6. changed 事件固定 `event_type=owned_group_ad_destination_setting_changed`，no-op 固定 `owned_group_ad_destination_setting_noop`，`resource_type=automation_setting`、`resource_id=null`、`result=success`。before/after 保存 enabled/revision，reason/request ID/fingerprint 使用专用列，correlation_id 使用验证后的 UUIDv4。
7. 两个并发 PUT 使用同一 expected_revision 时最多一个 changed 成功；另一个得到 409。重启后从 DB value 读取，不允许以内存默认覆盖。
8. GET 和 PUT 响应都使用统一 `{code,message,data}` envelope，并回传同一 `X-Correlation-ID`；静态开关永远只读。

### 14.10 既有私链管理接口收口

阶段 4的“普通 API/浏览器无私链”是系统级要求，但保留一个显式、可审计的管理 reveal 例外：

~~~http
GET  /api/owned-groups/{asset_id}/invite-links
POST /api/owned-groups/{asset_id}/invite-links/{link_id}/reveal
~~~

- 列表接口不再解密 private link；private 项返回 `link=null`、`secret_available=true`、link_type/status/time，不返回 fingerprint。
- public link 可继续返回公开 URL。
- reveal admin-only，请求体固定为 `{"current_password":"<SecretStr>","reason":"1-200 chars"}`。它没有 request_id且绝不幂等重放 secret；每次调用都重新二次认证、限流、读取当前 active link并写新审计。将现有 `app.api.auth.verify_password()` 下沉为 `app.core.security.verify_password()`，登录和 reveal 共用，禁止 API router 互相导入；密码字段禁止进入日志、审计和异常。
- reveal 只允许返回指定 active private link；每个 admin 每个 asset 限制 5 次/分钟，成功响应遵守统一 envelope：`{"code":0,"message":"success","data":{"link":"<secret>","revealed_at":"2026-09-11T02:00:00Z"}}`，并设置 `Cache-Control: no-store, private`、`Pragma: no-cache`；不得批量 reveal。
- 二次认证失败统一返回 403 `INVITE_REVEAL_REAUTH_FAILED`；link 非 active 返回 409 `INVITE_REVEAL_NOT_AVAILABLE`；限流返回 429 `INVITE_REVEAL_RATE_LIMITED`。错误响应均不泄漏 URL/ciphertext。
- reveal 限流依赖不可用时失败关闭为 503 `INVITE_REVEAL_UNAVAILABLE`，不得为了可用性绕过二次认证或限流。
- 每次成功、认证失败、不可用和限流都写 `OwnedGroupAuditEvent(event_type=invite_link_reveal,result=success|denied|unavailable|rate_limited)`，只记录 actor/asset/link ID、reason_code、经统一校验的 reason 和验证后 correlation ID，不记录密码、URL、ciphertext 或 fingerprint。
- success线性化顺序固定为：鉴权/限流通过 → 解密到短生命周期SecretStr → 在不含secret的事务中提交success AuditEvent → 事务成功后才组装一次性响应。审计commit失败必须清空buffer并返回503 `INVITE_REVEAL_UNAVAILABLE`，不得返回link；故障注入测试必须证明DB失败时响应、日志和前端均无明文。
- 现有 OwnedGroups 管理页面改用安全列表，并只在 admin 明确点击“显示一次”时调用 reveal；关闭弹窗立即清空内存。
- Automation/GrowthLogs/阶段 4 API 禁止导入或调用 reveal client。
- 旧 observer/operator 的明文读取权限在阶段 4上线时取消；接口契约和前端一起发布，避免兼容窗口泄漏。

## 16. 安全、隐私和可观测性

### 16.1 私链生命周期

允许明文存在的位置仅限：

~~~text
OwnedGroupInviteLink 解密结果
  ├→ ResolvedOwnedGroupDestination._destination_url(SecretStr)
  │   → 确定性渲染的短生命周期 buffer
  │   → Telegram client request
  │   → 立即释放引用
  ├→ P1 owner importer 的 invite_url(SecretStr)
  │   → messages.getChatInviteImporters 单页 RPC
  │   → AccountPool lease释放后立即释放引用
  └→ §14.10 admin 二次认证后的单次 reveal response buffer
      → 弹窗关闭/响应完成后立即释放引用
~~~

`SecretStr` 和 `repr=False` 不是完整安全边界。包含私链的对象必须只提供 `to_safe_log_snapshot()`；显式拒绝/覆盖 `dataclasses.asdict`、Pydantic `model_dump`、通用 JSON encoder、pickle/`__reduce__` 和 Celery 序列化。测试必须直接调用这些通用入口证明不会得到秘密。

禁止进入：

- `AdCampaign`、`AdDeliveryLog`、`OwnedGroupAuditEvent`。
- AccountRiskEvent、exception detail、structlog context。
- Redis value/key、Celery args/result、dead-letter payload。
- Prometheus label、trace span attribute、Sentry breadcrumbs。
- 除 §14.10 单次 admin reveal 响应外的 API JSON；以及任何持久前端 state、浏览器缓存、URL、埋点、截图和导出。

### 16.2 风险相似度缓存改造

当前 `_check_content_policy()` 仍需执行重复内容检测，但阶段 4目标型广告改为可恢复、无秘密的 `risk_content_v1`：

1. 先把所有 `https://t.me/+...`、`t.me/joinchat/...`、`telegram.me/...`、`tg://join?invite=...` 和当前 Resolver URL 替换为固定 `[TELEGRAM_DESTINATION]`，再执行 `redact_sensitive_text()`、Unicode NFKC、casefold、CRLF→LF和连续空白折叠；只在短生命周期内存保留 normalized text。
2. exact fingerprint 固定为 HMAC-SHA256(risk key version, `"owned-group-risk-content-exact:v1\0" + UTF8(normalized)`)，不同私链或公开 username轮换后的相同正文必须得到同值。
3. similarity signature 固定为 SimHash64：对 normalized 的 Unicode字符 3-gram 去重集合，分别用 `"owned-group-risk-content-shingle:v1\0"` 域的 HMAC取前 64 位进行标准 signed-bit投票；tie bit=0，最终按 PostgreSQL signed BIGINT two-complement保存。短于 3 字符时以完整 normalized 作为一个 shingle。
4. 同一 canonical source群最近 3 天最多 50 条 committed signature 按 `send_fence_committed_at DESC,id DESC` 比较，Hamming distance `<=5` 等价触发 `AD_RISK_CONTENT_DUPLICATE`；account exact窗口 6 小时、source exact窗口 3 天。查询和 Redis索引使用相同排序/窗口。
5. `risk_content_fingerprint/key_version/simhash/algorithm_version=1` 随 DeliveryLog fence同事务提交，是 DB 真源。Redis只缓存 committed 安全指纹/签名，不缓存 normalized正文；丢失时由 DB重建。preauthorization只读评估，fence前失败不留下假“已发送”内容记录。
6. key轮换时查询所有仍保留 risk key version并对当前 normalized分别计算；相似度只在相同 algorithm version下比较。旧 key覆盖窗口结束后才可删除。
7. 单元/集成测试读取 DeliveryLog、AccountRiskEvent和真实 Redis key/value，断言 bearer secret、完整私链及 normalized正文均不存在，同时验证换链仍命中 exact/similar。

不得为了避免泄漏关闭内容去重或风险判断；DB查询失败或必要 key不可用时预授权失败关闭为 `AD_RISK_PREAUTH_UNAVAILABLE`。

consumer fence与effect fence分层：handler execution claim、DB-only业务写、observation/fact、prepared outbox创建及cursor推进必须位于当前consumer lease/fence内；prepared一旦随有效consumer事务commit，恢复权即转交给outbox。dispatcher此后只按outbox自己的lease、不可变effect_fence_token及execution→outbox行CAS执行，不依赖已过期的旧cursor lease，也不得创建新业务行/新effect。dispatcher可以按全部child终态CAS完成execution，但不能推进cursor；新consumer取得新fence后观察execution终态，再以自己的cursor CAS推进。consumer锁序固定cursor→execution→outbox，dispatcher固定execution→outbox且不得反向等待cursor。

`recover_guardian_side_effect_outbox_task` 每分钟处理lease过期的in_flight：具有经inventory声明并测试的远端原生幂等键时，可在29天claim保护线前用同一effect/idempotency/risk reservation重领；Telegram/XBoard或任何无原生幂等证明的操作立即转unknown、令execution completed_with_unknown并清密文，绝不自动重发。dispatcher/recovery只有在所有child终态后才CAS execution；cursor仍由当前consumer fence推进。

外部适配器若有原生 idempotency key，固定使用 `{remote_bot_user_id}:{update_id}:{handler_name}:{subject_ordinal}:{effect_name}:{effect_ordinal}` 并可安全重试；Telegram无通用幂等键的写操作在RPC前提交 in_flight fence，响应丢失转 unknown且不自动重发。只有所有 execution达到 completed/completed_with_unknown或明确skipped，cursor才可前进；pending/blocked不得前进。

side-effect payload使用独立Guardian outbox AES-256-GCM keyring。envelope同样固定 `version(1 byte)|key_version(2 bytes big-endian)|nonce(12 bytes)|ciphertext|tag(16 bytes)`，每次加密随机96-bit nonce且不得复用；AAD固定 UTF-8 `vanguard:guardian-handler-outbox:v1\0{handler_execution_id}\0{subject_ordinal}\0{effect_name}\0{effect_ordinal}\0{effect_fence_token}`。plaintext是按operation allowlist的canonical JSON，最大16KiB；非恢复必需字段不得进入。

dispatcher必须先在内存解密/认证并冻结payload，再提交in_flight/send fence，随后只消费该内存对象一次。密钥缺失或GCM认证失败发生在fence前时，outbox变cancelled、handler变blocked、cursor不前进且coverage blocked；不得伪造unknown或调用外部系统。RPC fence后崩溃/响应丢失才写unknown/completed_with_unknown并允许cursor前进。

Guardian outbound `send_message/send_photo/send_document` 必须增加P1专用 `GuardianEffectRiskAuthorization` 合同：prepared创建时令 `risk_reservation_id=SHA256("guardian-effect-risk:v1\\0" + effect_fence_token)`、`risk_quota_state=not_reserved`；不受AccountRiskGuard写预算约束的delete/restrict/ban等固定为not_required。dispatcher解密后先读DB state：not_reserved调用 `preauthorize_guardian_effect()`，沿用现有 `BOT_MESSAGE` 内容/账号/群风险规则但只用安全target/payload/settings摘要，并以risk_reservation_id执行Redis Lua幂等reserve，随后DB CAS reserved并冻结三项digest/risk_preauthorized_at；reserved且marker/digest完整匹配则由当前dispatcher调用 `resume_guardian_effect_risk_authorization()`重新签发一次性内存对象，CAS影响0行但状态精确匹配视为幂等成功，不release、不重复计数。send fence事务必须把reserved→committed与outbox prepared→in_flight原子提交，再调用 `send_guardian_effect_preauthorized(authorization)`；该adapter验证bot/target/payload/settings digest且严禁再次进入现有通用 `BOT_MESSAGE` reserve路径。P1关闭时未接管的旧handler路径保持原行为。

Redis成功而DB CAS失败/commit结果未知时必须在risk token lock内重读：精确reserved匹配继续，只有DB仍not_reserved或已cancelled才释放；确认释放后回not_reserved并可按retry_at重试，无法证明释放则orphaned、handler/cursor blocked且不发送。DB为reserved而marker缺失/不一致时同样orphaned，禁止盲目再扣；DB为committed时marker过期只能由reconciler按同token恢复cache而不得增加预算。Guardian effect risk reconciler只修复marker/唤醒原outbox，绝不签发或传递内存authorization。AccountRiskGuard的当日判定必须把这些DB committed outbox作为durable真源并按risk_reservation_id去重，跨worker/重启/Redis flush均只能扣一次。该桥只复用Guardian自身风险设置，绝不读取 `AdCampaign`、`auto_ads_enabled`、广告额度/冷却/时段或阶段4外部投放设置。

completed/cancelled/unknown终态在同一事务把 `payload_ciphertext/payload_key_version` 置null，仅保留安全remote fingerprint/error code；prepared/in_flight密文不得被普通清理删除。key轮换时新行只用active key，后台只可在row lock下重加密prepared行；in_flight禁止重加密。旧key只有在该version密文计数为0后才可删除，否则启动/设置更新失败关闭。API、日志、DLQ和秘密扫描覆盖envelope及解密异常。P1不实现handler execution/outbox安全元数据的自动硬删除；terminal行作为幂等tombstone永久保留，30天PII任务只销毁密文和原始user ID。

payload运营SLA固定：外部RPC timeout不得超过60秒，outbox claim lease不得超过5分钟且不得越过payload_expires_at。创建满24小时仍prepared/in_flight时，以effect_fence_token为告警dedupe key告警；失败每小时重试，同一事件成功后最多每24小时重复一次。普通dispatcher不得claim `payload_expires_at <= now+1天`、handler blocked或cursor poison-blocked的prepared行。

`expire_guardian_side_effect_payloads_task` 每小时持独立task lock扫描：距expiry不足1天的prepared行立即cancelled、清密文并把handler/cursor标blocked；其中risk reserved先按risk token锁尝试release，确认后写released，无法证明则保守写orphaned并提交告警，但都不得保留业务payload。距expiry不足1天且lease已过期的in_flight行固定转unknown、清密文并把handler/cursor标blocked，risk保持committed，绝不自动重发或推进cursor；仍有有效lease时最多等待其5分钟边界后由下一轮处理。admin只能走skip-update并对unknown显式 `acknowledge_unknown=true`。29天保护窗保证正常调度在created_at+30天前清空所有payload ciphertext/key version；任何到期密文、expiry task滞后或时钟异常触发P0级告警并令P1 consumer/dispatcher fail-closed，不得为推进cursor延长expiry。

`_run_guardian_bot_cycle()` 必须按下列固定 `handler_name` 拆分；新增分支必须先更新此 inventory、数据库约束和故障注入测试：

| handler_name | 触发/现有入口 | 必须保护的副作用 | 固定策略 |
| --- | --- | --- | --- |
| `group_sync` | 所有可提取 chat 的 update / `_sync_guardian_group_from_chat` | Group、ManagedGroupBinding、默认策略、Asset治理状态、AuditEvent | DB-only同execution事务；AuditEvent使用source_event_key去重 |
| `private_coupon_claim` | 私聊 `/start` | User、CouponDistribution、Sub2API/XBoard奖励、Bot回复 | 复用Coupon unique/Sub2API idempotency；XBoard和send_message走outbox |
| `member_verification` | `new_chat_members` | VerificationSession/captcha状态 | `source_event_key` unique；captcha发送走outbox |
| `member_campaign` | `new_chat_members` | Tracking/Execution/Reward/Broadcast及外部奖励 | DB source_event_key；外部奖励/广播走outbox |
| `member_welcome` | `new_chat_members` | welcome/captcha message | 稳定effect ordinal；send_message围栏 |
| `moderation_db` | message/edited_message text/caption | Violation及惩罚决策 | Violation.source_event_key unique并与execution同事务 |
| `moderation_action` | 违规决策 | delete/restrict/ban/unban/kick | 每个动作独立稳定ordinal；Telegram fence，禁止重放WARN造成二次delete |
| `moderation_warning` | WARN/处罚提示 | Bot warning message | send_message fence；RiskGuard reservation由effect key派生且只扣一次 |
| `join_attribution` | chat_member join/leave | observation/fact epoch | 与cursor CAS同事务并使用event_key unique |

P1 `054/040` 同时向 VerificationSession、Violation、CampaignExecution、CampaignTracking 和 OwnedGroupAuditEvent 增加 nullable `source_event_key VARCHAR(255)` 与唯一部分索引；新 durable consumer产生的对应写必须非空，历史可空。单主体格式固定 `guardian:v1:{remote_bot_user_id}:{update_id}:{handler_name}:0`；一个 update包含多名成员时，先按远端 user ID无符号升序、再以原 payload位置打破重复值，生成从0开始的稳定 `subject_ordinal`，同一主体的业务行source_event_key与所有outbox必须共用该ordinal且绝不写user ID。一个主体的同名多项外部动作再用 `effect_ordinal` 从0稳定编号；不同subject可以各自从0开始。handler execution仍是每update/handler一行；不得把 subject ordinal和effect ordinal混用。

outbox operation至少枚举 `send_message/send_photo/send_document/delete_message/restrict/ban/unban/kick/sub2api_coupon/xboard_coupon/campaign_broadcast`。Sub2API复用现有原生幂等键；XBoard及Telegram send响应丢失固定unknown且不自动重发。所有Guardian出站内容必须走第17.3节 `GuardianEffectRiskAuthorization` + preauthorized adapter；只传reservation ID但继续调用现有会再次reserve的通用 `BOT_MESSAGE` 路径视为实现失败。

Guardian Bot 必须是目标群管理员并显式订阅 chat_member。Bot API 返回的 `ChatInviteLink` 若由其他管理员创建可能只有掩码；只有完整 URL 在内存按所有保留 key version HMAC 后精确命中本系统链接时才用于候选，否则立即丢弃 URL并记 destination_only。link-level 归因的主要可靠来源是 owner user session importer。

### 17.4 P1 保守算法

P1 固定常量：`ATTRIBUTION_WINDOW_DAYS=7`、`JOIN_PROVIDER_MERGE_TOLERANCE_SECONDS=120`、`ATTRIBUTION_RAW_USER_RETENTION_DAYS=30`、`ATTRIBUTION_KEY_RETENTION_DAYS=37`。配置修改需另起 migration/version，不允许环境间静默漂移。

1. 由第 17.3.1 节唯一 poller durable 地读取 `chat_member`；确认 old 非成员→new 成员后，在 observation、canonical fact 与全 feed cursor 的同一事务中以 `botapi:v1:{remote_bot_user_id}:{update_id}` 幂等插入。
2. 通过 Telegram Chat ID 精确解析 OwnedGroupAsset。
3. 若事件携带可用 invite link，只在内存规范化；对保留窗口内的各 fingerprint key version 计算候选 HMAC，以 `(version,fingerprint)` 匹配 DeliveryLog，并保存唯一命中的 version/digest。原始 URL 不落库、不进入 cursor。
4. 查加入前 `ATTRIBUTION_WINDOW_DAYS` 内 destination/fingerprint相同、outcome=confirmed 的 delivery logs。
5. 候选只对应一个 campaign/account/source group 组合：`modeled_single_candidate`；仅当该组合下恰好只有一条 DeliveryLog 时写 `matched_delivery_log_id`。同一组合有多条日志时该字段必须为 null，绝不任选一条。
6. 多个组合：`ambiguous`，matched delivery 为空。
7. 公共 username、无 invite 元数据，或链接由其他管理员创建且无法匹配本系统仍处于保留/归因资格窗口的链接：`destination_only`；不得保存或展示该管理员的原始链接。
8. 无相关投放：`unattributed`。
9. 不允许仅按“时间最接近”选择一条。
10. 归因 upsert 成功后才推进唯一 durable cursor；重放不产生重复 observation 或 fact 统计。
11. reducer拿到原始Telegram user ID后只在内存按所有retained PII key version计算fingerprint，并为每个 `(asset_id,key_version,fingerprint)` 派生 `vngrd-join-reducer` 64-bit advisory key；去重后按无符号数升序取得全部锁，结束后逆序释放。轮换必须先把新旧key全集部署到所有worker再切active，确保旧/新进程锁集合一致；禁止只锁active fingerprint。随后查所有版本下同用户在 ±`JOIN_PROVIDER_MERGE_TOLERANCE_SECONDS`、期间无Bot leave transition的open fact：唯一命中则合并 evidence；无命中则以首次 observation 时间生成 `SHA256("join-fact:v1\0" + asset_id + user_key_version + user_fingerprint + joined_at_epoch_microseconds)` 新建fact；多命中不猜，写 `join_attribution_id=NULL,merge_status=conflict` observation并告警。
12. Bot 与 importer 命中同一 fact 时 importer 只补强 invite fingerprint/method，不新增 join；两个非空 fingerprint 冲突时 fact 降为 ambiguous 且不覆盖旧证据。Bot leave 关闭当前 epoch；随后 rejoin 必须新建 fact。
13. `dispatch_join_attribution_recompute_outbox_task` 每分钟按第17.3节状态机领取outbox，并在同一claimed worker内调用纯 `recompute_join_attribution_candidates(delivery_log_id)`；扫描该destination/fingerprint且joined_at位于 `[send_fence_committed_at,send_fence_committed_at+ATTRIBUTION_WINDOW_DAYS]` 的fact，按相同全版本锁和规则重算候选，以attribution revision CAS更新，成功才以同一lease token标completed。另有每小时durable sweep补建遗漏的eligible confirmed outbox；唯一delivery_log约束和永久completed tombstone保证不重复行。人工confirmed后不得让既有fact永久停留在旧unattributed/ambiguous；重算仍禁止时间最近猜测。

owner importer reconciliation 固定协议：

1. importer任务每6小时扫描一次，每个 link cycle 每页 `limit=100`、单次 RPC timeout=30秒、单次task最多100页；达到页数上限保留cursor并立即排下一task，不标 completed。任务首先在短事务 claim `consumer_key=importer:v1:{asset_id}:{invite_link_id}`：仅 lease为空/过期且 `retry_at IS NULL OR retry_at<=now` 时，写 owner instance/canonical UUIDv4 lease token、`lease_expires_at=now+120s`、fencing_token+1并CAS当前row revision。claim事务提交后才允许等待 destination lock/account；每30秒heartbeat，任何持久化都须以 consumer key+lease token+fencing token CAS。claim/heartbeat/释放可改变当前revision/fencing_token/lease列，但绝不能改已有cipher-bound revision/fence。
2. 在有效consumer lease下按第12.2节取得destination link lock，锁内重读asset/link并解密 `OwnedGroupInviteLink` 到局部 `SecretStr invite_url`；随后使用 `OwnedGroupAsset.owner_account_id` 对应且仍是该群管理员的用户账号session单个AccountPool lease调用 `messages.getChatInviteImporters(peer=canonical destination peer,link=invite_url,requested=false,limit=100,...)`。该MTProto方法仅用户账号可用；不得使用Guardian Bot/Growth账号替代，不得持数据库row lock跨RPC。owner非管理员/权限不足固定标coverage blocked；`requested=true`待审批请求绝不能计作已入群。
3. 正常返回后先释放 owner AccountPool lease；仍在 destination lock内以短事务处理本页：再次验证 consumer lease/fence和link identity，对每个 importer计算独立PII HMAC、按observation event_key幂等upsert并运行跨provider reducer，然后以同一 lease/fence CAS写加密cursor；该事务先确定new row revision，再把它和当前fencing token分别冻结到 `cursor_cipher_revision/cursor_cipher_fencing_token`。任一 observation/fact/cursor失败整页回滚，下一次重读同页。事务提交后释放destination lock、清空SecretStr引用，再以CAS释放consumer lease。
4. 查询 active链接及 attribution window内已revoked链接；链接行统一至少保留到 `max(revoked_at+37天, final_completed_at)`，被任何observation/fact引用、未完成final checkpoint或仍在保留期时禁止硬删。
5. 每个 reconciliation cycle key固定为 `importer:v1:{asset_id}:{invite_link_id}:{invite_created_at_utc_microseconds}:{cycle_started_at_utc_microseconds}`。安全cursor_json只存cycle key/page count。cursor plaintext固定canonical JSON `{offset_date_unix_seconds,offset_user_id_decimal,offset_user_access_hash_decimal}`；使用独立 `VANGUARD_ATTRIBUTION_CURSOR_ENCRYPTION_KEYS` 的AES-256-GCM，每次写随机96-bit nonce且同key绝不复用。cipher envelope固定 `version(1 byte)|key_version(2 bytes big-endian)|nonce(12 bytes)|ciphertext|tag(16 bytes)`；AAD固定 UTF-8 `vanguard:join-cursor:v1\0{consumer_key}\0{cursor_cipher_revision}\0{cursor_cipher_fencing_token}\0{cycle_key}`。解密必须读取密文同写事务冻结的两列，不得代入cursor行的当前revision/fencing_token。
6. cursor ciphertext、access hash和明文offset user不返回API、不写日志/Celery/错误；cursor默认24小时到期。到期、key不可用或GCM认证失败时，用当前lease/fence CAS把ciphertext/key version/cipher revision/cipher fencing token/expires_at五列全清、标 `degraded_gap`并从第一页重扫，依靠observation event_key幂等，禁止猜造offset_user。
7. FloodWait或其他RPC错误时，先释放AccountPool lease、destination lock并清空SecretStr；绝不能在任何外部锁/lease下sleep。随后以当前consumer lease/fence短事务写 `retry_at=now+server_wait`（其他错误指数退避，1分钟起、最多1小时）、保留cursor且清空consumer lease字段；CAS失败不再写。正常页也不在锁内sleep。
8. 最终空页只在 observation/fact和cursor同一事务成功时写 `completed_at/last_success_at`、清除offset ciphertext/key version/cipher-bound revision/fence/expires_at及retry_at，才标记本cycle完成；transaction必须带lease/fence CAS，失败整页回滚。每页结束释放consumer lease，下一页重新claim并按密文冻结AAD续页；多worker不能并发抓同一页。
9. active链接及 `revoked_at + ATTRIBUTION_WINDOW_DAYS` 尚未到期的链接都要跑cycle。revoked链接只有完成最后一个覆盖到window截止点的空页cycle才停止；Telegram对revoked link返回不可查询时标记coverage blocked并告警，绝不能伪造completed。
10. 新cycle读取同一链接历史importer时，必须用所有仍保留的PII key version查重；不得因密钥轮换重复计数。

若业务以后要求精确到 Campaign/来源群，必须另做“每 Campaign/来源专属邀请链接”或 Vanguard 跟踪重定向；这会改变当前每资产单 active 私链约束，需独立立项。

### 17.5 隐私和保留期

- PII 指纹固定为 `HMAC-SHA256(VANGUARD_ATTRIBUTION_PSEUDONYM_KEYS[version], "owned-group-attribution-user:v1\0" + decimal_telegram_user_id)`；importer event_key 只含 version + fingerprint等安全身份，Bot event_key 只含 remote bot ID/update ID，二者都不含原始 user ID。
- `purge_join_attribution_pii_task` 每6小时以1000行batch、`FOR UPDATE SKIP LOCKED`处理 `joined_at < now-30天` 的fact，先确认所有当前retained key alias完整，再把 `telegram_user_id` 置null；同一任务清除过期24小时的importer ciphertext。清理后运行秘密扫描，确认observation event_key、cursor metadata、audit/error/outbox payload均不含原始十进制user ID。
- `backfill_join_identity_aliases_task` 在新active PII key启用前，对仍有原始user ID的fact计算新version alias并做完整性/冲突报告；同asset同alias指向时间不重叠的顺序membership epochs是合法结果。只有同一fact/version不同fingerprint、重叠open epochs或在merge tolerance内无法唯一选择时才停止切换并告警，不自动merge。
- 旧PII key至少保留37天，并继续保留到所有open fact都已有新active key alias、所有只依赖旧key且仍在importer重扫/merge窗口的记录到期。删除key前执行dry-run断言；不满足时阻止删除。已经匿名化且超出匹配窗口的closed fact不再参与importer重扫。
- 聚合统计可长期保留，但不含可逆用户标识。
- 普通 placement 日志不新增用户维度。
- 导出和用户明细权限另行评审；P1 默认只提供聚合。

### 17.6 P1 独立开关与启用闸门

静态 `OWNED_GROUP_JOIN_ATTRIBUTION_ENABLED=false` 与 `SystemSetting.key=automation.owned_group_join_attribution` 的 value `{"enabled":false,"revision":0}` 同时为true才启用。它与 P0 `automation.owned_group_ad_destination` 独立：关闭P1只停止新归因observation/importer，不得停止外部广告、修改placement日志或影响阶段2/3内部消息；关闭期间cursor写 `coverage_status=degraded_gap/gap_started_at`，Guardian其他handler照常执行并推进全feed cursor。

admin通过 `GET/PUT /api/settings/owned-group-join-attribution` 查看/修改，PUT固定 `{enabled,expected_revision,reason,request_id}`，沿用UUIDv4、reason、CAS、审计和 `extra=forbid` 合同。启用前必须同时通过：`054/040` schema head；PII/cursor/outbox AES keyring有效；唯一remote bot consumer无冲突；全部handler inventory幂等检查通过；至少一个asset具备Guardian chat_member权限或owner importer能力。未通过返回409稳定reason且保持关闭，绝不能降级为“精确归因”。

### 17.7 P1 聚合 API 与前端

新增：

~~~http
GET /api/automation/ads/join-attribution/summary?asset_id=&campaign_id=&from=&to=
GET /api/automation/ads/join-attribution/coverage?asset_id=
GET /api/automation/ads/join-attribution/cursors
POST /api/automation/ads/join-attribution/cursors/{consumer_key}/skip-update
~~~

P1稳定错误码至少固定：`ATTRIBUTION_P1_NOT_READY`、`ATTRIBUTION_CONSUMER_BLOCKED`、`ATTRIBUTION_CURSOR_REVISION_CONFLICT`、`ATTRIBUTION_CURSOR_CIPHER_INVALID`、`ATTRIBUTION_EFFECT_IN_FLIGHT`、`ATTRIBUTION_EFFECT_UNKNOWN_ACK_REQUIRED`、`ATTRIBUTION_EFFECT_PAYLOAD_EXPIRED`、`GUARDIAN_EFFECT_RISK_ORPHANED`。错误details只返回安全consumer/outbox内部ID、current revision和reason code，不返回user fingerprint、ciphertext、payload或远端token。

- summary只返回聚合：`destination_only/modeled_single_candidate/ambiguous/unattributed` fact数、confirmed placement数、coverage status、window和 `attribution_capability=invite_link_modeled`；不返回user ID/fingerprint/observation/cursor ciphertext，不命名为exact conversion。时间范围默认7天、最大90天。

- 前端在增长中心广告页增加“入群归因（试验）”，展示覆盖率、modeled/ambiguous/unattributed及coverage gap；不显示CTR、精确转化率、用户明细或来源断言。P1设置不得出现在自建群内部消息页。

### 17.8 P1 调度、恢复与告警

- importer scheduler、PII purge、alias backfill、recompute outbox dispatcher/sweep、side-effect outbox dispatcher/expiry、Guardian effect risk reconciler必须各有独立task lock；consumer业务写以cursor lease/fencing为并发边界，已commit的side-effect/recompute outbox分别以自身lease/fence为恢复边界。
- 告警：Bot `last_success_at>20h`、importer连续3个cycle blocked、cipher认证失败、remote bot 409、handler poison、alias冲突、recompute连续20次失败、side-effect满24小时未终结、risk orphaned或任一outbox unknown立即显示coverage degraded；不得修改P0 delivery outcome。
- Worker启动只恢复到期lease/outbox，不跳过pending handler、不伪造cursor completed。P1关闭后不claim新importer/attribution handler，但仍允许安全终结已提交的side-effect fence。
- P1 enable gate必须确认：`054/040` schema等价、三套keyring可读、唯一Guardian consumer、handler inventory全覆盖、cursor无未解释gap、recompute/side-effect dispatcher与expiry/reconciler存活；任一不满足保持false并返回稳定blocked reason。

- **P4-P1-027**：revoked link 完成覆盖归因窗口的最后空页后才停止；查询失败标 blocked，未 final checkpoint 或未过保留期不可硬删。

- **P4-P1-029**：FloodWait/RPC失败先释放AccountPool lease、destination lock和SecretStr，再CAS写retry_at/释放consumer lease；测试期间无锁内sleep。
- **P4-P1-030**：AES-256-GCM envelope、96-bit随机nonce和cipher-bound revision/fence严格匹配；页1释放→新fence重领及同lease heartbeat后仍能用冻结字段解密页2。篡改cipher/tag/AAD或缺key标degraded并从首页幂等重扫，明文offset/access hash零泄漏。

- **P4-P1-035**：新PII key切换前alias backfill完成；同fingerprint顺序epoch允许切换，重叠open epoch/同fact-version冲突阻止切换，open fact无新alias时阻止删除旧key。

- **P4-P1-038**：Guardian outbox envelope/随机nonce/AAD fence token可校验；篡改或缺key在RPC前cancelled+handler blocked且cursor不前进，外部调用为0。
- **P4-P1-039**：outbox completed/cancelled/unknown同事务清ciphertext；prepared重加密可恢复，in_flight不重加密，仍有旧version密文时阻止删key。
- **P4-P1-040**：owner importer使用仍为目标群管理员的用户session；Bot/Growth账号、非管理员和权限不足均不调用importer并标coverage blocked。
- **P4-P1-041**：DeliveryLog首次confirmed和人工unknown→confirmed都与唯一pending recompute outbox同事务；outbox插入失败时confirmed finalize回滚，不直接publish。
- **P4-P1-042**：两个recompute dispatcher、processing lease过期和stale token故障注入最终仅一个CAS生效；failed按1分钟至1小时重试，completed tombstone不被清理或sweep重建。
- **P4-P1-043**：prepared effect提交后原consumer强杀、新consumer fence+1；dispatcher仍按原effect fence只执行一次，旧consumer不能新增副作用，cursor仅由新consumer在全部execution终态后推进。
- **P4-P1-044**：side-effect满24小时告警可去重重试；距expiry不足1天的prepared不再claim并cancelled，过期lease的in_flight转unknown；两者均在30天前清密文、阻塞cursor且不会自动重发。
- **P4-P1-045**：Guardian出站消息的risk reservation跨worker/restart只扣一次；Redis成功后DB失败可释放，marker丢失进入orphaned且RPC为0，committed marker恢复不增预算；preauthorized adapter不会二次调用BOT_MESSAGE reserve。
- **P4-P1-046**：`054/040` SQL/Alembic对全部七张P1表、五类source_event_key、CHECK/FK/claim/expiry索引及默认false setting产生等价schema；有lease/in_flight/processing时downgrade失败关闭。
- **P4-P1-047**：P1关闭、cursor/outbox/risk依赖故障和payload expiry均不改变阶段2/3自建群内部消息语义，也不使其读取增长中心Campaign、广告额度/冷却/时段或阶段4外部投放设置。
- **P4-P1-048**：side-effect prepared lease过期可由单一新token恢复；无原生幂等的Telegram/XBoard在in_flight lease过期后只转unknown、不重发，有原生幂等的effect仅以完全相同远端key/risk reservation恢复，stale worker均无法覆盖终态。
- **P4-P1-049**：Guardian effect在risk reserved提交后、send fence前强杀，重启dispatcher按原risk reservation/digest恢复一次性authorization且预算只扣一次；CAS 0的精确reserved匹配不触发release，reconciler不保存/传递authorization。

## 25. 【历史作废】原固定决策与禁止项

以下内容仅记录原方案曾作出的设计选择；阶段 4 已取消，开发者不得据此实施：

1. destination 绑定在 Campaign，不绑定在 AccountAdBinding 或 Creative。
2. `target_group_ids` 永远是外部投放群；destination 永远是承接自建群。
3. destination=null 的旧计划保持原行为。
4. 目标型计划绝不回退 `creative.link_url`。
5. 公开用户名有效时优先于私链。
6. username 网络错误/身份不一致时失败关闭；只有明确不存在才尝试私链。
7. 阶段 4 Automation/GrowthLogs 前端永不读取私链；唯一例外是 OwnedGroups 管理页经 admin 二次认证后的单次 reveal，且禁止持久化。
8. CTA 由确定性代码生成，LLM/Persona 不参与。
9. 同一素材可被不同目标计划共享，不修改素材本身。
10. 使用有效治理服务结果，不只看 `asset.governance_status`。
11. destination link lock 与内部消息 chat lock 使用不同 namespace。
12. unknown 只能经证据确认成功或人工关闭为 closed_unknown；两者均不释放额度、不自动重发。
13. 有投放历史的 Campaign 不硬删除。
14. `acquisition_stop` 只覆盖第 10.2.2 节冻结的获客动作；不覆盖该节明确排除的外部暖场、关键词回复、私聊 CRM，也不覆盖自建群内部消息。
15. 阶段 4开关只控制目标型计划，legacy 计划不受其影响。
16. 增长中心广告配置继续约束外部广告，但不得约束自建群内部消息。
17. P0 只宣称 placement attribution，不宣称 click/join exact attribution。
18. 轮换不编辑历史外部广告，界面明确提示旧链接可能失效。
19. source/destination 任何 ID 冲突都阻止，不尝试“智能修复”。
20. 迁移、功能开关和日志设计必须支持先部署、默认关闭、灰度开启和保留数据回滚。
21. P0 对私有承接群只接受 join-request invite；member-invite 不得用于外部公开投放。
22. Redis reservation 只负责短期协调；实际发送前必须持久提交 quota consumption，TTL 不能重新产生额度。
23. 目标型绑定必须显式绑定本 Campaign 的有效 Creative，绝不调用全局素材 fallback。
24. Telegram群身份、锁、source=destination和目标型业务槽只使用已验证的 `source_canonical_telegram_chat_id` sidecar；既有raw列保持原义且不原地改写，禁止按正负猜类型。
25. retry/paused 的 pre-fence 失败保留同一 pending log/slot；skipped 是不可自动恢复的当前槽终结态。
26. 目标型发送固定 `plain_text_v1 + parse_mode=None`；媒体 unknown 不允许仅凭 caption 确认为成功。
27. 账号间隔、群冷却和日额度在 fence 时即按 `send_fence_committed_at` 占用，不能等 success/sent_at。
28. acquisition stop 只有在 exclusive permit 排空后才返回 200；超时保持 stopped并返回明确 503。
29. dry-run 禁止调用任何 mutating helper、LLM、Redis write 或 Telegram send。
30. request_id 和 correlation ID 统一使用 canonical UUIDv4；本阶段不引入 ULID。
31. 同一account+Campaign的多素材由多条binding组成；dispatcher按二元组只调度一次，reservation同时冻结selected binding与creative。
32. 目标型risk target和Telegram RPC recipient始终是外部来源群；destination owned group只作为CTA去向。
