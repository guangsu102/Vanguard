## 1. 本阶段结论

阶段 5 交付“一个群、一张运营详情、三类成员、统一入口”，但不重写阶段 1–3 已有业务页面和执行链。

必须交付：

1. 增加一张轻量的群成员观察事实表，记录 Guardian 已看到的入群、发言和退群事实。
2. 后端统一推导三种业务成员身份：`real_user`、`system_ad_account`、`system_bot`。
3. 增加两个只读聚合接口：运营中心摘要、成员分页列表。
4. 增加自建群运营详情页，统一展示能力状态、成员、任务和审计入口。
5. 从详情页跳转到既有自建群编排、Guardian 治理、群内消息、Persona、公告与活动页面。
6. 调整侧边栏信息架构，保留全部旧路径和书签兼容性。
7. 页面必须明确标注真实用户数据是“Guardian 已观察数据”，不是 Telegram 全量、实时成员名单。

本阶段不把 `member_kind` 落库。成员类别必须由服务端读模型实时推导，以免账号模式、Bot 绑定或身份信息变化后形成脏数据。

本阶段不能只用现表拼出一个名为“群成员”的页面。当前 `User` 没有群维度，Guardian 的退群处理也没有成员事实落库；若不增加最小观察表，“真实用户当前成员”会成为另一个伪需求。

## 2. 当前代码基线与事实边界

### 2.1 可直接复用的能力

| 能力 | 当前实现 | 阶段 5 用法 |
| --- | --- | --- |
| 自建群资产 | `OwnedGroupAsset`、`/api/owned-groups`、`OwnedGroups.vue` | 继续作为资产主数据和资产列表 |
| 系统编排成员 | `OwnedGroupMembership` | 作为系统账号、Owned Bot 的主要群关系事实 |
| 核心群账号关系 | `GroupAccountMembership` | 只作为系统推广账号群关系的补充证据 |
| Guardian 绑定 | `ManagedGroupBinding`、`GuardianBotProfile` | 识别当前主 Guardian Bot、治理状态和 Bot 角色 |
| Owned Bot | `OwnedBotProfile` | 解析 Bot 账号、父账号和 Telegram Bot 身份 |
| 全局用户 | `User` | 补充已观察真实用户的用户名、生命周期和全局风控摘要 |
| 群内消息 | `/api/owned-groups/{assetId}/messages/*`、`OwnedGroupMessaging.vue` | 只做能力摘要和深链，不复制消息工作区 |
| Persona | `/api/accounts/{accountId}/ai-persona`、`AccountPersonaDrawer` | 从系统账号成员行跳转既有账号页 |
| Guardian 策略 | `/api/group-governance/*`、`GroupGovernancePolicies.vue` | 通过 Telegram Chat ID 深链 |
| 公告与活动 | `ManagedGroups.vue`、`Campaigns.vue` | 复用现有公告/置顶和活动配置 |
| 操作与审计 | 自建群 operation API、`/api/owned-groups/audit-events` | 详情页内展示，不新建审计数据模型 |

### 2.2 三个容易误读的现有字段

1. `OwnedGroupMembership.resource_type=user` 的 `resource_id` 是 `TelegramAccount.id`，不是自然用户 `User.id`。
2. `OwnedGroupMembership.resource_type=bot` 的 `resource_id` 是 `OwnedBotProfile.id`，不是 `TelegramAccount.id`。
3. `OwnedGroupAsset.member_count` 只统计已核验的系统编排资源，不是 Telegram 群总人数。

前端统一只使用以下两个可信名称：

| 字段 | UI 名称 | 含义 |
| --- | --- | --- |
| `managed_resource_count` | 已核验编排成员 | 来自 `OwnedGroupAsset.member_count` |
| `observed_real_user_count` | 已观察真实用户 | 来自阶段 5 观察表去重计数 |

不得用两者相减计算“未分类人数”。`Group.member_count` 没有独立、可信的采集时间，且历史接入流程可能复制资产计数；阶段 5 API 和页面均不返回或展示 Telegram 人数快照。

### 2.3 当前缺口

- `User` 是全局用户，没有 `group_asset_id` 或群成员状态。
- `VerificationSession` 只证明用户曾进入验证流程；没有验证记录不能证明用户从未入群。
- `Violation` 只证明历史治理事件；不能证明当前仍在群。
- Guardian 的 `handle_member_leave` 当前只写日志。
- 当前 Worker 只处理 `message`/`edited_message` 中的 service message，不消费完整 `chat_member` 更新。
- Telegram Bot API 当前调用链不能枚举全量普通群成员。
- 前端没有统一群运营详情，也没有成员分类 API。

因此阶段 5 的真实用户范围固定为：从观察能力启用后，Guardian 在有效自建群绑定中看到过入群、发言或退群事件的用户。

### 2.4 开发前置门槛

进入联调前必须满足：

1. 阶段 1 的 `OwnedGroupAsset.core_group_id`、`managed_binding_id`、`guardian_bot_account_id` 已存在并通过唯一性检查。
2. 阶段 2 的消息摘要/eligible accounts 合同已冻结。
3. 阶段 3 的账号 Persona 字段与账号页深链已冻结。
4. 阶段 5 迁移必须接在合并后的真实 migration head 上；当前候选号是 SQL `052`、Alembic `038`，如阶段 2/3 合并后 head 改变，只重编号，不改变本规格语义。
5. 禁止基于当前 `Violation` 数据构造群成员或群级风险统计。现有 Guardian 处罚链存在 Telegram User ID 与 `User.id` 语义混用风险，见 2.5。

### 2.5 已知但不属于阶段 5 的 Guardian 用户 ID 缺陷

`Violation.user_id` 是外键 `User.id`，但当前 Guardian 违规调用链把 Telegram User ID 直接传入处罚管理器。阶段 5 不读取 Violation、不返回群级违规数，因此不把这一旧缺陷扩进成员分类与前端整合工作量。独立缺陷 `GUARDIAN-ID-001` 的修复合同如下：

- 参数命名拆分为 `telegram_user_id` 与 `local_user_id`，禁止继续使用无语义的 `user_id` 跨边界传递。
- 在进入 `calculate_punishment`、`record_violation`、`get_warning_count` 前，通过 `User.telegram_id` 获取或创建本地 `User`，向处罚持久化传 `local_user_id`。
- 向 Telegram 执行禁言、封禁、警告时仍传 `telegram_user_id`。
- 不自动改写既有 `Violation` 行；历史记录只做只读审计，无法证明归属的记录不进入阶段 5 成员摘要。
- 阶段 5 v1 不返回群级 `violation_count`。真实用户只返回 `User` 的全局状态摘要，并明确 `risk_scope=user_global`。

该缺陷进入 Guardian 治理维护 backlog；在任何功能开始使用 Violation 做用户/群风险统计前必须完成，但不是阶段 5 发布门槛，也不修改阶段 5 文件清单。阶段 5 的硬门槛是完全不读取或推断这批歧义历史行。

## 3. 目标、成功标准与非目标

### 3.1 业务目标

1. 运营人员能从一个自建群资产进入编排、治理、成员、消息、活动和审计。
2. 成员列表能可靠区分系统推广账号、系统机器人和已观察真实用户。
3. 同一个 Telegram 身份不会因为出现在多张表而重复显示。
4. 页面明确告诉用户数据覆盖范围、最近观察时间和阻断原因。
5. 能力未配置、已停止或已降级时，按钮不可误导用户继续操作。

### 3.2 成功标准

- `growth` 和 `ad_only` 两种 promoter 账号都归为 `system_ad_account`。
- Bot 即使属于某个推广账号，也只归为 `system_bot`。
- 同一 Telegram User ID 同时出现在系统关系与观察表时只返回一个系统成员。
- 真实用户只在存在群级观察事实时出现。
- 所有新 GET 接口不调用 Telegram、不调用 LLM、不创建默认配置、不写数据库。
- 旧路由全部可用，已有书签不失效。
- 前端不会把 `OwnedGroupAsset.member_count` 展示成 Telegram 总成员数。
- 任何自建群内消息能力不读取增长中心广告配置。

### 3.3 明确不做

- 不抓取或同步 Telegram 全量成员列表。
- 不做历史成员全量回填。
- 不消费新的 `chat_member` update 类型；首版继续复用现有 service message 和普通消息更新。
- 不增加踢人、禁言、提权、移除成员等成员写操作。
- 不允许人工编辑 `member_kind`。
- 不新建统一成员主表，不迁移 `User`、`OwnedGroupMembership`、`GroupAccountMembership`。
- 不合并自建群 Worker、Guardian Worker 和 Growth Worker。
- 不重做阶段 1–3 页面和表单。
- 不新增 WebSocket、跨页实时推送或服务端成员缓存。
- 不把阶段 4 重新包装为“外部群引流”新功能。
- 不自动把自建群链接写入 `AdCreative.link_url`。
- 不聚合外部广告素材、额度、冷却、投放状态或增长中心停止开关。

## 4. 角色与权限

复用现有角色，不建设新的 RBAC 系统。

| 能力 | admin | operator | auditor |
| --- | ---: | ---: | ---: |
| 查看群运营详情 | 是 | 是 | 是 |
| 查看成员与覆盖范围 | 是 | 是 | 是 |
| 查看脱敏任务与审计 | 是 | 是 | 是 |
| 自建群编排写操作 | 是 | 是 | 否 |
| Guardian 接入/reconcile | 是 | 是 | 否 |
| 阶段 2 策略、发送和审核 | 沿用原接口，当前为 admin | 沿用原接口，当前不可写 | 否 |
| Persona 编辑和预览 | 沿用阶段 3，当前为 admin | 否 | 否 |
| 公告与活动写操作 | 沿用原接口权限 | 沿用原接口权限 | 否 |

实现要求：

- 新只读接口复用 `require_owned_group_audit_reader` 的角色集合：`admin/operator/auditor`。
- 前端 `can_manage` 仅控制按钮展示和禁用；所有原写接口仍必须重新鉴权和重新校验业务状态。
- 未识别角色不可看到“群运营中心”菜单；直接访问新接口返回 403。
- 不改变 `/api/owned-groups`、`/api/managed-groups` 等旧接口已有权限行为。

前端必须新增单一权限源 `frontend/src/utils/groupOpsAccess.ts`：

```typescript
export const GROUP_OPS_READ_ROLES = ['admin', 'operator', 'auditor'] as const
export const canReadGroupOps = (role?: string | null) =>
  GROUP_OPS_READ_ROLES.some((item) => item === role)
```

`Layout.vue` 的“群运营中心”分组与新详情路由都调用该 helper，禁止一处复制数组、一处继续只判断 `adminOnly`。`router/index.ts` 为新路由增加 `meta.allowedRoles=GROUP_OPS_READ_ROLES` 并扩展全局守卫：用户信息未加载时先加载；不在白名单则跳 `/dashboard` 且不得挂载详情组件。若角色缓存过期、API 仍返回 403，详情页渲染无权限 `el-result` 并停止其余子请求。未知/null 角色默认拒绝，前端权限仅用于体验，不能替代后端鉴权。

## 5. 标识与命名规范

| 名称 | 类型 | 唯一语义 |
| --- | --- | --- |
| `asset_id` | Integer | `OwnedGroupAsset.id` |
| `core_group_id` | Integer/null | `Group.id`，治理策略内部主键 |
| `telegram_chat_id` | BigInteger/null | Telegram 群/频道 ID |
| `managed_binding_id` | Integer/null | `ManagedGroupBinding.id` |
| `account_id` | Integer/null | `TelegramAccount.id` |
| `owned_bot_profile_id` | Integer/null | `OwnedBotProfile.id` |
| `guardian_bot_profile_id` | Integer/null | `GuardianBotProfile.id` |
| `user_id` | Integer/null | 本地 `User.id` |
| `telegram_user_id` | BigInteger/null | Telegram 用户或 Bot 身份 ID |

规则：

- 新接口和前端代码禁止新增语义不明的 `group_id` 字段。
- 调 Guardian 策略接口时使用 `telegram_chat_id` 作为路径参数，由既有解析器转换成 `core_group_id`。
- 数据库内部关联治理策略时使用 `core_group_id`。
- TypeScript 在接收 Telegram ID 后必须先验证 `Number.isSafeInteger`；失败时只展示原值并禁用深链，不能四舍五入后继续请求。

## 6. 成员观察事实表

### 6.1 表定义

新增模型 `OwnedGroupMemberObservation`，表名固定为 `owned_group_member_observations`。

| 字段 | 类型 | 可空 | 默认 | 说明 |
| --- | --- | ---: | --- | --- |
| `id` | Integer PK | 否 | 自增 | 内部主键 |
| `group_asset_id` | Integer FK | 否 | 无 | 指向 `owned_group_assets.id`，删除资产时 CASCADE |
| `telegram_user_id` | BigInteger | 否 | 无 | 被观察的 Telegram 用户/Bot ID |
| `is_bot` | Boolean | 否 | 无 | Telegram 事件中的身份快照；禁止数据库/server default |
| `username_snapshot` | String(120) | 是 | null | 最近一次公开用户名，不带 `@` |
| `display_name_snapshot` | String(200) | 是 | null | 最近一次 first/last name 合成值 |
| `presence_status` | String(16) | 否 | `present` | 只允许 `present/left` |
| `last_event_type` | String(32) | 否 | 无 | `message/new_chat_member/left_chat_member` |
| `source_bot_account_id` | Integer FK | 是 | null | 产生该观察的当前 Guardian `TelegramAccount.id`，删除时 SET NULL |
| `last_update_id` | BigInteger | 否 | 无 | Telegram Bot API update_id |
| `first_observed_at` | DateTime UTC | 否 | 无 | 第一次成功接受事件的 `message.date` |
| `last_observed_at` | DateTime UTC | 否 | 无 | 最近被接受事件的 `message.date` |
| `joined_at` | DateTime UTC | 是 | null | 最近一次明确 `new_chat_member` 的 `message.date` |
| `left_at` | DateTime UTC | 是 | null | 最近一次明确 `left_chat_member` 的 `message.date` |
| `created_at` | DateTime UTC | 否 | now | 创建时间 |
| `updated_at` | DateTime UTC | 否 | now | 更新时间 |

固定约束：

```text
UNIQUE(group_asset_id, telegram_user_id)
CHECK(presence_status IN ('present', 'left'))
CHECK(last_event_type IN ('message', 'new_chat_member', 'left_chat_member'))
INDEX(group_asset_id, presence_status, last_observed_at)
INDEX(group_asset_id, last_observed_at)
INDEX(telegram_user_id)
INDEX(source_bot_account_id)
```

### 6.2 明确不落库的字段

以下字段禁止写入观察表：

- `member_kind`、`classification_status`。
- `operation_mode`、广告开关、广告额度、广告冷却。
- 账号风险、Persona 内容或 Persona Hash。
- Guardian 处罚汇总、验证状态。
- 消息正文、媒体、邀请链接、手机号、Bot Token、Session、代理信息。

这些值必须在读取时从权威来源补充或推导。

### 6.3 迁移要求

当前候选文件：

```text
backend/migrations/052_add_owned_group_member_observations.sql
backend/migrations/versions/038_add_owned_group_member_observations.py
```

迁移顺序：

1. 确认 SQL 和 Alembic 当前 head。
2. 新建表、外键、唯一约束和索引。
3. 不执行历史回填，不扫描 Telegram。
4. 迁移后空表是合法状态，页面显示“尚未开始观察/暂无已观察用户”。

生产回滚默认保留该表。只有确认旧版本不再写入且明确接受丢失观察数据时，才执行 downgrade 删除表。

## 7. Guardian 观察投影

### 7.1 唯一写入点

在现有 `TelegramWorker._dispatch_guardian_updates` / `_dispatch_guardian_message` 链内增加投影，禁止启动第二个 Bot Poller。

实现时不得在 `update.get("message") or update.get("edited_message")` 之后丢失事件种类。调用链必须显式携带以下上下文（可使用参数或等价的不可变 DTO）：

```python
_dispatch_guardian_message(
    ...,
    update_id: int,
    update_kind: Literal["message", "edited_message"],
)
```

`update_id` 必须来自 Telegram update 外层，不得用 `message_id` 替代；`update_kind` 必须在进入投影器前确定。投影器只把原始 `message` 作为在线事实，`edited_message` 仅继续既有 Guardian 业务处理，不得写入或刷新成员 presence。

调用顺序：

```text
getUpdates 返回 update
  -> 读取 update_id
  -> 解析 message / edited_message，并保留 update_kind
  -> resolve_governance_worker_target
  -> 既有 owned-group Guardian gate
  -> target.allowed 且 target.is_owned_group
  -> 投影本 update 中的成员事实
  -> 继续既有验证、治理、处罚、活动处理
```

只有同时满足以下条件才写观察表：

- `target.is_owned_group=true`。
- `target.allowed=true`。
- `target.owned_group_asset_id` 非空。
- `update_id` 是非负整数。
- Telegram 用户 ID 是正整数。
- 目标用户的 `is_bot` 必须是 JSON boolean（Python 中要求 `type(value) is bool`），不得用缺失值、0/1、字符串或默认 false 猜测。
- 外层 `message.date` 必须能解析成 UTC 时间；缺失、越界或非法时跳过本次投影并记录 `event_time_invalid`。

若治理绑定无效、Bot 不匹配、治理功能关闭或 `governance_stop` 生效，不写观察表。读取接口仍可用，并在 coverage 中显示未采集或已暂停。

事实时间统一取原始 Telegram `message.date` 并规范化为 UTC；`created_at/updated_at` 才取数据库当前时间。禁止用处理机 `now()` 代替缺失的事件时间，否则旧更新会在 Presence 合并时伪装成最新事实。

### 7.2 事件映射

| Telegram 事件 | 目标身份 | 写入状态 | 时间字段 |
| --- | --- | --- | --- |
| 原始普通 `message`（不含 service message）且存在 `from.id` 与正文/媒体 | `from` | `present` | 更新 `last_observed_at`，清空旧 `left_at`，不伪造 `joined_at` |
| 原始 `message.new_chat_members[]` | 数组中每个 member | `present` | 设置 `joined_at`，清空旧 `left_at` |
| 原始 `message.left_chat_member` | 离开的 member | `left` | 设置 `left_at` |

补充规则：

- service message 的操作者不能代替目标成员写入；新增成员取 `new_chat_members[]`，退群取 `left_chat_member`。
- `edited_message` 可能是离群用户编辑旧消息，不能证明当前仍在群；首版不处理其中的普通消息或 service 字段，不得用它插入 observation、刷新时间或把 `left` 改回 `present`。
- 匿名管理员只有 `sender_chat`、没有 `from.id` 时跳过。
- 同一 update 中多个新成员分别 UPSERT，各自使用同一个 `update_id`。
- `is_bot`、用户名和展示名只保存事件中的公开快照。
- 没有正文但有有效媒体的普通消息仍可作为 present 观察。
- 新事件 `is_bot` 与同一 observation 已存值不一致时拒绝覆盖，记录 `identity_type_conflict`；禁止把身份从 Bot 翻转为真人或反向翻转。

### 7.3 幂等与乱序

UPSERT 唯一键为 `(group_asset_id, telegram_user_id)`。

接受规则：

1. 记录不存在：插入。
2. `source_bot_account_id` 与已有记录相同：只有 `incoming_update_id > last_update_id` 才更新。
3. `source_bot_account_id` 不同：拒绝为 `source_bot_mismatch`，不得替换来源或比较两个 Bot 各自不相关的 update 序列。阶段 1 不支持更换主 Guardian Bot；未来若新增换绑能力，必须另行设计 sequence namespace/重建合同。
4. 相同或更小 update ID 视为重放/乱序，返回 `ignored_stale`，不得更新时间或状态。
5. 不以服务器到达时间覆盖 update_id 的顺序判断。

观察投影必须用数据库原子条件写，禁止“先 SELECT、在 Python 比较、再无条件 UPDATE”：

```text
1. INSERT ... ON CONFLICT (group_asset_id, telegram_user_id) DO NOTHING
2. 若未插入：
   UPDATE ...
   WHERE group_asset_id=:asset_id
     AND telegram_user_id=:telegram_user_id
     AND source_bot_account_id=:source_bot_account_id
     AND is_bot=:incoming_is_bot
     AND last_update_id < :incoming_update_id
3. UPDATE rowcount=0 时只读当前最小字段，判定 ignored_stale / source_bot_mismatch / identity_type_conflict
```

所有 presence、事件时间、快照和 `last_update_id` 必须在同一条条件 UPDATE 中改变。这样并发 update 101/102 无论执行顺序如何，最终都只能保留 102。PostgreSQL 并发集成测试为 P0；观察投影仍不创建逐消息审计事件。

### 7.4 失败隔离

- 每个 update 的投影使用独立数据库 Session 和短事务并在返回前提交；禁止复用 Worker 当前整批 Guardian Session，也不能仅依赖该批 Session 内的 savepoint。
- 投影失败不得阻断既有验证、治理、处罚、活动和消息处理。
- 严禁持有数据库事务跨越 Telegram 或 LLM 网络调用。
- 失败记录结构化日志和计数指标，不记录消息正文、用户名原文或 Token。
- 对明确的瞬时数据库错误允许在当前调用内立即重试 1 次；仍失败则记录 `observation_gap` 日志/指标并继续 Guardian 主流程。
- 现有 Worker 在 dispatch 前已经推进 update offset，因此不得承诺下一轮自动重放，也不在阶段 5 新建 outbox。后续该成员的新事件可以修复最新状态；阶段 5 没有持久 gap 字段，新 GET 不得假装能精确返回某次 gap，页面只维持统一的 partial coverage 告警。
- 成功 UPSERT 继续受 update_id 幂等保护；任何后续 Guardian 业务异常不得回滚已独立提交的 observation。

## 8. 三类成员分类合同

### 8.1 业务枚举

```text
MemberKind = real_user | system_ad_account | system_bot
ClassificationStatus = resolved | unresolved | conflict
PresenceStatus = present | pending | left | failed | unknown
PresenceConfidence = verified | observed | stored | unknown
DataQuality = reliable | partial | conflict
```

`unresolved/conflict` 是数据质量状态，不是第四种业务成员类型。此时 `member_kind=null`，前端显示“待修复”，并禁用成员相关动作。

固定分类原因：

```text
asset_owner_promoter
owned_membership_promoter
group_membership_promoter
owned_membership_bot
guardian_binding_bot
observed_real_user
third_party_bot_unmanaged
identity_incomplete
system_identity_conflict
```

固定质量码：

```text
identity_incomplete
third_party_bot_unmanaged
telegram_identity_conflict
system_identity_conflict
target_mapping_invalid
source_record_missing
presence_source_conflict
```

计算规则固定：`classification_status=conflict` 当且仅当存在身份冲突；无法归入三类但仍需展示时为 `unresolved`；恰好归入一类时为 `resolved`。`data_quality=conflict` 当且仅当 classification 为 conflict；classification 为 unresolved 或 `quality_codes` 非空时为 `partial`；其余为 `reliable`。presence confidence 与全群 roster coverage 使用各自字段表达，不得为了“非全量”把每一条正确系统成员都降为 partial。未识别的后端 reason/code 前端统一显示“未知数据质量问题”并保留转义后的原值用于排障。

### 8.2 候选来源

| 来源 | 用途 | 主键语义 |
| --- | --- | --- |
| `OwnedGroupAsset.owner_account_id` | 草稿阶段也显示预定群主 | `TelegramAccount.id` |
| `OwnedGroupMembership(user)` | 系统推广账号主要成员关系 | `resource_id=TelegramAccount.id` |
| `OwnedGroupMembership(bot)` | Owned Bot 主要成员关系 | `resource_id=OwnedBotProfile.id` |
| `GroupAccountMembership` | 系统推广账号补充关系 | `account_id=TelegramAccount.id` |
| `ManagedGroupBinding` + asset Guardian 字段 | 当前主 Guardian Bot | `bot_account_id=TelegramAccount.id` |
| `OwnedGroupMemberObservation` | Guardian 已观察身份 | `telegram_user_id` |
| `User` | 真实用户资料补充 | `User.telegram_id=telegram_user_id` |

`VerificationSession`、`Violation`、`CampaignTracking`、`CampaignExecution` 不作为阶段 5 v1 的当前成员来源。它们可以在后续历史重建需求中使用，但不能在本阶段冒充当前群关系。

### 8.3 分类优先级

同一群、同一 Telegram 身份合并后，优先级固定为：

```text
system_bot > system_ad_account > real_user
```

#### system_bot

满足任一有效群关系：

1. `OwnedGroupMembership.resource_type=bot` 且 `resource_id` 能解析到 `OwnedBotProfile`。
2. 当前资产的 `guardian_bot_account_id` 与有效 `ManagedGroupBinding.bot_account_id` 一致。
3. 上述群关系解析出的账号 `TelegramAccount.account_type=guardian_bot`。

`OwnedBotProfile.owner_account_id` 只作为 `parent_account_id` 展示，不能把 Bot 归类为推广账号。

同一逻辑 Bot 先以 `TelegramAccount.id` 归并 binding、Owned profile 和 Guardian profile。然后收集 `OwnedGroupMembership.telegram_user_id`、`OwnedBotProfile.bot_user_id`、`GuardianBotProfile.bot_user_id` 的所有非空值：唯一值为 0 个时标记 `identity_incomplete`；唯一值为 1 个时作为 Bot Telegram 身份；唯一值大于 1 个时返回 `classification_status=conflict`、`member_kind=null`、`quality_codes=[telegram_identity_conflict]`，禁止任选 ID，也禁止吸收该 ID 对应的 real-user observation。

第三方 Bot 只有观察记录且 `is_bot=true`、没有任何系统 Bot 关系时，不归为 `real_user`；返回 `member_kind=null`、`classification_status=unresolved`、reason=`third_party_bot_unmanaged`。

#### system_ad_account

满足：

- 本群存在 `OwnedGroupAsset.owner_account_id`、`OwnedGroupMembership(user)` 或严格匹配的 `GroupAccountMembership` 群关系；且
- 关联 `TelegramAccount.account_type=promoter`。

`AccountOperationConfig.operation_mode=growth|ad_only` 只是账号职责标签，不参与成员类别判定。两种模式都必须归为 `system_ad_account`。

#### real_user

满足全部条件：

- 存在本资产 `OwnedGroupMemberObservation`；
- `is_bot=false`；
- `telegram_user_id` 未命中任何本群系统账号或系统 Bot 身份。

仅存在全局 `User` 行而没有群观察记录时，禁止把该用户放入本群。

### 8.4 GroupAccountMembership 使用边界

只有满足以下双重映射才可作为补充候选：

```text
membership.group_id == asset.core_group_id
membership.telegram_group_id == asset.telegram_chat_id
```

若任一资产 ID 为空，不使用该来源；若两项发生冲突，记录 `target_mapping_invalid`，不能任选一个 ID 继续。

只允许读取：

- `group_id`
- `telegram_group_id`
- `account_id`
- `status`
- `joined_at`
- `left_at`
- `last_checked_at`
- `updated_at`

禁止用以下字段计算自建群成员能力或群内消息资格：

- `warmup_status`
- `probe_status`
- `ad_status`
- `ad_eligible_after`
- `ad_pause_until`
- `account_group_daily_cap`
- 任何广告发送、广告存活或增长中心冷却字段

### 8.5 去重与稳定 member_key

系统成员使用稳定内部资源键：

```text
system_ad_account:account:{account_id}
system_bot:account:{account_id}
real_user:telegram:{telegram_user_id}
unresolved:{source}:{source_id}
conflict:telegram:{telegram_user_id}
conflict:system_bot:account:{account_id}
```

系统 Bot 永远用 `account_id` 生成 member_key；`OwnedBotProfile.account_id` 有唯一约束，profile 后补或重建不会改变 key。`owned_bot_profile_id` 与 `guardian_bot_profile_id` 只作为可空详情字段，不能参与 key 或互相替代。

同一 Telegram ID 命中多个系统资源时合成一条 `conflict:telegram:*` 行，不返回多条互相矛盾的系统行；同一 Bot account 的三来源 Telegram ID 内部冲突时用 `conflict:system_bot:account:*`。`unresolved:{source}:{source_id}` 的 source 只允许 `owned_membership/guardian_binding/group_membership/observation`，使用对应数据库主键；禁止使用数组下标、名称或随机 UUID。

去重步骤：

1. 先按 account_id 归并系统 Bot 来源并校验三处 Telegram ID，再建立无冲突的系统 Bot Telegram ID 索引。
2. 建立系统推广账号的 Telegram ID 索引。
3. 合并同一系统资源的 Owned membership、Group membership、Observation。
4. 删除已被系统索引吸收的 real-user observation 候选。
5. 对剩余 observation 按 `telegram_user_id` 生成真实用户行。
6. 缺少 Telegram ID 的系统资源仍单独展示，标记 `identity_incomplete`。

同一 Telegram ID 命中多个不同系统账号、或命中多个不同系统 Bot account 时，不按最小 ID 静默选择；返回 conflict 质量项并记录指标。

### 8.6 群内角色

```text
TelegramRole = owner | administrator | member | unknown
```

优先级：

1. `account_id == asset.owner_account_id` -> `owner`。
2. 当前 Guardian binding 的 `bot_role=owner|admin`。
3. `OwnedGroupMembership.is_admin=true` -> `administrator`。
4. 已确认或观察在群 -> `member`。
5. 其他 -> `unknown`。

阶段 5 v1 的成员行只返回 `telegram_role/is_admin/admin_title`，不返回细粒度 `permissions` 字段。原因是 `OwnedGroupMembership.permissions_snapshot` 使用 Telethon 风格键，而 `ManagedGroupBinding.permissions_snapshot` 使用 `granted_permissions=[can_*]`，两者不是同一 schema；本阶段不做未经验证的扁平合并或名称映射。

任何来源的原始 `permissions_snapshot` 都不得进入成员 API。能力卡的顶层 `permissions.manage_*` 是当前登录人的产品权限，与 Telegram 成员权限无关，继续按摘要合同返回。若未来需要展示细权限，必须另立 source-specific sanitizer、来源优先级和冲突验收。

### 8.7 Presence 合并

来源事实时间：

| 来源 | 时间字段 |
| --- | --- |
| Observation | `last_observed_at` |
| OwnedGroupMembership | `last_verified_at`，为空则 `updated_at` |
| GroupAccountMembership | `last_checked_at`，为空则 `updated_at` |

先取时间最新的事实；时间相同按以下优先级：

```text
OwnedGroupMemberObservation > OwnedGroupMembership > GroupAccountMembership
```

Owned membership 映射：

| 原状态/事实 | presence | confidence |
| --- | --- | --- |
| `member_verified/admin_verified/skipped_already_member` | present | verified |
| `joined_at` 或 `last_verified_at` 非空，且无更新的离群事实 | present | verified |
| `pending/in_progress/invite_sent/waiting_approval/admin_promoting` | pending | stored |
| `failed_transient/failed_permanent/cancelled` 且从未核验 | failed | stored |
| `unknown/unknown_needs_reconcile` | unknown | unknown |

Group membership 映射：

| 原状态/事实 | presence | confidence |
| --- | --- | --- |
| `status=joined` 且 `left_at=null` | present | stored |
| `left_at!=null` 或 `status in (left,banned,rejected)` | left | stored |
| `status in (pending,joining)` | pending | stored |
| 其他 | unknown | unknown |

Observation 映射：

| 原状态 | presence | confidence | UI 文案 |
| --- | --- | --- | --- |
| `present` | present | observed | 最近观察为在群 |
| `left` | left | observed | 最近观察为离群 |

`observed` 不等于 Telegram 实时核验，前端不得只显示“在群”而隐藏置信度。

## 9. 覆盖范围与计数合同

所有摘要和成员响应都必须返回 coverage：

```json
{
  "data_scope": "managed_and_observed",
  "is_complete": false,
  "full_roster_supported": false,
  "coverage_status": "collecting",
  "observation_started_at": "2026-09-11T10:00:00Z",
  "last_observed_at": "2026-09-11T10:20:00Z",
  "blocking_reasons": ["telegram_full_roster_not_loaded"]
}
```

`coverage_status`：

| 状态 | 条件 |
| --- | --- |
| `historical` | 资产 archived；或已有观察但当前已无有效 managed Guardian 绑定 |
| `degraded` | 资产/Group/Binding ID 冲突或 Guardian degraded |
| `paused` | 有效绑定仍存在，但静态/运行时治理停止门禁阻断观察 |
| `collecting` | 有效 managed Guardian 当前允许处理更新 |
| `not_started` | 无观察记录，且资产未形成有效 managed Guardian 绑定 |

`is_complete` 在阶段 5 永远是 `false`。任何开发者不得根据观察数量接近 Telegram 快照人数而改成 `true`。

判定顺序固定为：asset archived -> `historical`；映射冲突/Guardian degraded -> `degraded`；有效绑定被 stop -> `paused`；有效绑定允许处理 -> `collecting`；已有观察但绑定失效/删除 -> `historical`；否则 `not_started`。不得因表格顺序或第一个命中条件不同产生另一结果。`historical` 的 blocking reason 必须区分 `asset_archived` 与 `governance_binding_missing`。

`observation_started_at = MIN(first_observed_at)`，`last_observed_at = MAX(last_observed_at)`，均限定当前 asset；空表时两者均为 null。它们描述已提交 observation 的时间边界，不是 Worker 心跳或 Telegram 全量同步时间。

计数字段：

```text
managed_resource_count
observed_real_user_count
counts_by_kind.real_user
counts_by_kind.system_ad_account
counts_by_kind.system_bot
unresolved_count
conflict_count
```

计数按成员 API 的去重与分类函数计算，不能由前端自己相加。列表 `total` 是应用本次全部过滤条件后、分页前的去重行数；响应 `summary` 始终是该 asset 全量去重读模型的过滤前摘要。`counts_by_kind` 只统计 resolved 行，并包含 latest presence 为 present/pending/left/failed/unknown 的所有行；`unresolved_count/conflict_count` 单列，不重复进入 kind 计数。`observed_real_user_count` 等于过滤前去重后的 `real_user` 总数，包含最后观察为 left 的用户，因此只能解释为“观察过”，不能解释为当前在群人数。

```json
  "data": {},

```

列表额外返回：

```json

  "data": [],

  "offset": 0,
  "limit": 50,

```

### 10.3 错误信封

```json
{
  "error": {
    "code": "OWNED_GROUP_NOT_FOUND",
    "message": "Owned group asset was not found",
    "details": {},
    "retryable": false
  },
  "correlation_id": "group-ops-..."
}
```

统一错误：

| HTTP | code | 使用条件 |
| ---: | --- | --- |
| 401 | `AUTHENTICATION_REQUIRED` | 未登录/Token 无效 |
| 403 | `OWNED_GROUP_ROLE_FORBIDDEN` | 非 admin/operator/auditor |
| 404 | `OWNED_GROUP_NOT_FOUND` | asset 不存在 |
| 422 | `MEMBER_QUERY_INVALID` | 非法枚举、分页、搜索参数 |
| 503 | `OPERATIONS_CENTER_READ_FAILED` | 摘要来源数据库读取失败 |
| 503 | `MEMBER_SOURCE_READ_FAILED` | 成员来源数据库读取失败 |

上述统一信封仅应用于新增的两个 GET，不全局修改旧接口。新增 router 必须指定专用 `OwnedGroupOperationsAPIRoute`（或等价的 router-local exception adapter），在 route handler 最外层统一转换：

- `get_current_user`/reader dependency 抛出的 401、403 `HTTPException`。
- path/query Pydantic 校验产生的 `RequestValidationError`，映射为 422 `MEMBER_QUERY_INVALID`。
- service 的 typed 404/503 错误。
- correlation ID 从安全请求头复用或生成，并在成功/失败信封中一致返回。

这里“复用 `require_owned_group_audit_reader`”只表示复用同一角色集合与鉴权语义，不得直接沿用其默认 `{detail: ...}` 响应形状。测试必须断言 401/403/404/422/503 的完整 JSON 信封；旧 `/audit-events` 和旧 operation API 响应不变。

下列业务状态不能返回 HTTP 失败，必须进入 section、coverage 或成员质量信息：

```text
target_mapping_invalid
governance_not_managed
member_data_scope_partial
member_observation_paused
member_identity_incomplete
member_classification_conflict
messaging_disabled
messaging_dry_run
```

### 10.4 只读保证

两个 GET 接口必须满足：

- 不调用 Telegram。
- 不调用 LLM。
- 不写 Redis。
- 不创建默认策略、Persona 或 runtime settings。
- 不更新 `last_checked_at`。
- read-model/service 不执行 `add/delete/flush`；现有 `get_db` 请求生命周期可以提交一个无写入事务。
- 单个 section 不可用时仍返回 200 和阻断原因，不能让整页因未配置能力变成 409。

### 11.3 section state 计算

`state` 只允许：

```text
ready | not_configured | pending | degraded | disabled | stopped | unavailable
```

同一 section 同时命中多项时，优先级固定：asset archived 规则 > `unavailable` > 映射冲突/`degraded` > `stopped` > `pending` > `not_configured` > `ready`。其中 archived 使 orchestration/governance/messaging/activities 为 `disabled` 且不可写；members/audit 仍可读，并附 `asset_archived`。非 archived 的“已有 observation 但绑定失效”使 members 为 `not_configured`、`can_view=true`，coverage 为 `historical`。各 section 不得用对象遍历顺序决定状态。

#### orchestration

- asset `ready` -> `ready`。
- `draft/prechecking/creating` -> `pending`。
- `create_failed/needs_attention` -> `degraded`。
- `archived` -> `disabled`，只读可见。
- `can_manage` 为 admin/operator 且非 archived。
- `can_execute` 还必须通过既有 owned-group module gate，不能只看角色。

#### governance

- `governance_status=managed` 且映射一致 -> `ready`。
- `pending` -> `pending`。
- `degraded` 或 ID/绑定冲突 -> `degraded`。
- `disabled` 且可配置 -> `not_configured`。
- 静态开关或运行时 stop -> `stopped`。
- 资产非 ready、无 Telegram Chat ID 或无 core group -> `unavailable`。

#### members

- 对 reader 始终 `can_view=true`。
- 阶段 5 无成员写操作，`can_manage=false`、`can_execute=false`。
- 有有效观察链 -> `ready`，但始终带 `member_data_scope_partial`。
- 观察被 gate 停止 -> `stopped`。
- 映射冲突 -> `degraded`。
- 未治理且无观察 -> `not_configured`。

#### messaging

必须复用阶段 2 自建群消息运行态：

- 静态开关、runtime enabled、dryRun、资产状态、策略计数。
- `can_execute` 只表示当前阶段 2 门禁允许发送，不代表某个账号一定可发送。
- 不能读取增长中心 `auto_ads_enabled`、广告额度、广告冷却、广告 campaign 或增长中心 stop。

#### activities

- 有有效 managed binding -> `ready`。
- 未接入治理 -> `not_configured`。
- degraded/停止 -> 对应 `degraded/stopped`。
- 权限沿用既有活动接口。

#### audit

- admin/operator/auditor -> `ready`、`can_view=true`。
- 始终无 `can_execute`。

### 11.4 查询和一致性

- 摘要使用最新已提交数据，属于弱一致性快照。
- 返回 `snapshot_at`，不宣称所有子系统共享同一个版本号。
- 不为追求单一事务而跨模块加锁。
- 单个可选来源不存在时返回 null/0 和阻断原因；只有资产主查询或数据库整体失败才返回 503。
- 禁止 N+1；每个摘要集合使用聚合查询或批量 join。

### 12.4 排序稳定性

- `last_observed_desc`：`COALESCE(last_observed_at,last_verified_at,joined_at,created_at) DESC`，再按 `member_key ASC`。
- `name_asc`：规范化 display name/username，null 最后，再按 `member_key ASC`。
- `kind_asc`：`system_bot`、`system_ad_account`、`real_user`、unresolved，随后按名称和 member_key。
- 分页期间允许新观察导致 total 和页内容轻微变化；阶段 5 不建设快照游标。

### 12.5 性能要求

- 服务端完成 join、去重、分类和分页，前端禁止拉全量后分类。
- 不能对每个成员逐条查询账号、User、Persona 或 Bot profile。
- 目标规模：单群 10,000 条 observation、100 个系统资源。
- 本地 PostgreSQL 基准下，limit=50 的成员接口 p95 目标小于 500ms；摘要接口 p95 目标小于 500ms。
- 查询计划必须命中 `group_asset_id` 领先索引；发现全表扫描必须在合并前处理。

## 13. 分类服务实现合同

新增纯读服务 `OwnedGroupOperationsReadModel`，建议拆出纯函数分类器：

```python
classify_member_candidates(candidates, asset) -> ClassificationResult
merge_presence(facts) -> PresenceResult
build_member_key(candidate) -> str
```

服务步骤固定：

1. 加载资产及关联 Group/Binding。
2. 批量加载 Owned memberships。
3. 收集 account IDs、Owned Bot profile IDs。
4. 批量加载 TelegramAccount、OwnedBotProfile、GuardianBotProfile；AccountOperationConfig 只能做列投影读取 `account_id/operation_mode`。
5. 严格匹配后以列投影批量加载 GroupAccountMembership 的 8 个允许字段。
6. 按资产加载 observation。
7. 用 observation Telegram IDs 批量左连接 `User`。
8. 构造候选并执行统一去重、分类、presence 合并。
9. 先应用服务端过滤，再执行稳定排序和分页。
10. 构造 summary 与 coverage。

分类函数不得依赖 FastAPI、数据库 Session、Redis、Telegram client 或前端路由。

测试中必须用表驱动覆盖每种来源组合、冲突和缺失字段。

| 任务 ID | `id`，显示 `#id` |
| 状态 | `status`；已知状态映射中文 Tag，未知值用灰色 Tag 安全显示原值 |

| 更新时间 | `updated_at` |

任务状态白名单为 `draft/queued/running/paused/stopping/stopped/completed/partial_completed/failed/unknown`。默认每页 20 条，可选 20/50/100；状态筛选变化后 offset 重置为 0；顺序完全采用服务端返回的 ID 倒序，不做跨页客户端排序。

审计表：

| 列 | 数据源与显示规则 |
| --- | --- |
| 时间 | `created_at` |
| 事件 | `event_type`，自由字符串，未知值原样转义显示 |
| 结果 | `result`，未知值使用中性 Tag 原样显示 |

- 定义判别联合类型。
- 校验信封和必要字段。

- 不做成员分类、不合并数据源。
- 不持久化手机号、私链或其他敏感字段到浏览器 storage。

## 17. 安全与隐私

## 18. 事务、一致性与故障处理

### 18.1 事务边界

- 观察 UPSERT 是唯一阶段 5 写事务。
- 分类与两个 GET 是纯读，不加行锁、不写回分类结果。
- 不持有事务跨越 Telegram/LLM 请求。
- 每个 update 的观察投影必须使用独立 Session 和独立短事务，并在 projector 返回前提交；不得仅使用 Worker 批 Session 或其 savepoint，确保后续 Guardian 异常不会回滚已提交 observation。

### 18.2 弱一致性

- summary 和 member list 都表示请求时已提交的最近状态。
- 多个来源可能在毫秒级不同步，使用 `snapshot_at`、source time 和 data quality 对用户说明。
- 不通过任意覆盖来隐藏冲突。

### 18.3 故障矩阵

| 故障 | 行为 |
| --- | --- |
| observation UPSERT 失败 | 记录指标，Guardian 主流程继续 |
| account/profile 缺失 | unresolved，成员页仍返回 |
| asset/Core Group 映射冲突 | members section degraded；不使用 Group membership 补充 |
| Guardian 未配置 | 系统编排成员可读，coverage not_started |
| governance stop | 历史成员可读，coverage paused |
| Persona 阶段尚未联调 | persona 字段 null，深链 disabled，不影响成员分类 |
| 消息阶段尚未联调 | messaging section unavailable，不影响其他 section |
| audit API 失败 | 审计 Tab 局部失败，成员可用 |
| 未知枚举 | 显示 unknown/质量提示，不崩页 |

## 24. 上线与灰度

### 24.1 上线顺序

1. 备份数据库并记录当前 migration head。
2. 应用 observation 迁移。
3. 发布后端模型、projector 和只读 API。
4. 保持前端入口未曝光，验证 API 权限、脱敏、性能和分类样本。
5. 发布前端菜单和运营详情。
6. 选择一个 test owned group 开始观察。
7. 对照 service message、普通消息和退群事件验证 observation。
8. 阶段 6 再进行两账号以内真实 Telegram 灰度和全量回归。

### 24.2 灰度检查

- 同一用户重放 update 不增加记录。
- 系统账号发言不会生成重复 real user 行。
- Guardian stop 后 observation 不再增长且页面显示 paused。
- Growth 广告开关、额度和 cooldown 变化不改变本页消息能力。
- 页面所有数量使用正确口径。
- 页面无手机号、Token、Session、私链和消息正文。

### 24.3 回滚

- 前端回滚后旧 `/owned-groups`、`/guardian/groups`、`/guardian/policies` 继续可用。
- 后端回滚时停止 observation writer；默认保留新表和数据。
- 若只读 API 异常，可先撤下新菜单/路由，不影响阶段 1–3 原接口。
- 不因运营中心异常停止 Growth Center，也不因 Growth Center 异常停止自建群消息。

- coverage 始终明确 partial，页面不存在“Telegram 全量成员”暗示。
- 运营详情、成员、任务/审计三个 Tab 可用。
- 阶段 1–3 页面只通过入口和深链复用，没有复制业务逻辑。

## 26. 已固定决策与开发禁止项

### 26.1 已固定决策

1. 阶段 5 增加一张轻量 observation 表，不建设全量统一成员主表。
2. observation 只保存事实；`member_kind` 读时推导。
3. 三类优先级为 `system_bot > system_ad_account > real_user`。
4. promoter 的 `growth/ad_only` 均为系统广告账号，mode 只是标签。
5. 真实用户数据范围是 Guardian 已观察，不是 Telegram 全量实时名单。
6. 新增接口仅两个，资产列表和审计/任务继续复用现有接口。
7. 前端新增一个运营详情壳，不重写阶段 1–3 页面。
8. 旧路径全部保留。
9. 阶段 4 仍为取消状态；阶段 5 不新增引流卡片、状态、按钮或 API，原 Growth Center 菜单保持独立。
10. 自建群内部消息不受增长中心广告配置、额度、冷却或 stop 影响。

### 26.2 开发禁止项

- 禁止前端自行读取多张表/API 并分类成员。
- 禁止持久化可人工编辑的 member kind。
- 禁止把全局 User 当作任意群的成员。
- 禁止把第三方 Bot 归为真实用户。
- 禁止把 observation present 文案写成“当前在群”。
- 禁止把 `OwnedGroupAsset.member_count` 命名为群总人数。
- 禁止用增长中心 ad status 决定自建群消息卡状态。
- 禁止从详情页自动创建广告素材或写 link_url。
- 禁止在 GET 摘要/成员时触发 Telegram、LLM、Redis 写入或默认配置创建。
- 禁止在日志或接口返回 Token、Session、手机号、私链、消息正文和原始异常。
- 禁止为阶段 5 新建第二个 Telegram Poller、统一 Worker 或成员操作状态机。

## 27. 最终开发边界

阶段 5 完成后，产品能可信地回答：

- 这个自建群当前有哪些系统推广账号和系统机器人；
- Guardian 从启用观察以后见过哪些真实用户，以及最后一次观察状态；
- 当前群的编排、治理、消息、活动和审计能力分别处于什么状态；
- 下一步应进入哪个既有页面操作，以及为什么某项操作不可用。

阶段 5 仍不能回答：

- Telegram 当前完整成员名单是什么；
- 未被 Guardian 观察到的成员是谁；
- 某个真实用户此刻一定仍在群内；
- 外部群广告是否已经为该自建群完成配置或产生转化。

这些边界必须同时体现在接口字段、页面文案、验收用例和上线说明中。
