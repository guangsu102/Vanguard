## 二、代码规范

### 2.1 文件行数限制

| 文件类型 | 行数限制 |
|----------|----------|
| Python 文件 | ≤ 500 行 |
| Vue 组件 | ≤ 300 行 |
| 配置文件 | ≤ 200 行 |

**拆分原则**：按职责/功能/层级拆分，禁止单文件过大。

### 2.2 类描述规范

**所有类必须包含 docstring，描述类的作用**

```python
class TelegramAccount:
    """
    Telegram 用户账号封装类

    负责管理单个 Telegram 账号的连接状态、消息收发。
    支持代理IP绑定和设备指纹模拟。

    Attributes:
        phone: 手机号（带国际区号）
        api_id: Telegram API ID
        status: 账号当前状态
    """

    def __init__(self, phone: str, api_id: str, api_hash: str):
        ...
```

**docstring 要素**（必需项用 ✓ 标记）：

| 要素 | 说明 | 必需 |
|------|------|------|
| 一句话描述 | 类的主要职责 | ✓ |
| 详细说明 | 功能、用途、特点 | 推荐 |
| Attributes | 公共属性 | 推荐 |
| Example | 使用示例 | 推荐 |

### 2.3 Python 代码规范

**遵循 PEP 8 + 类型提示**

| 规则 | 说明 |
|------|------|
| 命名 | 类名 `PascalCase`，函数/变量 `snake_case`，常量 `UPPER_SNAKE_CASE` |
| 类型提示 | 所有函数参数和返回值必须标注类型 |
| 异步 | IO 操作必须使用 `async/await`，禁止混合同步代码 |
| 异常 | 使用具体异常类型，禁止裸 `except:` |
| 文档 | 类和公开方法必须写 docstring |

### 2.4 Vue 代码规范

- 使用 Composition API (`<script setup>`)
- 组件样式使用 `scoped`
- 类型定义使用 TypeScript

## 三、Git 使用规范

### 3.1 分支命名

```
main                    # 主分支（生产环境）
├── develop             # 开发主分支
├── feature/xxx         # 功能分支
├── fix/xxx             # 修复分支
├── refactor/xxx       # 重构分支
└── docs/xxx           # 文档分支
```

### 3.2 提交信息格式

```
<type>(<scope>): <subject>

<body>

<footer>
```

| Type | 说明 | 示例 |
|------|------|------|
| feat | 新功能 | `feat(account): 添加账号连接功能` |
| fix | Bug 修复 | `fix(keyword): 修复关键词匹配遗漏` |
| docs | 文档更新 | `docs: 更新API文档` |
| style | 代码格式 | `style: 格式化代码` |
| refactor | 重构 | `refactor: 重构账号管理模块` |
| test | 测试 | `test: 添加关键词测试用例` |
| chore | 构建/工具 | `chore: 更新依赖版本` |

### 3.3 PR 规范

```
## 概述
[简要描述本次改动]

## 改动类型
- [ ] 新功能 / Bug 修复 / 重构 / 文档更新

## 影响范围
[涉及模块]

## 测试情况
- [ ] 单元测试通过
- [ ] 集成测试通过

## 截图/日志
[如有UI改动或关键日志]
```

## 四、API 设计规范

### 4.1 RESTful 规范

| 方法 | 端点 | 说明 |
|------|------|------|
| GET | /api/accounts | 获取列表 |
| POST | /api/accounts | 创建资源 |
| GET | /api/accounts/{id} | 获取单个 |
| PUT | /api/accounts/{id} | 完整更新 |
| DELETE | /api/accounts/{id} | 删除资源 |
| POST | /api/accounts/{id}/connect | 资源操作 |

### 4.2 响应格式

```json
// 成功
{ "code": 0, "message": "success", "data": {...} }

// 错误
{ "code": 1001, "message": "错误信息", "data": null }
```

### 4.3 错误码

| 范围 | 类型 |
|------|------|
| 0 | 成功 |
| 1000-1999 | 通用错误 |
| 2000-2999 | 账号错误 |
| 3000-3999 | 群组错误 |
| 4000-4999 | 业务错误 |

- 使用 Docker Compose 部署
- 环境变量通过 `.env` 文件管理
- 敏感信息禁止硬编码

### 7.2 环境优先级

```
.env.local > .env.development > .env.staging > .env.production > .env.example
```

### 7.3 容器规范

- 非 root 用户运行
- 敏感文件通过 volume 挂载

## 八、安全规范

### 8.1 敏感信息处理

| 类型 | 处理方式 |
|------|----------|
| 密码 | BCrypt 加密，禁止明文 |

### 8.2 禁止硬编码

```python

api_key = os.getenv("TELEGRAM_API_KEY")

# ✗ 错误
api_key = "123456"  # 禁止！
```

## 十、开发流程

### 10.1 设计评审流程

**按复杂度分级管理设计评审，简化小型改动流程**

#### 10.1.1 设计分级

| 级别 | 判断条件 | 设计方式 |
|------|----------|----------|
| **L0 - 口头** | 纯格式化/注释/变量重命名，不影响逻辑 | 口头确认即可 |
| **L1 - 轻量设计** | 小功能，不影响现有接口，改动 <500 行 | PR 描述 + 简单方案说明 |
| **L2 - 完整设计** | 核心模块/接口/数据库变更 | 完整设计文档 + 评审 |

#### 10.1.2 L2 触发条件（满足任一即需完整设计）

- 涉及 `core/` 核心模块
- 修改已有 API 接口
- 数据库表结构变更
- 预估影响 > 3 个模块
- 涉及安全/权限逻辑
- 引入新外部依赖

### 10.2 需求变更管理

**开发计划确认过程中，如果需求发生变更，必须同步更新需求文档**

变更触发条件：
- 功能点增加/删除/修改
- 接口参数变化
- 业务流程调整
- 优先级调整
- 验收标准修改

变更流程：发现变更 → 评估影响 → 更新文档 → 通知确认 → 继续开发

### 10.3 完整开发流程

```
需求阶段   → 需求确认清单
    ↓
设计阶段   → 技术设计文档 → 评审 → 确认通过
    ↓
开发阶段   → 代码开发 → 单元测试 → 自测
    ↓
测试阶段   → 集成测试 → 功能测试 → 性能测试
    ↓
上线阶段   → 代码审查 → 部署 → 验证
```

### 10.4 发布流程

```
develop → 预发布环境 → 测试 → main → 生产环境

版本号：v{MAJOR}.{MINOR}.{PATCH}
- MAJOR: 不兼容的 API 变更
- MINOR: 向后兼容的功能新增
- PATCH: 向后兼容的问题修复
```
